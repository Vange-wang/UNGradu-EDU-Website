## 1. 目标、背景和非目标

### 1.1 背景与问题

当前需求方文本 childIntro、老师资料文本 abilityDescription 已有少量连续大陆
手机号和微信关键词规则，但没有覆盖邮箱、座机、QQ、网址、分隔混淆、长数字、中文
数字、Unicode 混淆和语义暗示。业务方希望提交后有快速审核期，重点识别夹带联系
方式，并倾向 AI 智能审核。

联系方式在本平台不是普通公开字段：站内沟通先行，只有双方完成联系方式交换授权后
才显示各自预存联系方式。因此审核既要防止公开文本绕过隐私规则，也不能把存档联系
方式、聊天正文或未成年人资料发送给不必要的外部服务。

### 1.2 产品目标

1. 在需求/老师资料成为公开版本前，对确定性联系方式和隐蔽变体进行可解释检测。
2. 对语义不确定或检测器冲突的内容进入人工复核，不把 AI 输出当唯一证据。
3. 让所有状态、拒绝原因、重试、申诉、审计和回滚可观察、可幂等、可恢复。
4. 保持 ISSUE-0033 已完成的所有权、版本、软删除、聊天和联系方式门控不变。
5. 通过本地、集成、预生产、生产和业务验收矩阵，区分技术可用与用户接受。

### 1.3 非目标

* 不决定最终 AI/规则供应商、模型、部署地域、数据处理协议、预算或法律保留期。
* 不把 AI、OCR 或第三方服务写成唯一真相，不自动修改/删除用户原文。
* 不审核已分离存档的联系方式本身，不把聊天正文或联系方式交换内容发送到模型。
* 不在本稿决定老师资质、实名认证、人工撮合、支付、评价、排课或未确认的交易责任。
* 不把 OCR 纳入首期默认范围；是否审核老师证明图片必须另行业务确认。
* 不把 ISSUE-0036 编为后 0033 草案的 S4，不阻塞 ISSUE-0031、0032、0034 的顺序

## 4. 审核对象、输入边界与标准化

### 4.1 首期字段

首期候选为需求方 childIntro 和老师 abilityDescription，以及经业务方确认的
其他会公开展示的用户可控文本。标题、科目、时间、地址等结构化字段先做字段盘点；
只有被列入公开文本清单才进入审核。

存档联系方式、登录标识、站内聊天、交换联系方式、审计正文和未公开证明图片默认
不进入本流程。图片 OCR 为独立决策门，未确认前禁止采集、上传或调用 OCR。

### 4.2 标准化流水线

对审核副本做双视图、不可变标准化，不覆盖用户原文：

1. 记录内容版本、字段名、长度和 contentHash；拒绝超出产品长度上限的输入。
2. **先对未经 NFKC 的原始 Unicode 文本扫描混淆**：识别零宽字符、控制字符、同形
   字符、全角字符、连字、分隔符、插入空格/点号/括号/破折号、换行、emoji、反向书写
   和谐音变体，并保留原文索引与脱敏偏移证据。
3. 再执行 Unicode NFKC、全角/半角统一、大小写折叠和数字脚本归一，生成检测视图，
   同时建立从归一视图到原文的 offset map；原文视图和归一视图都不得被覆盖。
4. 对原始视图和归一视图分别运行规则；两者结果不一致、偏移无法映射、映射越界或
   归一产生信息损失时，进入 needs_manual_review，不能直接 allow。
5. 将常见中文数字、阿拉伯数字和可安全解释的分隔符生成检测视图，识别 URL/社交 ID
   但不执行或抓取 URL；标准化规则版本和偏移 hash 写入审计，不写完整命中片段。

任何标准化失败、映射不确定、原文混淆检测失败或输入疑似提示注入时，进入
needs_manual_review，不直接 allow。原文仍由原业务数据权限保护。

## 5. 检测架构

### 5.1 确定性检测层

检测器按版本管理、可离线运行、输出类别和置信等级而非完整敏感内容：

* 邮箱：本地部件、@、域名和常见拆分/混淆；不因普通 @ 语义直接自动拒绝。
* 手机/座机：国家/地区前缀、连续数字、常见分组、区号/分机；需排除日期、价格、
  门牌、成绩和订单号等合法长数字。
* 微信/QQ：关键词、账号长度/字符集、分隔/谐音/Unicode 变体；关键词单独出现
  只进入低置信或 AI/人工判断。
* URL/社交 ID：协议、域名、短链、点号/斜杠变体；不发起网络请求。
* 长数字：连续、分隔、中文数字、混合脚本和语义邻近特征；高召回后必须做上下文
  反误杀。
* Unicode/分隔混淆：同形字符、零宽、标点插入、换行、反向顺序；不把混淆检测
  直接等同于联系人，交由 AI/人工确认。

#### 5.1.1 高置信确定性与合法数字上下文

高置信确定性命中必须同时满足：规则版本固定、命中完整模式、上下文通过、合法数字
排除未命中、原文偏移可映射且不是仅由 AI 单独判断。以下是可测试的最小框架，均为
建议默认，业务方只能收紧：

* 邮箱：完整 `local@domain`，local 非空、domain 有合法标签和后缀，未被空格/标点
  拆断；只有 `@` 或不完整结构进入人工。
* 手机：连续或可还原为 11 位、第一位为 1 且第二位为 3–9，允许已批准的 `+86/0086`
  和分隔变体；同时不满足合法日期、价格、地址、成绩上下文。
* 座机：可识别区号加本地号码，或明确电话/座机/分机标签的组合；无地区/上下文的
  长数字不自动拒绝。
* QQ：5–12 位数字与 QQ/扣扣/联系等标签或明确账号语义邻近；纯 5–12 位数字只进
  人工，不自动 reject。
* 微信：微信、V信、vx、wechat 等标签与账号字符邻近；单独关键词不自动拒绝。
* URL/社交 ID：完整协议 URL、`www` 或可识别域名结构；教育资料链接若无联系方式
  语义进入人工或 `allow_candidate`，不能仅因 URL 自动拒绝。
* 长数字、中文数字或混淆本身不构成高置信，必须叠加联系方式上下文或第二独立信号；
  纯长数字、中文数字、单独关键词不得自动拒绝。

合法数字上下文按版本化规则先排除再决定：

* 年份：1900–2099 等四位数字邻近“年/年度/学年”；日期/时间：YYYY-MM-DD、MM/DD、
  周/月/日、时/分等完整表达。
* 价格：数字邻近“元/块/¥/人民币/课时费/每小时/预算”；若后续同时出现电话/微信
  标签，联系方式信号优先。
* 成绩/等级：数字邻近“分/分数/等级/排名/名次/绩点”；范围由黄金集确认，不硬编码
  为业务事实。
* 地址/房间：数字邻近“号/栋/单元/室/楼/路/街/区/县/校区/门牌”；数量/时长：数字
  邻近“人/名/次/小时/分钟/课时/年级/版本/订单”等正常量词。
* 纯长数字没有合法上下文也没有联系方式标签时，只进入 ambiguous/manual，不自动
  allow 或 reject。

规则顺序为先识别明确联系方式上下文，再应用合法上下文排除；同一跨度同时命中联系
方式与价格/地址时升级人工。建议的自动拒绝只适用于上述高置信确定性命中，并返回
修改提示；低置信、检测器冲突、跨语言不确定项一律人工。高置信命中不得进入
published；无效、过期、冲突或未知服务结果不得公开；规则版本、命中类别、偏移和
黄金集中的误杀/漏放必须可追溯。

### 5.2 AI 语义分类层

AI 仅接收经业务/隐私批准的最小审核副本和字段上下文，不接收存档联系方式、聊天
记录或无关身份数据。采用供应商中立适配器，固定版本、模型、区域和策略标识，模型
输出严格结构化：

* allow_candidate：未发现联系方式语义，但不能覆盖确定性高置信命中；
* contact_likely：疑似在引导公开联系方式；
* ambiguous：可能是正常数字/地址/经验描述或隐晦联系方式；
* policy_or_input_error：输入不可信、提示注入、越权指令、输出格式错误或模型异常。

AI 不执行用户文本中的命令、不访问工具/URL、不改变审核规则、不生成可直接发布的
替代文案。系统提示与用户文本分隔，用户文本视为不可信数据；输出用 schema 校验，
解析失败重试一次，仍失败进入人工。AI 的评分只作路由/排序证据，不能单独作为
自动拒绝或自动公开依据。

### 5.3 人工兜底

人工队列至少包含：detector conflict、ambiguous、Unicode/长数字变体、AI 超时/
不可用、输入疑似提示注入、申诉和高风险用户/未成年人数据。审核员最小权限访问
原文，决定 allow、reject 或 needs_manual_review/补充信息；决定必须有 reasonCode、
reviewerId、policyVersion 和时间，不把敏感原文写进普通日志。

高风险自动拒绝可由业务方批准的规则触发；AI 单独命中、模型分数边界、人工覆盖
规则或供应商错误不能自动公开。人工决定覆盖必须可审计，必要时要求二审。

## 6. 状态机与用户可见行为

### 6.1 状态

核心审核状态为：

draft → pending_review → published

pending_review → rejected  
pending_review → needs_manual_review → published 或 rejected  
needs_manual_review → needs_manual_review（等待/重试）或 published/rejected  
rejected → appeal_pending → needs_manual_review → published 或 rejected（不改内容的申诉）  
rejected → draft → pending_review（用户修改内容后重新提交）

申诉不改内容时只能走 `rejected → appeal_pending → needs_manual_review`；
`appeal_pending` 是独立中间状态，不能直达 published。申诉原因码必填；补充说明一旦
提供，必须与其他用户文本走同一联系方式审核和 fail-closed 规则。`appeal_pending` 与
`needs_manual_review` 均不公开、不恢复聊天或联系方式能力。修改内容的请求必须走
`rejected → draft → pending_review`，不得复用旧审核结果或旧 contentHash。

published 的编辑创建新 contentVersion，候选版本重新进入 pending_review；旧的最后
一个已发布快照继续作为公开版本，直到新版本通过。新建记录在审核通过前没有公开
快照。拒绝的候选内容不公开，原发布版本不因单次编辑自动消失，除非用户执行已有
删除流程或业务方确认重大安全事件处理。

删除不是新的审核状态，而是 ISSUE-0033 的生命周期覆盖：已发布记录软删除后 48
小时内可恢复。删除期间不公开；历史消息仅可读，会话只读，禁止新消息、创建/确认/
继续联系方式交换及查看联系方式。恢复必须重新校验 owner、参与者、记录状态、
contentVersion、contentHash、policyVersion 和并发版本。恢复只允许进入
`deleted → pending_review`，不得直接进入 published；在人工/规则复核完成前保持
pending_review，不公开内容、聊天或联系方式。若任一版本或关系不能证明仍合规，先保持
`pending_review`，再按 `pending_review → needs_manual_review` 处理；业务方不响应不能
选择绕过复核的快捷路径。

### 6.2 状态不变量

* 只有服务端在检查当前 owner、contentVersion、policyVersion、审核状态和幂等键后
  才能把候选置为 published。
* pending_review、rejected、needs_manual_review 不得出现在公开列表/详情，不得
  新建或继续联系方式交换。
* 任何旧的迟到 AI/人工结果如果 contentVersion 或 contentHash 不一致，必须丢弃为
  stale result，不得发布。
* deletedAt + 48h 和 0033 的恢复/审计规则优先；本 Spec 不能绕过并发控制。

### 6.2.1 允许与禁止转换

允许的最小转换为：`draft → pending_review`；`pending_review → published`（仅服务端
当前版本检查与审核通过）或 `rejected`/`needs_manual_review`；
`needs_manual_review → published`/`rejected`（仅人工在当前版本作出可追溯决定）或
继续 `needs_manual_review`；不改内容的申诉允许 `rejected → appeal_pending →
needs_manual_review → published/rejected`，修改内容只允许 `rejected → draft →
pending_review`；已发布编辑生成新版本并进入 `pending_review`，旧 published 快照保持
隔离；`published → deleted`；`deleted → pending_review`。申诉最终发布前，服务端必须
再次核对当前 `policyVersion`、`contentVersion`、owner、contentHash 和审计写入成功；
恢复不得跳过复核。

禁止的转换包括：`draft → published`、`rejected → published`、
`deleted → published`、`deleted → chat/contact`、未有当前版本人工决定的
`needs_manual_review → published`，以及任何因供应商允许、AI 单独允许、前端标志、
超时、预算熔断、队列/审计失败而进入 published。旧的 contentVersion、contentHash、
owner、权限或 policyVersion 不匹配，或幂等/审计写入绕过时，必须拒绝发布并标为
stale/manual；不得以重试或旁路恢复发布。

### 6.3 用户可见文案

* 提交后：正在快速审核，审核通过后公开显示；审核期间其他人不可见。
* 人工复核：需要进一步人工复核，复核完成前不会公开；不要在文案中暴露完整命中
  模式，避免指导规避。
* 拒绝：内容可能包含公开联系方式，请修改后重新提交；只显示必要的字段级提示，
  不展示敏感命中值。
* 通过：审核通过，内容已公开。
* 服务异常/超时：审核服务暂不可用，内容暂未公开，请稍后查看；不暗示已通过。
* 申诉待处理：申诉已提交，人工复核完成前不会公开，也不会恢复聊天或联系方式；原因码
  必填，补充说明按同一审核规则处理。

文案需支持键盘、屏幕阅读器、错误关联、焦点管理和移动端换行；不得把审计 reasonCode
或模型提示原文直接展示给用户。

## 7. 编辑、重复、并发和幂等

* 每次创建/编辑携带 idempotencyKey、entityId、ownerId、contentVersion 和 contentHash。
  同一键/同一内容版本重试不得生成重复记录、重复队列或重复通知。
* 并发编辑使用版本条件写入；旧版本提交返回统一冲突，不覆盖新内容、不复用旧审核。
* 人工决定先检查当前版本、删除状态和 owner；不匹配则标记 stale，重新排队。
* 用户连续提交相同内容可合并审核，但每次公开变更仍有可追溯版本；不同内容版本
  不得错误共用通过结果。
* 队列重试采用有限次数和退避；超限转人工，不循环生成新审核任务。
* 模型、规则或 policyVersion 升级可触发重新审核，但不能静默把既有 published 快照
  改成 rejected；先生成候选/人工任务，重大风险按业务确认处置。

### 7.1 申诉滥用、重复和锁定

同一 `owner + entityId + contentVersion` 在 24 小时内最多发起 1 次申诉；计数由服务端
维护，不因刷新、换页面或重试清零。重复 `idempotencyKey` 必须幂等返回既有结果且不
新建队列；同一 key 携带不一致的 owner/entity/version/hash 视为冲突，拒绝且不入队，
保留审计。

同一 `contentHash` 连续维持原判累计达到第 3 次后锁定 7 天；锁定期间请求拒绝或幂等，
仅追加最小审计，不再进入人工队列。锁定由服务端强制，业务、管理员和前后端均不得
绕过；锁定解除也不能跳过当前版本、owner、policyVersion 和审计校验。

删除状态、过期版本、非 owner、失配版本、重复或冲突 key、锁定期请求均 fail-closed：
不公开、不恢复聊天或联系方式、不产生新的审核任务。只有满足所有权、当前版本、未
锁定和幂等条件的请求才可进入 `appeal_pending`。

## 8. 失败、降级、成本和安全边界

### 8.1 Fail-safe / fail-closed

以下任一情况不得公开新候选：确定性检测器失败、标准化失败、AI 超时/不可达/费用
熔断、输出格式错误、人工队列不可用、contentVersion 或 contentHash 不一致、无法确认
owner/权限、提示注入或审计写入失败。结果为 pending_review 或 needs_manual_review，
并告警。

已发布旧快照在新候选审核失败时继续维持原状态，除非已有规则/安全事件要求其进入
0033 删除或人工处置；不能因新服务故障自动公开新内容，也不能自动物理删除原文。

### 8.2 成本与供应商

推荐配置项只列变量名，不写真实值：REVIEW_PROVIDER_REF、REVIEW_MODEL_REF、
REVIEW_REGION_REF、REVIEW_API_KEY_REF、REVIEW_MONTHLY_BUDGET_CAP、
REVIEW_REQUEST_RATE_LIMIT、REVIEW_TIMEOUT_MS、REVIEW_RAW_RETENTION_HOURS、
REVIEW_AUDIT_RETENTION_DAYS、REVIEW_QUEUE_SLA_MINUTES。

最终 provider/model/region/budget/secret owner/数据处理协议必须业务方确认。预算
达到上限或供应商不可用时停止外部调用、保留候选在人工/待处理状态，不切换到未审查
供应商，不删除审计。密钥只使用环境 secret 引用，开发/测试/预生产/生产隔离。
预算熔断是服务端门：熔断后新的外部请求不得发出，已有结果也不能绕过状态机；恢复
必须有审计事件、告警解除条件和幂等重试，不得由前端或降级供应商自行放行。

### 8.3 隐私、未成年人和审计

* 先本地确定性检测；未经业务、隐私和供应商协议确认，不把含孩子简介的原文发送
  外部模型。无法安全脱敏且必须判断时进入内部人工队列。
* 供应商请求/响应的原始日志默认不留存（`REVIEW_RAW_RETENTION_HOURS=0`），不得用于
  训练、广告、画像或其他二次用途，也不得未经批准由供应商人员查看。供应商接入前
  必须提供并由业务/隐私 owner 确认 DPA、处理地域与跨境路径、子处理者名单、删除/保留
  门、访问与密钥控制，以及请求/响应/滥用日志的字段、目的、留存和删除规则；未知或
  无法证明的策略一律 fail-closed，不发送原文。若供应商强制原始留存，只能在明确的
  业务/隐私批准下，且最长 24 小时并有删除凭证；否则该供应商不可用。
* 默认不允许供应商训练/二次使用；地域、跨境、DPA/合规和数据主体请求必须在门禁
  中确认，不从“AI 倾向”推断合法性。
* 普通日志只记 entityId 的受限映射、contentHash、类别、版本、耗时、结果和错误；
  不记邮箱、电话、微信、QQ、完整 token、完整 prompt/response 或儿童敏感正文。
  平台可记录供应商/模型标识、请求 hash、policyVersion、调用耗时、错误类别和结构化
  结果；不得复制供应商原始请求/响应或完整命中片段。
* 建议原文审核副本仅在队列生命周期内保留，默认不超过 24 小时；审核元数据/审计
  建议 180 天，均为保守建议值域而非法律决定，最终取业务/合规批准的最短必要期。
* 访问采用字段级、最小权限、审计和定期复核；申诉所需证据按 reasonCode 和 hash
  保存，不复制敏感正文。

## 9. 快速审核 SLO 和产品成功标准

以下为建议最小骨架，必须由业务方确认或收紧：

| 指标 | 建议骨架 | 失败处理 |
| --- | --- | --- |
| 提交响应 | 接收确认 p95 ≤1 秒；返回 pending_review 不等待长模型调用 | 超时仍返回安全 pending，不重复创建 |
| 确定性层 | p95 ≤200 毫秒；规则版本可追溯 | 失败进入人工/待处理，不公开 |
| 自动审核路径 | 端到端 p95 ≤10 秒；硬超时 15 秒；提交接口仍 p95 ≤1 秒返回安全 pending | 达到硬超时进入 pending_review/needs_manual_review，不公开、不由前端绕过 |
| 人工队列 | 入队 p95 ≤5 分钟；决定 p95 ≤30 分钟；99% ≤2 小时（工作时间定义待确认） | 超时通知 owner，保持不公开 |
| 申诉队列 | 入队 p95 ≤30 分钟；人工裁决 p95 ≤4 小时；99% ≤1 个工作日 | 超时保持 pending/manual、不公开并告警，不自动通过或转普通编辑 |
| 高置信确定性命中 | 公开漏放 0；用户得到修改提示 | 自动 reject 或业务批准的人工复核 |
| 清洁样本误杀 | 合成/业务批准黄金集建议 ≤2% | 进入误判分析和规则回滚，不直接放宽 |
| 审计/幂等 | 100% 有版本、策略、决定、时间、actor；重复提交不重复发布 | TECH_REWORK_REQUIRED |

提交响应、确定性规则、AI 调用、队列等待和端到端自动路径必须分别埋点，至少记录
p50/p95/p99、硬超时次数、pending/manual 数量和任何公开结果；不能用提交接口的快速
返回冒充审核完成。15 秒是自动审核硬超时，业务方只能收紧 p95 或缩短超时，不能放宽
fail-closed 或以超时结果公开。

准确率只在脱敏/合成、业务批准的黄金集上测量；真实用户文本不得作为未授权训练
数据。建议黄金集覆盖中文、英文、数字、正常地址/价格/年份/成绩、所有联系方式
变体和提示注入样本，并按需求方/老师字段分桶。

## 10. 验收矩阵

### 10.1 单元验收

责任：规则/服务端负责人；证据：测试报告、固定 golden corpus、规则/模型版本。

* 标准化覆盖全角、零宽、控制字符、Unicode 同形、连字、分隔、中文数字、长数字和
  正常合法数字；测试同时断言原文视图、归一视图、原文偏移与 offset map 不越界，
  NFKC/去混淆造成信息损失或双视图不一致时只能进入人工，不能直接 allow。
* 邮箱、手机、座机、微信、QQ 的完整高置信模式和 URL/社交 ID（协议、www、域名、
  短链、常见平台变体）均有 golden cases；URL 只解析不发起网络请求。纯长数字、
  中文数字、单关键词不自动拒绝；年份/日期时间、价格、成绩、地址/房间、数量/时长
  等合法数字上下文和冲突样本均验证为排除或人工。
* 高置信规则使用固定 `policyVersion`，完整匹配、上下文与合法数字排除均通过，且
  原文偏移可追溯；AI 单独高分不能构成自动公开或自动拒绝。
* AI schema、置信分段、一次重试、错误输出、超时和提示注入可复现；“忽略规则/直接
  发布/调用 URL/泄露系统提示”等不受信指令不得触发工具或公开，改为人工/待审。
* 以下 12 项均以故障注入验证 fail-closed：
  1) 确定性检测器失败；2) 标准化或 offset map 失败；3) AI 超时；4) AI 不可达；
  5) 预算熔断；6) AI schema/输出解析错误；7) 人工队列不可用；8) contentVersion
  不一致；9) contentHash 不一致；10) owner/权限不能确认；11) 提示注入或不受信指令；
  12) 审计写入失败。每项结果只能为 pending_review/needs_manual_review，禁止公开，
  有告警和可重试/人工接管证据。
* 预算熔断测试使用 provider stub/隔离测试 key，断言熔断后不再发出外部请求、候选保持
  待审、告警/恢复/幂等重试可追踪，且前端、重试或降级供应商不能绕过。
* 状态机所有允许/禁止转换、版本冲突、stale result、删除/恢复和 idempotencyKey
  有覆盖：恢复只能 `deleted → pending_review`，不得 `deleted → published`；删除期间
  聊天只读且无联系方式；零容忍项为越权公开、重复发布、无审核公开和联系方式明文日志。
* 申诉 golden path 有覆盖：不改内容的 `rejected → appeal_pending → needs_manual_review
  → published/rejected`，以及修改内容的 `rejected → draft → pending_review`；断言
  reasonCode 必填、补充说明走同一审核，申诉状态/列表/详情/聊天/联系方式门控，以及
  发布前当前 `policyVersion`、`contentVersion`、owner、contentHash 和审计成功检查。
* 使用 390px 移动端真实页面/DOM 或等价操作记录验收 pending、人工、拒绝、申诉和长
  文案：内容可换行无裁切/横向溢出，焦点顺序与错误关联正确，屏幕阅读器能读出状态，
  触控目标可操作且没有把 reasonCode、命中正文或服务提示注入原文暴露给用户。

### 10.2 集成验收

责任：技术负责人 + 独立安全复核；证据：API/队列/数据库/模型 stub、审计。

* 创建/编辑仅生成 pending_review；通过后才公开；拒绝/人工期间公开 API 不返回。
* 规则、AI、人工服务的超时/不可达/费用熔断均保持 fail-closed；队列重试幂等。
* 不同用户、entity、版本无法读取或发布他人候选；旧 published 快照和新 pending
  版本隔离。
* 服务端负测覆盖伪造 published/allow 标志、旧 contentVersion/contentHash、错误
  owner/权限、重复幂等键、删除态发布、超时/费用熔断旁路和前端直接调用发布接口；
  每个负测均被拒绝、留有审计并保持 pending/manual。
* 申诉负测覆盖 24 小时内同 owner/entity/version 第二次请求、重复 idempotencyKey、同
  key 不同 payload、跨账号/非 owner、过期 contentVersion 或 policyVersion/contentHash、
  删除态、7 天锁定及申诉/审计写入失败；均应拒绝或幂等、不重复入队/发布/恢复聊天或
  联系方式，锁定请求仅追加最小审计且前后端/业务/管理员路径不能绕过。
* 0033 软删除 48h、聊天只读、联系方式禁用；恢复只能走 `deleted → pending_review`
  并重校验 owner/参与者/版本/策略，复核前不得公开、发消息、创建/确认/继续交换或
  查看联系方式；明确验证不存在 `deleted → published` 或删除期间新公开关系。
* 审计脱敏、密钥引用、供应商禁止训练/广告/画像/二次使用、DPA、处理地域/跨境、
  子处理者、删除/保留门、原始请求响应默认零留存与 prompt injection 防护均通过；
  未知供应商日志政策或协议时验证不发送原文并保持 pending/manual。

### 10.3 预生产验收

责任：运维/平台、独立技术/安全、产品；证据：合成数据、隔离 key、SLO dashboard、
故障注入、成本和回滚 receipt。

* 需求方/老师样本、正常长数字、联系方式变体、人工和申诉流程可重放。
* 自动路径、队列积压、供应商超时、模型错误、成本上限和密钥轮换的停止/回滚有效。
* provider stub 故障注入验证 15 秒硬超时、预算熔断、停止外部调用、告警、恢复和幂等；
  单独展示提交、规则、AI、队列和端到端 p95，不以提交响应冒充审核完成。
* 申诉 SLO 分别测量入队 p95 ≤30 分钟、人工裁决 p95 ≤4 小时和 99% ≤1 个工作日；
  任一超时均保持 pending/manual、不公开并告警，不自动通过或转普通编辑。
* 72 小时等价观察或业务确认的更严格窗口内，零容忍项为零；SLO 和误杀目标满足。
* 无生产正文、真实联系方式或未成年人敏感数据流入测试供应商；清理 targets/audit
  receipt 可核对。

### 10.4 生产验收

责任：平台/运维、独立技术/安全、产品；证据：部署 provenance、生产配置引用、合成
或最小授权样本、监控、告警、回滚、清理和观察报告。生产数据写入需另行书面授权，
不得以本稿授权。

* 先以合成/专用资料做小流量或只读路径验证；未取得业务方批准不发送真实正文到外部
  模型，不做大流量自动拦截。
* 观察窗口至少 72 小时或业务方确认的更严格值；零绕过、零联系方式公开、零未授权
  写入、零重复发布；SLO、队列、错误率和成本均在门限内。
* 供应商/模型/规则版本、地区、密钥、审计脱敏和回滚入口可追溯；故障时维持旧公开
  快照和新候选不公开。
* 供应商协议/日志策略/地域/子处理者/删除与保留证据、无训练/广告/画像声明和 raw
  retention=0（或经批准 ≤24h）均可回读；任何缺失项阻止真实正文出域。

### 10.5 业务方验收

责任：业务方 + 产品经理；证据：带日期确认、四类用户操作记录和文案/可访问性检查。

业务方必须实际确认：清洁内容、明确联系方式、长数字正常场景、模糊场景、拒绝修改、
人工等待、申诉、编辑重审、删除/恢复、聊天/联系方式门控、移动端可见文案和服务
异常行为。技术通过不自动产生 BUSINESS_ACCEPTED；业务方不响应保持
ACCEPTANCE_PENDING。

## 11. 回滚、观察与关闭门禁

### 11.1 回滚

规则/模型版本可回到上一已验证版本；AI 适配器或供应商关闭后，所有新候选保持
pending/manual，不允许绕过；已发布旧快照按 0033 规则维持或由授权安全处置。队列
和审核记录 append-only 保留，回滚不物理删除证据。若发现已公开联系方式或越权，
立即停止发布、冻结受影响版本、按安全/隐私响应流程处置并重新产品验收。

### 11.2 观察与失败传播

生产观察至少覆盖建议 72 小时，具体值由业务方确认且只能收紧。若规则/AI 服务失败，
0036 不影响 0031→0034→0032 主序列的既有门禁，但本 Issue 保持 TECH_REWORK_REQUIRED
或 ACCEPTANCE_PENDING；不能把服务异常扩散为允许公开。若 0033 删除/恢复或版本
控制失败，0036 发布和审核结果冻结，直到 0033 owner/技术复核恢复。

### 11.3 关闭条件

必须同时具备：业务确认范围/阈值/供应商/预算/隐私；Spec Hermes/Document QA 通过；
代码/测试/独立技术安全产品复核通过；预生产和生产证据完整；观察期通过；业务方
明确接受；Issue 管理员更新并关闭。任何一项缺失，保持 open / USER_CONFIRMATION_PENDING
或相应阻塞状态。
