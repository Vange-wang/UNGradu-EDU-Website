## 4. 阻塞问题

### P0：授权前会话接口返回双方手机号，实际绕过联系方式保护

位置：

- `Code文档/features/chat/chat-storage.ts:7-13`
- `Code文档/features/chat/chat-storage.ts:30-39`
- `Code文档/features/chat/chat-storage.ts:209-212`
- `Code文档/features/chat/chat-storage.ts:226-240`
- `Code文档/features/chat/chat-storage.ts:526-531`

问题说明：

当前 `SavedConversation` 直接保存并返回：

```ts
participantPhones: [string, string]
```

当前 `SavedContactExchangeRequest` 直接保存并返回：

```ts
requesterPhone: string;
receiverPhone: string;
```

`readConversationForUser` 在确认当前用户是参与者后，直接返回完整 `conversation` 对象；`listContactExchangeRequestsForConversation` 也会把该会话内完整交换请求对象返回给参与者。也就是说，只要进入聊天会话，用户在联系方式交换被同意前，就已经可以从会话数据或交换请求数据中拿到对方手机号。

这与 Spec 中以下要求冲突：

- “未同意交换联系方式前，聊天界面不展示联系方式。”
- “未同意交换联系方式前，接口不返回对方联系方式。”
- “存档联系方式默认不公开。”
- “用户不能通过修改 ID 查看他人未授权联系方式。”

当前 UI 没有把手机号渲染到页面上，但数据层已经返回了手机号。根据项目安全主线，“前端隐藏不等于权限控制”，因此该问题按 M4 验收阻塞处理。

建议修复：

1. 会话与交换请求对页面返回时，不应包含对方手机号字段。
2. 参与者识别应改用不透明用户 ID 或只在内部存储层使用手机号，并提供脱敏 View Model 给页面。
3. 联系方式授权前，聊天页只能拿到“对方基础展示信息”或“对方角色/来源对象摘要”，不能拿到手机号、微信号或可识别联系方式。
4. 补充测试：创建会话、列出会话、列出交换请求时，未授权返回对象中不得包含对方手机号；授权后二次确认通过后，才允许 `readAuthorizedContactProfiles` 返回双方存档联系方式。

### P1：聊天页没有准实时刷新，无法满足 5 秒内看到新消息

位置：

- `Code文档/app/chats/[id]/page.tsx:50-101`
- `Code文档/app/chats/[id]/page.tsx:103-127`

问题说明：

聊天页 `refresh()` 只在两个场景触发：

1. 页面加载时 `useEffect(() => { refresh(); }, [refresh])`。
2. 当前用户发送消息、发起/处理联系方式交换请求后手动调用 `refresh()`。

代码中没有 `setInterval`、轮询、焦点恢复刷新、storage event 监听或其他准实时机制。因此当 A 用户已经停留在聊天页，B 用户在另一个浏览器或标签页发送新消息后，A 的页面不会在 5 秒内自动看到新消息，除非 A 重新加载页面或进行一次本地操作。

这与 Spec 9.3 中“双方可以实时或准实时发送文字消息，新消息发送后应在 5 秒内被对方看到”冲突。

建议修复：

1. 在当前本地测试阶段，聊天页至少增加 3-5 秒轮询 `refresh()`，并在组件卸载时清理定时器。
2. 如仍采用本地存储测试方案，可补充 `storage` 事件监听来覆盖同浏览器多标签页场景。
3. 补充测试或轻量组件验证：对方写入新消息后，聊天页无需手动刷新即可在 5 秒内重新读取并展示。
4. 后续接入 CloudBase 时，将该本地轮询替换为后端 API 轮询或经安全规则验证的准实时能力。

## 5. 非阻塞观察

### 5.1 当前仍是本地测试存储，不代表生产权限模型通过

M4 当前实现继续使用浏览器本地存储和测试登录态。它可以用于本地验证功能闭环，但不能证明生产环境下的后端权限、安全规则和接口过滤满足要求。

这不单独阻塞 M4，因为当前阶段仍处于前端本地 MVP 验证；但 M5 必须完成后端可信登录态、会话参与者权限、消息读取权限、联系方式读取权限和交换请求处理权限验证。

### 5.2 对方账号不可用、来源对象删除后的异常流程尚未形成可测闭环

Spec 6.1.1 和 9.3.1 要求账号不可用后禁止继续发送消息、待处理交换请求自动失效；来源需求或家教信息删除后，不能再从被删除内容发起新聊天或交换请求。

当前代码尚未引入账号不可用、发布内容删除等状态能力，因此本轮无法完整验证这些异常流程。考虑到前序里程碑也尚未实现删除和账号注销，该项暂不作为本轮 P0/P1 阻塞，但应进入 M5 安全和异常流程验证清单。
