## 3. 主要问题

### P1-1：孩子简介为空时仍可发布

涉及文件：

- `Code文档/features/parent-needs/parent-need.ts`
- `Code文档/app/parent-needs/new/page.tsx`

Spec 依据：

- Spec 5.5 将 `孩子简介` 列为家长发布需求字段。
- Spec 7.5：`必填字段不能为空。`
- Spec 9.1：`发布时必填字段校验正常。`

代码现状：

```ts
if (childIntro.length > 100) {
  errors.childIntro = "孩子简介最多 100 字";
} else if (
  MAINLAND_PHONE_PATTERN.test(childIntro) ||
  WECHAT_HINT_PATTERN.test(childIntro)
) {
  errors.childIntro = "孩子简介不得包含手机号或微信号";
}
```

确认结果：

- 当 `childIntro` 为空字符串时，`length > 100` 为假，手机号和微信号正则也不会匹配，因此不会进入任何错误分支。
- `validateParentNeedInput` 会把空孩子简介判定为合法输入，`saveParentNeed` 也会继续保存。
- `/parent-needs/new` 页面 textarea 没有 `required`，提交逻辑完全依赖同一个校验函数。
- `Code文档/tests/parent-need.test.ts` 中没有空 `childIntro` 断言。

横向对比：

- 同一文件中 `teacherGenderPreference`、`subjects`、`grade`、`community` 等字段均有空值校验。
- `Code文档/features/tutor-profiles/tutor-profile.ts` 对结构对应的 `abilityDescription` 有 `if (!abilityDescription)` 校验。
- 因此这是明确遗漏，不是尚未进入 M2 的能力缺口。

影响：

- 家长可发布缺少孩子简介的需求，破坏 M2 结构化需求完整性。
- 后续 M3 需求广场需要展示孩子简介摘要，空简介会影响列表可用性。

建议：

- 在 `validateParentNeedInput` 中补充 `if (!childIntro)` 空值校验。
- 增加“孩子简介为空时拒绝”的单元测试。
- 页面可同步增加 `required`，但最终仍应以后续后端校验为准。

### P1-2：孩子简介未拦截详细门牌地址

涉及文件：

- `Code文档/features/parent-needs/parent-need.ts`

Spec 依据：

- Spec 5.5：`孩子简介不得填写手机号、微信号或详细门牌地址。`
- Spec 7.5：`地址不得填写详细门牌号。`

代码现状：

```ts
const DOOR_NUMBER_PATTERN = /(\d+\s*(栋|幢|座|单元|楼|层|室|房|号))|门牌/;
...
if (!community) {
  errors.community = "请填写小区或村";
} else if (DOOR_NUMBER_PATTERN.test(community)) {
  errors.community = "具体位置最多填写到小区或村，不填写门牌号";
}
```

确认结果：

- `DOOR_NUMBER_PATTERN` 仅用于 `community` 字段。
- `childIntro` 只检测字数上限、手机号和微信号关键词，没有检测详细门牌地址。
- 用户可以在孩子简介中填写类似 `3 栋 1201 室` 的详细地址并通过发布。
- `Code文档/tests/parent-need.test.ts` 中只测试了 `community` 字段门牌号，没有测试 `childIntro` 门牌号。

影响：

- 绕过“具体位置最多到小区或村”的隐私保护要求。
- 涉及未成年人和家庭住址信息，属于 MVP 需要谨慎处理的隐私风险。

建议：

- 将 `DOOR_NUMBER_PATTERN` 检测同步应用到 `childIntro` 字段。
- 增加“孩子简介包含门牌号时拒绝”的单元测试。

### P2：发布记录列表页对空孩子简介做条件渲染，掩盖 P1-1 影响面

涉及文件：

- `Code文档/app/profile/parent-needs/page.tsx`

代码现状：

```tsx
{need.childIntro ? <p>孩子简介：{need.childIntro}</p> : null}
```

问题说明：

- 该列表页在渲染孩子简介时做了“空值则不渲染”的判断。
- 防御性渲染本身可以保留，但它客观上说明数据层可能产生空 `childIntro`，而源头校验没有拦截。
- 如果不修复 P1-1，未来 M3 需求广场的孩子简介摘要也可能用类似方式掩盖问题，导致部分卡片缺少摘要但无错误提示。

严重程度：

- 定为 P2。它不是独立根因，而是 P1-1 的连带表现。

建议：

- 优先修复 P1-1，从源头杜绝空 `childIntro` 进入存储。
- P1-1 修复后，列表页条件渲染可保留为防御性写法，但不应作为唯一防线。
