## 1. 大白话结论

现在正式环境已经部署，但登录页还是 M1 阶段的“手机号 + 测试验证码”过渡页面。生产环境正确关闭了测试登录，所以真实用户目前不能注册，也不能登录。

本阶段要解决的不是“解释为什么登不了”，而是把登录系统真正落地：

- 新用户能用手机号完成注册 / 登录。
- 老用户能用手机号再次登录。
- 登录后能继续使用家长 / 老师身份入口。
- 刷新页面后登录状态还在。
- 退出登录后不能再看个人数据。
- 生产环境继续禁用测试登录。

## 2. 本阶段目标

本阶段目标：**真实用户可以注册、登录、退出，不再依赖测试登录。**

完成后应达到：

- 正式环境登录页不再提示 M1 测试登录。
- 用户输入手机号后可以获取验证码或进入受控试运行登录流程。
- 新手机号首次验证通过后自动创建账号，至少形成可识别的用户记录。
- 老手机号再次验证通过后直接登录原账号。
- 登录态由服务端可信 Cookie 或等价安全机制维护。
- 已登录用户能进入家长 / 老师身份入口和个人页。
- 未登录用户访问个人数据或私有发布接口时被拒绝或引导登录。
- 退出登录后服务端会话失效。
- 生产环境 `/api/auth/test-login`、`000000` 测试验证码、`x-ungradu-test-user-phone` 继续不可用。

## 3. 推荐登录方案

### 3.1 首选方案：手机号短信验证码登录

推荐采用正式手机号短信验证码登录。

用户流程：

1. 用户打开登录页。
2. 输入 11 位手机号。
3. 点击“获取验证码”。
4. 系统通过正式短信服务发送一次性验证码。
5. 用户输入验证码。
6. 验证通过后：
   - 如果手机号从未登录过，自动创建账号。
   - 如果手机号已存在，直接登录原账号。
7. 系统写入服务端签名登录态。
8. 用户进入原目标页、首页或身份入口。

短信验证码基本规则：

- 验证码只能使用一次。
- 验证码必须有有效期，建议 5 分钟。
- 同一手机号不能无限发送，建议至少限制 60 秒内不能重复发送。
- 同一手机号、同一 IP 或同一设备应有基础频控。
- 验证码不得写入前端、日志、报告或错误信息。
- 验证码存储必须避免明文长期保存，建议只保存哈希、过期时间和尝试次数。

### 3.2 短信服务暂未就绪时的受控临时方案

如果短信服务账号、短信签名或模板暂时没审批下来，不能直接公开上线。只能做“小范围受控试运行登录”。

可接受的临时方案：

- 只允许项目总控制人确认的白名单手机号登录。
- 登录验证码或一次性登录码由运营人工发放，或由后台受控生成。
- 一次性登录码必须有有效期和使用次数限制。
- 白名单、登录码生成、发放和使用记录必须可追溯。
- 临时方案必须有明确有效期，建议不超过 7 天或仅用于本轮内部试运行。
- 临时方案不得开放给未受邀公网用户。
- 临时方案不得复用 M1 的 `000000` 测试验证码。
- 临时方案不得打开 `/api/auth/test-login`。
- 临时方案不得接受 `x-ungradu-test-user-phone` 作为生产身份。

不接受的临时方案：

- 在生产环境重新打开测试登录。
- 使用固定验证码 `000000`。
- 在页面上展示“测试验证码”。
- 在代码或文档里写真实手机号名单和真实验证码。
- 让所有公网访问者都能用临时码登录。

## 4. 代码开发员要做什么

代码开发员应围绕“正式登录闭环”完成仓库内工作。

### 4.1 页面与交互

- 改造登录页，去掉 M1 测试登录说明。
- 增加“手机号输入 + 获取验证码 + 验证码输入 + 登录”流程。
- 支持验证码发送中的 loading、倒计时、错误提示和成功提示。
- 支持 `next` 参数，登录成功后回到用户原本要去的页面；非法跳转路径仍要拦截。
- 保留退出登录入口，并确认退出后跳回首页或登录页。

### 4.2 服务端 API

建议至少提供：

- `POST /api/auth/sms/send-code`：发送验证码或触发受控临时登录码流程。
- `POST /api/auth/sms/login`：校验验证码并登录。
- `GET /api/auth/session`：读取当前登录态，继续复用或兼容现有接口。
- `POST /api/auth/logout`：退出登录，清除登录态。

API 要求：

- 所有入参都做服务端校验。
- 手机号格式必须校验。
- 验证码错误、过期、已使用、尝试次数过多都要返回明确错误。
- 频繁发送验证码要被拦截。
- 登录成功后写入服务端签名 Cookie。
- 不允许客户端传入任意 userId 冒充他人。
- 不在响应中返回验证码、密钥或敏感内部状态。

### 4.3 用户数据

建议形成或复用用户集合，至少能表达：

- 用户唯一 ID。
- 手机号或手机号哈希 / 脱敏展示字段。
- 创建时间。
- 最近登录时间。
- 账号状态：正常、禁用、试运行移除等。
- 是否为试运行白名单用户，若采用白名单方案。

注意：

- 不要把手机号当成所有业务表的唯一长期主键硬塞到各处；如果当前代码已用手机号作为临时用户 ID，需要给出兼容迁移方案。
- 不要破坏已有需求、家教信息、聊天、联系方式交换的数据归属规则。
- 新登录系统必须兼容已有服务端权限校验：当前用户是谁，只能由服务端会话判断。

### 4.4 短信服务接入

如采用腾讯云短信，代码开发员需要：

- 使用服务端环境变量读取短信 Secret、签名和模板 ID。
- 在服务端调用短信发送接口。
- 不在前端暴露短信密钥。
- 不在日志中打印完整手机号、验证码、SecretId、SecretKey。
- 对短信发送失败给用户返回可理解提示。
- 对服务商异常、模板未审核、余额不足等情况提供可定位日志，但不泄露密钥。

如短信未就绪，代码开发员需要：

- 实现受控白名单 / 一次性登录码方案。
- 明确该方案只在小范围试运行内生效。
- 增加环境变量或配置开关，避免误对公网开放。
- 提供退出临时方案、切换正式短信方案的说明。

### 4.5 测试与验证

代码开发员至少补充：

- 手机号格式校验测试。
- 发送验证码成功测试。
- 发送验证码频控测试。
- 验证码错误测试。
- 验证码过期测试。
- 验证码重复使用测试。
- 新手机号首次登录自动创建账号测试。
- 老手机号再次登录复用账号测试。
- 登录态刷新后仍可读取测试。
- 退出登录后不能访问个人数据测试。
- 生产环境测试登录仍不可用测试。
- 不泄露验证码、手机号、密钥的测试或审查说明。

## 8. “可以正常登录”的验收标准

以下标准必须可操作、可复验。

### 8.1 正式登录主流程

- 用户能在正式环境打开登录页。
- 登录页不再展示 M1 测试登录说明。
- 登录页不展示“测试验证码 000000”。
- 用户能输入有效手机号并请求验证码。
- 验证码发送成功时，页面给出明确提示。
- 新手机号首次通过验证码后，系统自动创建账号或完成注册。
- 老手机号再次通过验证码后，直接登录原账号。
- 登录成功后能进入家长 / 老师身份入口。
- 从受保护页面跳转到登录页时，登录成功后能回到原页面。

### 8.2 登录态与退出

- 登录后刷新页面，登录状态不丢。
- 登录后能访问个人页、我的发布、我的聊天、联系方式管理等个人数据。
- 退出登录后，服务端会话被清除。
- 退出登录后刷新页面仍保持未登录。
- 退出登录后不能访问个人数据或私有 API。
- 未登录用户访问受保护入口时被引导登录或得到 401。

### 8.3 验证码安全

- 错误验证码会被拒绝。
- 过期验证码会被拒绝。
- 已使用验证码不能重复使用。
- 频繁发送验证码会被拦截。
- 同一手机号连续输错验证码次数过多会被限制。
- 验证码不得出现在前端源码、浏览器可见数据、接口响应、日志、报告正文中。
- 短信密钥、验证码密钥、会话密钥不得出现在 Git 或报告正文中。

### 8.4 生产环境安全边界

- 正式环境 `APP_ENV=production`。
- `/api/auth/test-login` 在正式环境不可用。
- `M5_ENABLE_HOSTED_TEST_LOGIN=true` 即使误配，也不能打开生产测试登录。
- `NEXT_PUBLIC_ALLOW_TEST_LOGIN=true` 即使误配，也不能展示生产测试登录入口。
- `x-ungradu-test-user-phone` 在生产环境不能作为登录身份。
- `000000` 不能作为生产验证码。
- 生产 `AUTH_SESSION_SECRET` 使用独立强随机密钥，不复用测试密钥。

### 8.5 数据与隐私

- 登录成功不会泄露完整手机号给不该看到的人。
- 公开列表和详情仍不返回联系方式。
- 聊天和联系方式交换仍按原授权规则工作。
- 非参与者仍不能读取会话、消息或联系方式。
- 用户手机号、验证码和密钥不被写入前端日志、服务端普通日志或审查报告正文。

### 8.6 临时方案额外验收

如果短信服务暂未就绪，采用受控白名单 / 临时试运行方案，则还必须满足：

- 只有白名单手机号可以登录。
- 非白名单手机号被拒绝，并有清晰提示。
- 临时登录码不是固定 `000000`。
- 临时登录码有有效期和使用次数限制。
- 白名单新增 / 移除有记录。
- 临时方案有效期和退出条件写入验收报告。
- 不得宣布“完全公开登录上线完成”。

## 11. 开发交接摘要

给代码开发员的简版任务：

1. 把登录页从 M1 测试登录改成正式手机号验证码登录。
2. 新增发送验证码、校验验证码并登录的服务端 API。
3. 新手机号首次验证通过后创建账号，老手机号验证通过后复用账号。
4. 登录态继续使用服务端可信 Cookie 或等价安全机制。
5. 退出登录后清除会话，私有数据不可访问。
6. 继续保证生产环境测试登录不可用。
7. 补齐验证码错误、过期、频控、重复使用、新老用户、退出后拒绝访问等测试。
8. 更新 Code 文档和开发员工作记录。
9. 提供远端 commit、变更文件清单和验证命令结果。
10. 等产品经理验收后，交给 Zcode 使用 `DeepSeek V4 Pro` 复核。

## 12. 产品经理当前判断

本阶段可以启动代码开发，但存在必须项目总控制人确认的外部事项。

优先建议：

```text
正式短信验证码登录
```

如果短信服务暂未就绪，只能采用：

```text
受控白名单 + 一次性临时登录码 + 明确有效期 + 不公开开放
```

不得采用：

```text
恢复测试登录 / 固定 000000 / x-ungradu-test-user-phone 生产身份
```

本阶段通过后，项目才能说“正式环境真实用户可以正常登录”。在此之前，正式环境只能算“代码侧可发行候选通过，登录能力仍未完成”。
