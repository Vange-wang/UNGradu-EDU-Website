### 4.3 数据归属和越权校验

服务端接口已按以下规则实现：

- `contact_profiles`：只读写当前登录用户自己的联系方式档案。
- `parent_needs`：保存时强制使用当前用户作为 `ownerUserId`；我的列表只按当前用户查询；公开视图不返回 `ownerUserId`。
- `tutor_profiles`：保存时强制使用当前用户作为 `ownerUserId`；我的列表只按当前用户查询；公开视图不返回 `ownerUserId`。
- `conversations`：按来源对象 owner 建立参与者；非参与者不能读取会话、读取消息或发送消息。
- `contact_exchange_requests`：只有会话参与者可发起和查看；只有接收方可同意或拒绝；只有发起方可撤回。
- `authorized-profiles`：未同意、未二次确认、请求过期、拒绝、撤回或非参与者场景下均返回 `null`。

### 4.4 联系方式保护

## 5. 阻塞问题

### P1：尚未完成部署环境下的真实 API 闭环验证

Spec M5 要求：

- 核心流程全部走通。
- CloudBase 免费额度和部署方式经过验证。
- 已完成发布、筛选、聊天、交换联系方式流程的发布前验证。

当前已完成的是本地 Next.js 构建、服务端模块测试和 CloudBase 集合读取；但本轮未看到以下证据：

- CloudBase 云托管或 Web 应用托管部署成功记录。
- 部署后 `/api/*` 路由可在真实托管环境访问。
- 真实托管环境中完成登录、发布、筛选、聊天、交换联系方式闭环。
- 真实托管环境中的 `AUTH_SESSION_SECRET`、CloudBase 密钥和生产/测试环境变量配置校验。

复核进一步确认：`Code文档/README.md` 当前仅记录本地 CloudBase 服务端 SDK 连接、`.env.local` 配置、`cloudbase:check` 和 `m5:cloudbase:collections`，未发现云托管或 Web 应用托管的部署地址、部署步骤和部署后验证记录。

风险：

- 本地 `next build` 通过不能等同于 CloudBase 托管部署通过。
- 本地 API 可以读取 CloudBase 集合，不能等同于部署环境中的 API 路由、Cookie、安全头、环境变量和网络权限都可用。

验收影响：

- 该项阻塞 M5 发布前验收通过。

建议修复：

1. 将当前分支部署到 CloudBase 测试环境或云托管测试服务。
2. 记录部署方式、服务名、访问地址和环境变量配置方式。
3. 在部署地址上完成一次核心闭环验证：登录、发布、筛选、详情、聊天、交换联系方式、二次确认、授权展示。
4. 将结果追加到 M5 第二轮复验报告。

### P1：50 并发基础压测尚未覆盖真实 API 或部署环境

Spec M5 要求：

- Next.js API route 层在并发请求下正常。
- CloudBase SDK 真实读写在并发下正常。
- CloudBase 测试环境在 50 并发下响应稳定。

复核进一步确认：`m5:flow` 与 `m5:load` 指向同一测试文件，当前不存在独立的 HTTP 压测脚本。

验收影响：

## 6. 非阻塞观察

### 6.1 `m5:cloudbase:collections` 未检查 `users` 集合

当前 `npm run cloudbase:check` 默认读取 `users` 集合，并已通过；`npm run m5:cloudbase:collections` 检查了 6 个业务集合，但不包含 `users`。

由于当前 M5 尚未把真实用户账号写入 `users`，该问题不阻塞本轮。但从 Spec 数据对象看，`users` 属于核心集合，建议后续将 `users` 也纳入 M5 集合检查脚本，避免发布前遗漏。

### 6.2 页面仍显示“测试账号”文案

部分页面仍显示“当前测试账号”相关文案。考虑到当前仍是 M5 测试环境和临时登录态阶段，该项不阻塞本轮代码验收。但正式 MVP 发布前，如果采用真实手机号登录，应同步替换为更正式的账号文案。

### 6.3 正式短信验证码仍未接入

本轮通过 HttpOnly 签名 Cookie 解决了“前端 localStorage 登录态不可信”的问题，但登录入口仍是测试验证码 `000000`。生产环境禁用测试登录已经通过；正式上线前仍需补充合规手机号短信登录或明确上线阶段仍处于受限测试环境。

### 6.4 生产环境缺失 `AUTH_SESSION_SECRET` 会导致会话不可用

复核确认生产环境缺少 `AUTH_SESSION_SECRET` 时会话签名不会使用开发默认密钥，而是直接不可用。这是安全上正确的失败模式，但部署清单必须明确该变量必填，否则部署后登录态功能会表现为不可用。

### 6.5 `m5:flow` 与 `m5:load` 当前同源

`m5:flow` 与 `m5:load` 当前均执行 `vitest run m5-server-flow-and-load`。这不影响本轮服务端模块模拟通过的判断，但后续第二轮复验必须避免把这两条命令误读为两套独立验证。
