Claude Code 复核报告明确指出，本轮原始审查对象是“当前工作区相对 `HEAD` 的未提交变更”。复核环境只能访问 GitHub 远端仓库，无法访问开发者本机工作区。

该限制不影响本轮“暂不通过”结论的成立，但需要在最终报告中明确保留，避免误解为复核方已独立验证所有本地未提交代码。

## 3. 最终结论

MVP 收口阶段第一次代码验收结论：**暂不通过**。

本轮实现已覆盖多数 Spec 要求，且本地工程验证与本地真实 HTTP API flow/load 均通过。但按最终版 Spec 的阶段验收口径，仍有 4 个 P1 阻塞项需要关闭后才能判定本阶段通过：

1. 服务端业务逻辑已改动，但真实托管环境 `m5:hosted:verify` 尚未完成复验。
2. 发布前浏览器冒烟验收清单仍全部为“待执行”。

因此，本轮可以认定为：**主要代码收口项已实现，本地验证通过；发布前验收证据链尚未闭合。**

Claude Code 复核确认：在无法独立访问本地未提交工作区代码的限制下，初审报告的论证逻辑自洽、与项目历史脉络和此前 Spec 审核建议高度吻合，没有发现内部矛盾或明显夸大、缩小判断的问题，可以作为本轮验收的正式结论使用。

## 6. 阻塞问题

### P1-1：服务端业务逻辑已改动，但托管环境复验仍未完成

依据 Spec 第 13 节：

> 若本阶段任何改动涉及服务端业务逻辑，包括会话索引化、Cookie 校验、API 容错等 10.1-10.5 节改动，或涉及托管环境配置变更，均应在合并前复跑 `npm run m5:hosted:verify`；仅文档类交付物不强制要求复跑。

本轮实际改动已经涉及：

- 会话索引化：`server/conversations.ts`
- Cookie 校验：`server/auth-session.ts`
- API 容错：`features/api/api-client.ts` 及多个 API client

但 `规划文档/里程碑文档/发布前准备/架构收口问题修复对照表.md` 第 8-14 行均记录：

```text
现有 M5 托管地址复跑返回 HTML，待重新部署后复验
```

判断：

- 本地 `m5:http:flow/load` 已通过，属于重要正向证据。
- 最终 Spec 明确要求服务端业务逻辑改动需要托管复验。
- 当前缺少新部署后的 `M5_BASE_URL=<新托管地址> npm run m5:hosted:verify` 成功证据。

复核补充：

- 此项与此前 Claude Code Spec 审核意见中的标准修订一致，即 `m5:hosted:verify` 的触发条件不应只看“托管配置是否变化”，还应覆盖“服务端业务逻辑变更”。
- “现有 M5 托管地址复跑返回 HTML”可能是 CloudBase Run 冷启动或平台临时错误页，也可能是测试托管服务过期、被回收或配置漂移。下一轮复验前应先确认根因，再决定复跑原服务还是重新创建部署。

验收影响：阻塞本阶段通过。

修复建议：

1. 先确认现有托管地址返回 HTML 的根因：临时平台错误、冷启动、服务不可用、服务过期、配置失效或地址已变更。
2. 将当前收口阶段代码重新部署到 CloudBase Run 测试托管环境，或恢复可用测试托管服务。
3. 使用有效托管地址执行 `M5_BASE_URL=<托管地址> npm run m5:hosted:verify`。
4. 将目标地址、请求数、成功率、错误率、延迟指标写回架构收口问题修复对照表或第二轮复验报告。

### P1-3：会话索引化缺少旧数据迁移或兼容，既有会话可能不可见或重复创建

当前实现：

- `server/conversations.ts` 新增 `conversationUniqKey`、`participantKeys`、`sourceKey`。
- `createOrReadServerConversationFromSource()` 通过 `conversationUniqKey` 查询已有会话。
- `listServerConversationsForUser()` 通过 `participantKeys` 查询当前用户会话。

风险：

- M5 已经在 CloudBase 测试环境中创建过会话数据。
- 这些旧会话很可能只有 `participantUserIds`、`sourceId`、`sourceType`，没有本轮新增的 `conversationUniqKey` 和 `participantKeys`。
- 新逻辑不会通过 `conversationUniqKey` 找到旧会话，因此同一来源和同一双方用户再次发起聊天时可能重复创建会话。
- 新逻辑不会通过 `participantKeys` 找到旧会话，因此用户“我的聊天”列表可能看不到既有会话。

测试缺口：

- `tests/conversation-server.test.ts` 新增的大量历史会话测试数据已经带有 `conversationUniqKey` 和 `participantKeys`。
- 当前未看到覆盖“旧会话缺少新增索引字段，但仍应可读、可复用或被迁移”的回归测试。

判断：

- 本轮确实关闭了“继续全量扫描”的代码模式。
- 但缺少旧数据兼容策略，会在已有测试托管数据、后续试运行数据或真实生产迁移中形成新的业务断点。

复核补充：

- 此项与 Claude Code 此前 Spec 审核意见高度吻合。此前审核已指出，聊天会话全集合扫描与 M5 第四轮公开列表缺陷属于同类模式复发，应该补充“大量历史会话下仍能查到当前用户会话”的回归测试。
- 本轮初审将该预见性风险落实为具体 P1 阻塞项，技术逻辑成立：只要新查询依赖新字段，旧数据没有该字段就无法命中。

验收影响：阻塞本阶段通过。

修复建议：

1. 增加旧会话兼容读取或一次性迁移策略。
2. 对缺少 `conversationUniqKey` / `participantKeys` 的旧会话，按 `sourceType`、`sourceId`、排序后的 `participantUserIds` 生成并写回新索引字段。
3. 增加回归测试：旧会话缺少新索引字段时，当前用户仍能看到聊天列表，且重复发起聊天不会创建第二条会话。
