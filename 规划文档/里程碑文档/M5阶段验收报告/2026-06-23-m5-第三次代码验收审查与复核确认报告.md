## 1. 验收结论

M5 第三次代码验收最终结论：**暂不通过**。

本轮新增提交确实解决了第二轮报告中的一项关键设计缺口：当托管平台以 `NODE_ENV=production` 运行隔离 M5 测试环境时，系统现在可以通过 `APP_ENV=test` 且 `M5_ENABLE_HOSTED_TEST_LOGIN=true` 临时允许 `/api/auth/test-login` 写入后端签名 Cookie；同时 `APP_ENV=production` 作为最高优先级生产边界，仍会拒绝临时测试登录。

复核确认：上述托管测试登录隔离设计没有破坏生产安全边界。即使误将 `M5_ENABLE_HOSTED_TEST_LOGIN=true` 或 `NEXT_PUBLIC_ALLOW_TEST_LOGIN=true` 配到生产环境，只要 `APP_ENV=production`，服务端仍拒绝临时测试登录。

但 M5 发布前验收仍不能通过，原因有两项：

1. 仓库和开发记录仍未提供实际 CloudBase 云托管或 Web 应用托管部署地址，也没有部署地址下 `M5_BASE_URL=<部署地址>` 的 HTTP flow/load 复跑证据。

复核确认：第二项不是 `199ee3e0` 新增代码引入的回归。`199ee3e0` 的 patch 并未改动 `server/parent-needs.ts` 或 `server/tutor-profiles.ts`；本轮暴露的是此前已存在、但在 fake collection 或较轻量验证中未被触发的公开列表查询缺陷。真实 HTTP route + 真实 CloudBase 数据集合 + 50 并发压测让该缺陷第一次稳定暴露。

因此，本轮只能确认“托管测试登录隔离方案补强通过”，不能确认 M5 发布前验证通过。

## 4. 阻塞问题

### P1：HTTP 50 并发基础压测失败，发布后筛选结果无法稳定包含新建需求

复现命令：

```powershell
Set-Location Code文档
npm run dev -- --hostname 127.0.0.1 --port 3000
npm run m5:http:load
```

复验结果：

```text
M5 HTTP load start
Target: http://127.0.0.1:3000
Pairs: 25; virtual users: 50
Success pairs: 0
Elapsed: 1921ms
Requests: 200
Success rate: 76.00%
Error rate: 0.00%
Latency avg/p95/max: 545ms / 774ms / 804ms
M5 HTTP load failed
Created parent need was not visible in filtered public list.
```

直接失败点：
- `Code文档/scripts/m5-http-flow-and-load.mjs` 查询 `/api/parent-needs?subject=math`。
- 脚本断言刚创建的 `parentNeed.id` 必须出现在筛选列表。
- 实际断言失败，脚本退出。

相关实现风险：
- `Code文档/server/parent-needs.ts` 的公开列表实现使用 `collection.where({}).get()` 拉取集合数据，再在服务端内存中排序和筛选。
- `Code文档/server/tutor-profiles.ts` 的公开家教信息列表也采用同类 `collection.where({}).get()` 后内存过滤方式。
- 当前没有在 CloudBase 查询层按 `subject`、`createdAt` 或稳定分页条件过滤/排序，也没有明确分页策略。

复核确认的故障机制：
- 多数云数据库或类 MongoDB 接口的 `.get()` 默认带有返回条数上限。集合文档数超过单次返回上限后，`where({}).get()` 拿到的是集合子集，不是全量数据。
- 该子集通常不保证按 `createdAt` 倒序返回。服务端随后再做内存排序和筛选，只能处理这次取回的子集。
- 当测试集合数据积累后，新创建记录可能没有落在 `.get()` 本次返回的子集内，于是“刚发布后按 subject 筛选不可见”。
- 这与 `m5:http:load` 在 25 对用户 / 50 虚拟用户场景下失败，而单用户 `m5:http:flow` 仍通过的现象吻合。

复核补充定性：
- 该问题不是 `199ee3e0` 引入的回归，而是此前已存在的查询模型缺陷。
- 前两轮 `m5:flow` / `m5:load` 使用 fake collection 或较轻量数据条件，无法触发真实 CloudBase 查询返回上限和排序不稳定问题。
- 本轮真实 HTTP route + 真实 CloudBase 数据集合 + 50 并发压测提高了验证真实性，才暴露出该缺陷。
- 这不只是压测边界问题。只要 CloudBase 测试或生产集合中文档数超过单次 `.get()` 默认返回上限，即使低并发或单用户场景，也可能出现用户刚发布后在公开筛选列表看不到自己内容的情况。因此应按核心功能正确性缺陷处理。

验收影响：
- Spec M5 明确要求完成 50 并发核心流程基础压测，且发布、筛选、聊天、交换联系方式正常响应。
- 当前本地真实 HTTP + CloudBase 测试环境下的 50 并发脚本已经失败，不能判定 M5 通过。

建议修复方向：
1. 将公开列表查询改为 CloudBase 查询层可稳定命中的条件查询、排序和分页，不要依赖 `where({}).get()` 后内存过滤完整集合。
2. 为 M5 HTTP load 脚本增加测试数据唯一标识或更精确的查询条件，避免在历史测试数据中做不稳定全局筛选。
3. 修复后重新跑 `npm run m5:http:flow`、`npm run m5:http:load`，并记录成功率、错误率和延迟指标。

## 5. 非阻塞观察

### P2：HTTP 压测指标会低估业务断言失败

本轮 `m5:http:load` 已经失败，但脚本输出：

```text
Success rate: 76.00%
Error rate: 0.00%
```

原因是 `recordFailure` 目前只在 HTTP 状态码不符合预期或网络错误时记录失败；业务断言失败，例如“刚创建的需求未出现在筛选列表”，不会被计入失败分布。

复核确认：
- HTTP 状态码异常或网络错误会进入 `recordFailure`。
- `Created parent need was not visible in filtered public list.` 属于业务断言失败，直接 `throw new Error`，没有进入 `recordFailure`。
- 因此脚本会同时出现“整体 load 失败、Success pairs: 0”和“Error rate: 0.00%”这种看似矛盾的输出。

该问题不单独阻塞 M5，因为当前已有 P1 压测失败；但后续若要把脚本输出作为发布前压测报告，需要把业务断言失败计入失败率和失败分布。
