## 4. 阻塞问题（复核结果）

### P0：生产环境仍可通过公开环境变量启用临时测试登录

复核证据（独立验证，逐行核对原文引用）：

```ts
// features/auth/test-auth.ts 第34-42行
export function isTestLoginAllowed({
  allowTestLogin,
  nodeEnv
}: {
  allowTestLogin?: string;
  nodeEnv?: string;
}) {
  return nodeEnv === "development" || allowTestLogin === "true";
}
```

```tsx
// features/auth/login-form.tsx 第20-27行
const allowTestLogin = useMemo(
  () =>
    isTestLoginAllowed({
      allowTestLogin: process.env.NEXT_PUBLIC_ALLOW_TEST_LOGIN,
      nodeEnv: process.env.NODE_ENV
    }),
  []
);
```

复核确认这是一个 **OR 条件**：只要 `allowTestLogin === "true"`，无论 `nodeEnv` 是什么（包括 `"production"`），函数都返回 `true`。`NEXT_PUBLIC_` 前缀意味着这个变量本身会被打包进客户端 JS。

复核还原文核对了原报告引用的测试用例：

```ts
// tests/auth.test.ts 第39-47行
it("requires an explicit flag outside development", () => {
  expect(isTestLoginAllowed({ nodeEnv: "production" })).toBe(false);
  expect(
    isTestLoginAllowed({
      nodeEnv: "production",
      allowTestLogin: "true"
    })
  ).toBe(true);
});
```

**复核观察（原报告未明确点出的细节）**：这个测试用例的标题是"要求明确开关"（requires an explicit flag），但断言本身把"生产环境 + 显式开关 = 允许测试登录"当作期望行为钉了下来。这意味着这不是一处疏忽的 bug，而是被显式设计、显式测试覆盖的行为——如果后续有人想把这行代码改成真正安全的版本，第一步就会先被这条测试拦下来，需要同时修代码和测试才能修复。

复核还核对了 `开发员工作记录.md` 第123行的描述："生产环境必须显式配置 `NEXT_PUBLIC_ALLOW_TEST_LOGIN=true` 才允许测试登录"。复核进一步查证发现，这句话实际上是在响应上一轮审查报告里给出的建议——上一轮报告建议"临时测试登录必须有环境开关……生产环境不得启用"，开发员确实加上了一个环境变量开关，但**实现的方向正好相反**：本应是"无论开关设成什么，生产环境都强制拒绝"的硬限制，做成了"生产环境下，开关可以覆盖默认拒绝"的放行通道。换句话说，建议被采纳了，但理解反了。

Spec 依据（复核确认行号与原文一致）：

- spec 第677行：如果短信验证码短期不可用，M1 可采用临时测试登录方案用于本地或测试环境开发。
- spec 第678行：临时测试登录方案不得出现在生产环境配置中。
- spec 第830行：生产环境不得启用临时测试登录方案。

影响（维持原判断，补充编译产物层面的证据）：

- 这是账号入口的安全闸门问题。
- 复核已用实际构建证实：一旦生产部署配置中带有 `NEXT_PUBLIC_ALLOW_TEST_LOGIN=true`，固定验证码 `000000` 建立测试登录态的能力会原样出现在生产环境的服务端渲染产物中，不存在"代码写了但永远不会被触发"的侥幸。
- 由于变量名带 `NEXT_PUBLIC_`，这个开关本身也会被打进客户端可读的 JS 中，进一步降低了攻击者发现这个入口的门槛。

建议修复（维持原报告建议）：

- `isTestLoginAllowed` 必须显式拒绝生产环境，例如：

  ```ts
  export function isTestLoginAllowed({ allowTestLogin, nodeEnv }: {...}) {
    if (nodeEnv === "production") return false;
    return nodeEnv === "development" || allowTestLogin === "true";
  }
  ```

- 更新 `tests/auth.test.ts`：把现有那条"production + allowTestLogin=true => true"的断言改为断言 `false`，并补一条"production 下无论 allowTestLogin 是什么都必须返回 false"的用例，确保以后类似回退会被测试拦下来。
- 更新 `开发员工作记录.md` 中关于"生产环境显式配置即可启用测试登录"的描述，改为准确反映"生产环境下该开关不生效"。
- 修复后建议重新跑一次本复核中执行的生产环境模拟构建（`NODE_ENV=production NEXT_PUBLIC_ALLOW_TEST_LOGIN=true npm run build`），并检查编译产物中 `isTestLoginAllowed` 对应的压缩代码，确认其逻辑不再包含可被该环境变量绕过的分支，作为修复验证的硬证据。

## 5. 非阻塞问题（复核结果）

### P1：个人页和联系方式管理页尚未绑定测试登录态

复核证据（独立验证）：

- `app/page.tsx` 第29-31行，"个人页面"入口仍是普通 `Link`，未经过 `GuardedEntryLink`。
- `app/profile/page.tsx` 全文搜索不到任何 `useTestSession` 或登录态读取逻辑，第17-23行直接渲染四个链接。
- `app/profile/contact/page.tsx` 第24-31行的 `useEffect` 只调用 `readContactProfile(storage)`，不检查当前是否存在测试登录态。

与原报告一致，维持 **P1，非阻塞但建议在 M2 前收口**。

复核补充观察（原报告未直接点出的细节）：

复核进一步查看了 `contact-profile-storage.ts`，确认存储 key 是固定字符串：

```ts
const CONTACT_PROFILE_KEY = "ungradu.contactProfile";
```

这个 key 没有携带任何用户标识。原报告在建议部分已经提到"联系方式本地存储可以暂时继续用 localStorage，但 key 最好带上当前测试手机号，避免不同测试账号互相覆盖"，复核确认这条建议命中了真实存在的问题：**在同一浏览器中，任何两个测试手机号登录后操作联系方式管理页，会读写同一份数据，后保存的会覆盖前一个账号的内容**。这与 P1 本身（联系方式管理与登录态完全脱钩）是同一个根因的两个表现，建议在收口 P1 时一并修复 key 的设计，而不是分两次改。

建议（维持原报告建议）：

- 个人页和联系方式管理页至少在本地测试登录体系下要求已有测试 session。
- 未登录访问 `/profile` 或 `/profile/contact` 时，跳转到 `/login?next=...`。
- 联系方式本地存储可以暂时继续用 `localStorage`，但 key 应该带上当前测试手机号（例如 `ungradu.contactProfile.${phone}`），避免不同测试账号互相覆盖。

此项不必阻止 P0 修复后的 M1 验收，但建议在进入 M2 前一并收口。
