# 阶段任务闭环工作流

更新日期：2026-07-18

维护负责人：项目总负责人 Agent

适用场景：项目总控制人下达阶段性任务，例如“完成 MVP 阶段的 M5 阶段”。

## 1. 角色链路

| 角色 | 职责 |
| --- | --- |
| 项目总控制人 | 向项目总负责人下达阶段任务，处理必须人工介入的高风险事项 |
| 项目总负责人 Agent | 分发命令、编排工作流、创建必要目录、归档交流、驱动闭环、责任溯源 |
| 产品经理 Agent | 根据 Spec 确认阶段规划、待完成事项、验收标准；执行代码审查；合并最终验收报告 |
| 代码开发员 Agent | 根据 Spec 和产品经理说明完成实现、修复、测试、提交代码，并给出 GitHub 代码分支链接 |
| Zcode 复核会话 | 基于代码仓库链接和产品经理审查报告，输出复核版本审查报告 |
| ISSUE 管理员 Agent | 接收代码开发员提出的 Issue 包，并维护 Issue 编号、状态、Open/Close 归档和闭环依据 |

## 2. 总流程

1. 项目总控制人向项目总负责人下达阶段任务。
2. 项目总负责人向产品经理 Agent 说明当前阶段任务。
3. 产品经理 Agent 读取 MVP Spec 和相关阶段文档，确认该阶段规划、待完成事项、验收标准，并打包说明给项目总负责人。
4. 项目总负责人把产品经理说明、Spec 路径、阶段目标和输出要求转发给代码开发员 Agent。
5. 代码开发员 Agent 完成代码任务，并提交当前代码分支 GitHub 仓库链接。
6. 同一阶段内，代码仓库链接只需由代码开发员首次提供一次；后续审查和复核沿用该链接。
7. 代码开发员 Agent 表达“已完成”后，项目总负责人将代码仓库链接交给产品经理 Agent，要求进行该阶段第 N 次审查。
8. 产品经理 Agent 输出第 N 次审查验收报告 Markdown，并放入对应阶段验收报告文件夹。
9. 项目总负责人打开 Zcode 复核会话，提供代码仓库链接和产品经理第 N 次审查报告，要求输出第 N 次复核版本审查报告。
10. 项目总负责人将 Zcode 复核报告保存为 Markdown 到同一阶段验收报告文件夹。
11. 项目总负责人将复核报告交给产品经理 Agent。
12. 产品经理 Agent 合并产品经理审查报告和 Zcode 复核报告，整理为第 N 次最终版报告。
    - 这里的“最终版报告”指该第 N 次审查循环的最终报告，不代表整个阶段已经最终完成。
    - 每一轮审查都应形成自己的第 N 次最终版报告入口，作为该轮继续修复或允许验收的唯一依据。
13. 产品经理 Agent 删除或要求删除前两份中间报告入口，只保留最终版报告作为该轮唯一入口，避免误认点错。
14. 项目总负责人将最终版报告发给代码开发员 Agent。
15. 代码开发员 Agent 按最终版报告继续修改、验证、提交。
16. 重复第 7 到第 15 步，直到产品经理审查报告、Zcode 复核报告、最终审查报告均给出允许验收结论。
17. 当前阶段任务完成后，项目总负责人提醒代码开发员 Agent 和产品经理 Agent 提交文件更新 Git。
18. 项目总负责人向项目总控制人做简短总结：改了什么、验证了什么、还有什么风险。

## 3. 阶段验收报告目录规则

项目总负责人在启动某阶段审查前，必须提前确认并创建对应报告目录。

目录命名示例：

```text
规划文档/里程碑文档/M5阶段验收报告/
```

报告入口规则：

- 产品经理第 N 次审查报告、Zcode 第 N 次复核报告、最终版报告可以在整理前短暂共存。
- 产品经理合并最终版报告后，该轮只保留最终版报告入口。
- 中间报告不得长期保留在同一报告目录，避免后续误读。
- 不同轮次的最终版报告可以保留，例如第一次最终报告、第二次最终报告。

## 4. GitHub 链接规则

- 每个阶段由代码开发员 Agent 首次提供一次当前代码分支 GitHub 仓库链接。
- 同一阶段后续审查、复核和修复默认沿用该链接。
- 若代码分支发生变化、仓库迁移或基线失效，代码开发员 Agent 必须主动说明并提供新链接。
- 项目总负责人需在交流记录和任务记录中保存该阶段当前使用的代码仓库链接。
- 项目进入正式部署 / 生产试运行阶段后，后续新任务不得继续默认沿用 `codex/m5-security-preflight` 这类 M5 阶段分支。
- 后续每个正式部署阶段的新功能、体验优化、生产修复或验收补丁，应由代码开发员基于当前已确认的部署基线新建语义化分支，并在任务回报中明确新分支名、基线 commit、目标 commit 和推送状态。
- 旧 M5 分支仅作为历史审查依据保留；除非项目总控制人明确要求修补历史分支，否则不得把新阶段代码继续推到旧 M5 分支。

## 4.1 发布阶段 S1 / S2+ 规则

- 发布阶段 `S1` 已定义为“发布收口、生产试运行修复与追溯归档”，当前口径为已完成。
- 后续发布阶段任务不再称为“继续完成 S1”，应从 `S2` 开始规划，例如生产运行观察、运维基线、风控审核、公开推广前评审等。
- S1 的固定 Spec 入口为：`规划文档/Spec文档/Release_version_Spec/2026-06-29-release-s1-发布阶段-spec.md`。
- S1 已验收的聊天、联系方式交换、保存密码、密码登录、登录状态 UI 同步等事项，不应重新登记为 S1 阻塞项；如后续出现新回归，应按 S2+ 新 Issue 单独登记。
- 发布阶段后续每个新任务必须记录：阶段编号、任务 ID、目标分支、基线 commit、目标 commit、是否推送、验证命令、部署状态和验收结论。
- 需要写文件、提交 Git、推送或构建的任务，优先在项目总控制人当前已授权完全访问的前台线程处理；后台只读线程仅用于分析、状态同步或不需要写入的审查。

## 4.2 发布报告与远端追溯规则

- 发布阶段的产品审查报告、Zcode / Claude 复核报告、最终审查报告、执行打包说明、Issue 总表、Open / Close Issue 单文件和工作记录，默认应纳入仓库工作区。
- 当文档已提交并推送后，才能表述为“远端可追溯”。
- 当文档只在本地工作区更新、尚未提交或尚未推送时，只能表述为“本地工作区已更新”，不得作为远端追溯证据。
- 每个 Issue 关闭记录必须写明关闭依据；涉及代码修复时，还必须写明分支、基线 commit、目标 commit、验证命令和生产验收反馈。
- `ISSUE-0005` 已作为 S1 追溯归档规范事项关闭；后续同类问题不再复用 `ISSUE-0005`，应按新阶段新问题重新编号。

## 5. Zcode 复核规则

项目总负责人负责：

- 打开 Zcode 复核会话。
- Zcode 复核模型统一使用 `DeepSeek V4 Pro`，不得使用 Flash 模型。
- 贴出代码仓库链接。
- 贴出产品经理第 N 次审查报告。
- 要求 Zcode 输出第 N 次复核版本审查报告。
- 将 Zcode 复核报告保存为 Markdown 到同一阶段验收报告文件夹。
- 将复核报告交回产品经理 Agent 合并。

Zcode 复核报告不替代产品经理最终报告，最终入口由产品经理 Agent 合并整理。

## 6. 循环终止条件

只有当以下三类报告均给出允许验收结论时，当前阶段任务才算完成：

- 产品经理审查报告。
- Zcode 复核报告。
- 产品经理合并后的最终审查报告。

若任一报告结论为暂不通过、有条件通过、需修复、需补验证或存在阻塞，则继续进入代码开发员修复循环。

## 7. 允许暂停询问项目总控制人的情况

除以下情况外，项目总负责人不得中途停止流程，应持续行动直到阶段完成：

- 需要账号、密钥、外部权限。
- 有多个高风险产品决策无法合理默认。
- 继续执行可能破坏数据或产生不可逆后果。
- 需要项目总控制人手动重新部署网站或代码配置。

调度超时暂停规则：

- 项目总负责人向其他成员线程发送任务信息后，如超过 3 到 4 分钟无任何动作、行动加载或思考进展，则必须暂停。
- 暂停的含义是停止当前轮思考与所有动作，不继续等待、轮询、改道执行或自行推进。
- 暂停后必须等待项目总控制人下一次明确要求“继续任务”后，才重新调用任务或接续调度。

## 9. 最终汇报格式

阶段完成后，项目总负责人只向项目总控制人输出简短总结：

```text
改了什么：
验证了什么：
还有什么风险：
```

不得用冗长过程替代结论；完整过程应写入交流记录和工作记录。
