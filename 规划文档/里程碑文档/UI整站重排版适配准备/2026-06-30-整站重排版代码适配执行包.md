# 整站 UI 重排版代码适配执行包

日期：2026-06-30

任务 ID：`UI-REDESIGN-ADAPT-2026-06-30-001`

阶段：发布后 UI 体验重排版适配准备

状态：待代码开发员接收

## 1. 背景

项目总控制人反馈此前首页微调版“太杂”“界面太丑”，明确要求：

```text
直接打乱整个格局，重新设计，把所有已经存在的界面都重新排版设计，要求简单但不低调。
```

UI 设计师已输出整站级大方向改版方案，核心方向是：

- 白色为主基底。
- 天蓝为主行动和结构色。
- 黄色只做少量强调。
- 不再沿用旧的统一 `content-panel` 卡片式页面。
- 按页面类型重排版：Gateway、Filter Workbench、Step Form、Conversation Workspace、Account Dashboard、Notice Pages。

总负责人判断：该 UI 方案方向成立，可以进入代码适配准备；不要求 UI 设计师返工大方向。

## 3. 适配总原则

本轮优先做页面结构和视觉样式适配，不改变核心业务流程。

必须保持：

- 登录、退出、密码登录、验证码登录逻辑不变。
- 发布需求、发布老师资料的字段和校验逻辑不变。
- 聊天和联系方式交换流程不变。
- 联系方式不在公开页展示。
- 风险与功能反馈边界不变。
- 生产运行和测试脚本不因 UI 适配被破坏。

不得通过 UI 暗示：

- 实名认证。
- 老师资质认证。
- 担保交易。
- 在线支付。
- 退款或合同。
- 即时人工客服。
- 人工仲裁。
- 教学质量保证。
- 自动推荐。
- 复杂排课、课时记录或评价体系。

## 4. 分阶段适配建议

### 4.1 第一批：全局视觉 token 与基础布局

目标：

- 在 `Code文档/app/globals.css` 或现有样式入口中建立新的颜色、间距、按钮、页面容器、卡片、工作台、表单分组等基础 class。
- 尽量复用现有 React 结构，避免先大拆组件。
- 保留响应式规则：移动端单列，桌面端左右布局。

建议范围：

- 全局背景色。
- 顶部导航基础样式。
- 主按钮 / 次按钮。
- 页面标题区。
- 容器最大宽度。
- 卡片边框与圆角。

验收：

- 旧功能路径仍可访问。
- 页面没有横向滚动。
- 移动端不出现文字互相遮挡。

### 4.2 第二批：首页与工具页

目标：

- 首页改为 Gateway Layout。
- 登录页改为 Split Auth。
- 规则页、反馈页改为 Notice Pages。

涉及页面：

- `/`
- `/login`
- `/rules`
- `/feedback`

验收：

- 首页首屏能明确看到“找家教”和“做家教”两条入口。
- 登录页未登录时仍能正常显示验证码 / 密码登录入口。
- 已登录访问登录页仍不显示登录表单。
- 反馈页继续明确“不承诺即时客服或人工介入处理”。

### 4.3 第三批：广场页与详情页

目标：

- 需求广场、家教信息广场改为 Filter Workbench。
- 详情页改为 Detail Sheet：主信息 + 侧边行动。

涉及页面：

- `/parent-needs`
- `/tutor-profiles`
- `/parent-needs/[id]`
- `/tutor-profiles/[id]`

验收：

- 筛选字段可用。
- 列表结果仍展示核心业务信息。
- 公开列表和详情页不展示联系方式、ownerUserId、集合名、密码哈希或验证码信息。
- 详情页仍有返回入口。

### 4.4 第四批：发布页 Step Form

目标：

- 发布需求和发布家教信息改为分组任务式表单。
- 不改变字段、校验、提交 API 和保存逻辑。

涉及页面：

- `/parent-needs/new`
- `/tutor-profiles/new`

验收：

- 原有字段都仍然可填写。
- 老师多组“学段 + 科目 + 课时费”能力仍可用。
- 表单错误提示仍清楚。
- 提交成功后的跳转或反馈不变。

### 4.5 第五批：聊天与个人中心

目标：

- 聊天页改为 Conversation Workspace。
- 个人页改为 Account Dashboard。
- 个人子页使用 Account Form / Owner List / Conversation List。

涉及页面：

- `/chats/[id]`
- `/profile`
- `/profile/contact`
- `/profile/parent-needs`
- `/profile/tutor-profiles`
- `/profile/chats`

验收：

- 聊天发送消息正常。
- 联系方式交换按钮只在明确状态区出现。
- 未授权时不展示双方联系方式。
- 个人页功能入口清晰。
- 退出登录仍有二次确认。

## 5. 代码开发员执行要求

若进入代码适配，代码开发员必须：

- 使用当前生产试运行分支或新建语义化分支，并回报分支名。
- 回报基线 commit、目标 commit、是否推送。
- 每一批适配完成后运行至少：
  - `npm run typecheck`
  - `npm test`
  - `npm run lint`
  - `npm run build`
- 涉及页面结构 / 样式时补充浏览器截图或本地页面冒烟说明。
- 不引入新业务能力。
- 不修改数据库集合。
- 不修改认证、聊天、联系方式交换、密码和验证码主逻辑。

## 6. 建议交付顺序

建议不要一次性改完整站。推荐顺序：

1. 第一批全局 token 与基础布局。
2. 第二批首页、登录、规则、反馈。
3. 第三批广场页和详情页。
4. 第四批发布页。
5. 第五批聊天和个人中心。

每一批都应形成可验证的独立提交或至少独立回报。

## 7. 总负责人判断

该 UI 设计方案可以交给代码开发员进入适配准备，不需要退回 UI 设计师重做大方向。

但适配必须以“分批、可验收、不改业务逻辑”为原则。第一步建议由代码开发员做只读技术评估，确认当前组件和 CSS 的改动范围，再决定是否在当前前台完全访问线程中执行代码改造。
