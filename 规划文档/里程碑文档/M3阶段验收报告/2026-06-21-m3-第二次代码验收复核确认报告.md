## 1. 验收结论

M3 第二次代码验收结论：**暂不通过**。

本轮修复已经解决第一次验收报告中的主路径 P0：新发布的家长需求和大学生家教信息不再使用手机号拼接公开详情 ID，而是改为不透明 ID，并补充了新记录 ID 与详情链接不包含 `ownerPhone` 的测试。

但本轮为处理第一次报告中的 P2 兼容风险，新增了从本地存储旧 key 中恢复 M2 历史数据的逻辑。该逻辑会把旧记录重新展示到公开广场中，而旧记录的 `id` 仍可能包含发布者手机号。由于广场页继续用 `id` 拼接公开详情链接，旧数据一旦被恢复，就会再次把手机号暴露到浏览器地址栏、历史记录、截图、日志和分享链接中。

因此，第一次验收中的 P0 隐私阻塞项在“历史数据兼容路径”上仍未彻底关闭。M3 在该缺口修复并复验通过前，不建议进入 M4 站内聊天与联系方式交换开发。

## 3. 已确认修复

### 3.1 新发布记录 ID 已改为不透明 ID

家长需求保存路径已从手机号拼接 ID 改为调用不透明 ID 生成函数：

- `Code文档/features/parent-needs/parent-need-storage.ts`

核心实现：

```ts
function createOpaqueId(prefix: string) {
  if (globalThis.crypto?.randomUUID) {
    return `${prefix}-${globalThis.crypto.randomUUID()}`;
  }

  return `${prefix}-${Date.now()}-${Math.random().toString(36).slice(2, 12)}`;
}

function createParentNeedId() {
  return createOpaqueId("parent-need");
}
```

大学生家教信息保存路径存在对称实现：

- `Code文档/features/tutor-profiles/tutor-profile-storage.ts`

确认结果：

- `createParentNeedId` 和 `createTutorProfileId` 不再接收 `ownerPhone` 参数。
- 新记录 ID 优先使用 `crypto.randomUUID()`。
- 回退方案也不包含手机号、微信号或其他可识别联系方式。
- `saveParentNeed` 与 `saveTutorProfile` 均调用无参数的不透明 ID 生成函数。

对应测试：

- `Code文档/tests/parent-need-marketplace.test.ts` 中存在 `uses an opaque detail id without the owner phone`。
- `Code文档/tests/tutor-profile-marketplace.test.ts` 中存在对称用例。

测试断言覆盖：

- `saved.value.id` 不包含 `ownerPhone`。
- `/parent-needs/${saved.value.id}` 不包含 `ownerPhone`。
- `/tutor-profiles/${saved.value.id}` 不包含 `ownerPhone`。

结论：新发布记录主路径的公开 ID 泄露手机号问题已修复。

### 3.2 M2 旧数据 owners 索引兼容方向正确

本轮新增了从 `localStorage`/测试内存存储枚举旧 key 的能力：

- 该兼容逻辑本身有产品体验价值，但必须与旧记录 ID 脱敏绑定，否则会重新触发 P0 隐私风险。

## 4. 阻塞问题

### P0：M2 旧记录恢复后仍可能通过公开详情 URL 泄露手机号

严重程度：P0

状态：未通过

问题说明：

本轮兼容逻辑会从旧 key 恢复 owner phone，再调用原有读取函数返回对应记录。以家长需求为例：

```ts
export function readAllParentNeeds({
  storage
}: {
  storage: KeyValueStorage;
}): SavedParentNeed[] {
  const ownerPhones = readAllOwnerPhones(storage);

  ownerPhones.forEach((ownerPhone) => saveOwnerPhone(ownerPhone, storage));

  return ownerPhones.flatMap((ownerPhone) => readParentNeeds({ ownerPhone, storage }));
}
```

关键问题是：该函数枚举 owner 手机号后，直接调用 `readParentNeeds` 把存储中的记录原样读出并返回，没有对旧记录的 `id` 字段做重写、迁移或脱敏。大学生家教信息侧存在同构问题。

现有旧数据兼容测试中，已经构造了类似下面的旧格式记录：

```ts
id: `${ownerPhone}-legacy-id`
```

但测试只断言旧记录能被读出、`ownerPhone` 正确，没有断言恢复后的旧记录 `id` 或详情链接不含手机号。

公开广场页仍然直接使用 `id` 拼接详情链接：

- `Code文档/app/parent-needs/page.tsx`
- `Code文档/app/tutor-profiles/page.tsx`

因此，若用户在 M2 阶段已有形如 `13800138000-...` 的历史记录，本轮新兼容逻辑会让这些记录进入广场列表，详情链接会变成：

```text
/parent-needs/13800138000-legacy-id
/tutor-profiles/13800138000-legacy-id
```

这与 M3 “详情页不展示联系方式”和第一次报告中“公开 URL 不得泄露发布者登录手机号”的验收要求冲突。

## 5. 独立复现验证

为避免仅凭代码阅读得出推测性结论，本次复核额外编写了最小复现脚本，模拟 M2 历史记录场景：

1. 构造一条没有 owners 索引的家长需求记录。
2. 将记录 `id` 设置为 `13800138000-legacy-id`。
3. 调用 `readAllParentNeeds`。
4. 打印返回结果中的 `id` 和对应详情页 URL。

实际运行结果：

```text
NEEDS LENGTH: 1
RETURNED ID: 13800138000-legacy-id
DETAIL URL WOULD BE: /parent-needs/13800138000-legacy-id
```

该结果证实：`readAllParentNeeds` 会把带手机号的旧 `id` 原样返回，对应公开详情链接会包含完整发布者登录手机号。

结论：旧数据路径的 P0 不是理论风险，而是可以被实际触发、可复现的真实问题。
