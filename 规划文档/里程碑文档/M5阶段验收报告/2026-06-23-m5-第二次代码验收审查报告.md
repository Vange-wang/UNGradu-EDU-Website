## 1. 验收结论

M5 第二次代码验收结论：**暂不通过**。

本轮新增 `m5:http:flow` 和 `m5:http:load`，已经把第一轮的“仅 fake collection 服务端模块模拟”推进到“本地 HTTP API route + 真实 CloudBase 测试环境”的验证口径。经产品经理复验：

- 本地开发服务 `http://127.0.0.1:3000` 下，HTTP 核心闭环通过。
- 本地开发服务 `http://127.0.0.1:3000` 下，25 对用户 / 50 虚拟用户 HTTP 基础压测通过。
- `cloudbase:check` 与 `m5:cloudbase:collections` 均可读取测试环境集合。

但第一轮最关键的发布前阻塞项仍未完全关闭：

1. 仓库和开发记录仍未提供 CloudBase 云托管或 Web 应用托管部署地址、部署方式和部署后验证记录。
2. 新增 HTTP 脚本默认目标仍是本地 `127.0.0.1:3000`；虽然支持 `M5_BASE_URL`，但本轮未提供真实托管地址下的执行证据。
3. 用生产构建运行态 `next start` 复验时，新增 HTTP 脚本在第一步 `/api/auth/test-login` 即被 401 拒绝。这符合“生产环境禁用临时测试登录”的安全要求，但也说明该脚本不能直接作为生产/托管运行态闭环验证工具，除非托管环境明确是非生产测试运行态，或先接入正式登录能力。

因此，本轮只能判定为：**本地 HTTP API + 真实 CloudBase 口径的 M5 验证明显补强，但尚未达到 CloudBase 托管发布前验收标准**。

## 4. 阻塞问题

### P1：CloudBase 托管部署后的真实 API 闭环验证仍未完成

第一轮阻塞项要求补齐：

- CloudBase 云托管或 Web 应用托管部署成功记录。
- 部署访问地址。
- 部署环境变量配置说明。
- 部署地址上的核心闭环验证结果。

本轮新增脚本提供了 `M5_BASE_URL` 参数，但仓库和开发记录只记录：

- 默认目标为 `http://127.0.0.1:3000`。
- 可通过 `M5_BASE_URL=https://your-deploy.example.com` 指向部署地址。
- 当前仍未包含 CloudBase 托管部署配置或部署 URL，需要获得部署地址后复跑。

因此，本轮没有真实托管地址下的闭环证据。

验收影响：

- 该项继续阻塞 M5 发布前验收通过。

建议：

1. 将当前分支部署到 CloudBase 测试托管环境。
2. 记录部署方式、服务名、访问地址和环境变量配置。
3. 用 `M5_BASE_URL=<部署地址> npm run m5:http:flow` 在部署地址复跑。
4. 在报告中记录目标地址、执行命令、成功结果和异常处理。

### P1：新增 HTTP 脚本不能直接覆盖生产运行态闭环

新增脚本依赖 `/api/auth/test-login` 获取登录 Cookie。当前 `isTestLoginAllowed` 的逻辑是：

```ts
if (nodeEnv === "production") {
  return false;
}
```

这保证了生产环境无法启用临时测试登录，是正确安全行为。但 CloudBase 托管、Next 生产启动或多数部署环境通常会以 `NODE_ENV=production` 运行。这样一来，新增 HTTP 脚本在真实托管运行态很可能第一步就失败，除非：

- 部署环境明确是非生产测试运行态，并且 `NODE_ENV` 不是 `production`；或
- 项目接入正式手机号/短信登录后，脚本改为走正式认证链路；或
- 另行设计仅限测试环境的受控登录验证方式，且不会在生产环境启用。

验收影响：

- 当前脚本证明了本地开发态 HTTP API 可用，但不足以证明“生产禁用临时测试登录”与“部署地址核心闭环验证”两件事能同时成立。
- 该项继续阻塞 M5 发布前验收通过。

建议：

1. 明确 CloudBase 测试托管环境的运行态：如果 `NODE_ENV=production`，则不能继续依赖 `/api/auth/test-login` 做发布前闭环。
2. 优先接入正式登录或提供受控测试登录方案，方案必须以 `APP_ENV` / 测试环境白名单等方式与生产环境硬隔离。
3. 将 HTTP 脚本拆分或扩展为可配置认证方式，至少支持“正式登录 Cookie/Token 输入”或“测试环境专用登录”。
4. M5 第三轮复验时必须同时证明：生产环境临时测试登录不可用，托管测试环境闭环可验证。

## 5. 非阻塞观察

### 5.1 HTTP 压测结果缺少成功率和错误率明细

当前脚本输出成功 pairs 和总耗时，失败时会整体抛错退出。这对本轮判断“是否跑通”已经够用，但发布前报告最好记录更标准的压测摘要：

- 总请求数。
- 成功率。
- 错误率。
- 平均、P95 或最大响应时间。
- 关键接口失败分布。

该项不单独阻塞本轮，因为当前更大的阻塞仍是托管地址缺失和认证链路问题。

### 5.2 压测会向 CloudBase 测试集合写入验证数据

`m5:http:flow` 和 `m5:http:load` 会创建联系方式、需求、家教信息、会话、消息和交换请求。当前集合可读样本已从 0 增加到 1，说明测试库已有验证数据。

建议后续补充测试数据标识和清理策略，例如统一前缀、创建时间记录、清理脚本或测试环境重置说明。该项不阻塞 M5 第二轮，但会影响后续长期反复压测的测试库整洁度。

## 6. 阶段判定

M5 第二次代码验收：**暂不通过**。

本轮相对第一轮的实质进展：

- 新增 HTTP API route 层闭环脚本。

下一步建议：

1. 先完成 CloudBase 测试托管部署，并提供可访问 URL。
2. 明确托管环境认证方案：正式登录，或与生产硬隔离的测试登录。
3. 用部署地址复跑 `m5:http:flow` 和 `m5:http:load`。
4. 记录目标地址、运行态、环境变量配置、成功率、错误率和关键接口响应结果。
