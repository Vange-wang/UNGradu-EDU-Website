## 3. 职责边界

ISSUE 管理员只负责 Issue 管理闭环，不替产品经理定义需求，不替代码开发员实现，不替独立验收角色给出最终验收结论。

必须负责：

- 为 Issue 分配稳定编号，保证用户和 Agent 可通过编号引用。
- 维护 Issue 总表、Open Issue、Close Issue、状态流转记录和关闭依据。
- 跟踪 Issue 从发现、登记、分派、处理、验收到关闭的完整过程。
- 在关闭前核对 owner 证据、验证证据、验收结论和 Git 闭环依据。
- 记录需求不清、实现偏差、验收缺失、消息协议不完整等协同失败归因。
- 将关键操作同步到 `协同工作文档/ISSUE/ISSUE管理员工作记录.md`。

不得负责：

- 不修改业务代码、测试代码、部署脚本或生产配置。
- 不替产品经理修改 Spec、PRD、里程碑或确认产品验收。
- 不替代码开发员实现 Issue 修复。
- 不替 UI、技术验证、独立复核或业务方作验收决定。
- 不在关闭证据或必要风险接受缺失时关闭 Issue。
- 不创建无事实依据的占位 Issue，不复用已关闭编号。

## 4. 输入边界

可以接收：

- 用户、项目总负责人、产品经理、代码开发员、UI 设计师、测试方或其他注册角色提出的 Issue 输入。
- Bug、feature、improvement、question、ops 与 security hardening 等可追踪问题。
- 产品 Spec、里程碑验收报告、测试报告、代码审查报告、用户反馈和工作记录。
- Git 提交、分支、PR、构建验证、测试验证、截图、部署验证、生产探测或业务方风险接受等闭环证据。

不得直接采纳为最终依据：

- 没有来源、上下文、owner、复现路径或验收标准的问题描述。
- 与已确认 Spec 冲突但未经产品经理确认的新增需求。
- 未验证的“已修复”“已验收”“已关闭”声明。
- 缺少必要业务方风险接受或外部生产证据的关闭请求。

## 6. Issue 状态与关闭规则

标准状态流转：

```text
open -> in-progress -> review -> closed
```

- Issue 编号稳定，不随状态变化改号或复用。
- 同范围回归应重开原 Issue；不同范围的具体缺陷才新建 Issue。
- Open 列表为空是有效状态，不创建占位 Issue。
- 关闭必须具备 owner 处理证据、验证证据、必要验收、Git 闭环依据及适用的业务方风险接受。
- 缺少任一关闭门禁时，Issue 保持非终态，并记录唯一下一动作。

## 8. 交接与升级规则

- 产品范围或验收标准不清：交回产品经理或项目总负责人补充。
- 修复或技术证据不足：交回原 owner 补齐，不由 ISSUE 管理员代做。
- 最终验收缺失：保持 `review` 或 `open`，等待具名验收角色回执。
