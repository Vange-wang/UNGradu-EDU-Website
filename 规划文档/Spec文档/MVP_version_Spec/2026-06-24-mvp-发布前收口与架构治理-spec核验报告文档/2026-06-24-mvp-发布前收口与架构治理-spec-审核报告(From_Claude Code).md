# 《MVP 发布前收口与架构治理 Spec》审核报告

日期：2026-06-24

审核身份：产品经理

审核对象：`2026-06-24-mvp-发布前收口与架构治理-spec.md`（草案）

审核方式：核对该 Spec 引用的历史结论与既有验收报告是否一致；逐项核实第10节列出的 P1/P2 代码问题是否真实存在于当前仓库代码（分支 `codex/m5-security-preflight`），避免在不知道问题是否真实存在的情况下评判优先级排序是否合理。

## 1. 总体结论

这份 Spec **方向合理，定位准确，可以作为发布前收口阶段的工作依据**，不需要重写。第10节列出的全部 P1/P2 技术问题，经代码核实，**均真实存在**，不是凭空列出的假想风险，优先级排序也基本恰当。但仍有若干处需要增删补改，具体见下文，按"必须改"和"建议改"分级。

## 2. 必须改（影响 Spec 严谨性或可执行性）

### 2.1【增】第10.1节遗漏"该问题是已知模式的复发"这一关键背景

**问题**：第10.1节"聊天会话查询索引化"描述的全集合扫描风险（`conversations.ts`），经代码核实，与第三轮 M5 验收中发现并修复的`parent-needs.ts`/`tutor-profiles.ts`全集合扫描问题**是完全相同的代码模式**（`collection.where({}).get()`后内存`.filter()`）。当前`server/conversations.ts`第193行仍是这个写法，没有跟随M5第四轮的修复一起改。

**为什么要改**：这不是一个新发现的独立风险点,而是同一类缺陷在另一个集合上的复发。如果不在 Spec 里点明这一点，容易让人误以为这是M5之外的全新问题，从而：
1. 低估修复的紧迫性（这个模式已经在生产数据量下出过一次真实故障）。
2. 让开发团队重新摸索解法，而不是直接复用 M5 第四轮已经验证过的"按状态过滤+orderBy+skip/limit分页"方案。

**建议增补内容**（第10.1节"当前风险"之后）：

> 该问题与 M5 第四轮修复的 `parent_needs`/`tutor_profiles` 公开列表全集合扫描问题属于同一代码模式的复发，建议直接复用该修复方案中验证过的"按条件过滤 + `orderBy` + `skip`/`limit` 分页轮询"思路，并补充与 `parent-need-server.test.ts` 同等强度的"大量历史会话下仍能查到当前用户会话"回归测试。

### 2.2【增】第10.2节"`next`参数白名单校验"应补充当前实现细节，便于开发定位

**问题**：核实 `features/auth/login-form.tsx` 后发现，当前实现是客户端 `router.push(searchParams.get("next") ?? "/")`，直接使用 `next/navigation` 的客户端路由跳转，**没有任何字符串校验**。Spec 第10.2节的风险描述准确，但没有指出具体文件位置，增加了开发排查成本。

**建议增补**（第10.2节"当前风险"之后）：

> 当前实现位置：`features/auth/login-form.tsx`，登录成功回调中直接执行 `router.push(searchParams.get("next") ?? "/")`，未做任何校验。

### 2.3【删/改】第13节验收标准中"`npm run m5:hosted:verify`"的触发条件需要更明确

**问题**：第13节写"若涉及托管环境改动，应复跑 `npm run m5:hosted:verify` 或记录无法复跑原因与风险"。但本阶段第10节列出的多项改动（会话索引化、Cookie过期校验、API容错）本质上都是**服务端业务逻辑改动**，并不直接是"托管环境改动"（如部署配置、环境变量），但这些改动一旦合并部署，理应在托管环境复验一次，否则"代码改了、测试本地过了、但没人在托管环境验证过"的情况会重演——这正是M5前几轮反复出现的问题模式。

**建议改为**：

> 若本阶段任何改动涉及服务端业务逻辑（含会话索引化、Cookie校验、API容错等10.1-10.5节改动）或托管环境配置变更，均应在合并前复跑 `npm run m5:hosted:verify`；仅文档类交付物（产品说明、环境变量清单等）不强制要求复跑。

理由：把"是否复跑托管验证"的判断标准从"是否涉及托管环境改动"这种容易被狭义解读的措辞，改成"是否涉及服务端业务逻辑改动"，能避免开发团队以"我只是改了查询逻辑，没碰部署配置"为由跳过托管复验，重蹈此前几轮"本地测试通过≠托管环境通过"的覆辙。

## 3. 建议改（提升 Spec 质量，非必须）

### 3.1【增】第10节应明确每一项 P1/P2 的责任验证方式：单测 vs 托管复验

**观察**：第10.1-10.7节各自都有"验收标准"，但standard普遍只写"单测覆盖XX场景"，没有区分"这一项是否也需要在 `m5:hosted:verify` 链路里跑一次"。结合上面2.3的修改，建议在每一小节的验收标准末尾统一加一句：

> 修复后需随下一次 `npm run m5:hosted:verify` 一并复验。

这样可以避免出现"单测过了就直接认为该P1已关闭，但实际上从未在真实HTTP+CloudBase环境下跑过"的情况——这正是M5验收过程中反复出现并最终导致延期的问题模式，这份治理 Spec 理应主动吸收这个教训，而不是只在第13节笼统提一句。

### 3.2【补】第12.1节"公开列表分页上限"的技术债描述可以更精确

**观察**：第12.1节说"当前策略最多读取约1000条近期公开记录"，这个数字经核实（`RECENT_PUBLIC_QUERY_LIMIT = 100` × `RECENT_PUBLIC_QUERY_MAX_PAGES = 10`）准确无误,不需要改动数字本身。但建议补充一句触发条件，让后续读者不需要去翻代码就能理解风险边界：

> 当 `status=published` 的有效记录数超过约1000条时，最早发布且仍在分页窗口之外的记录可能不再出现在公开列表中；这不是"近期发布的新记录丢失"问题（M5第四轮已修复该场景），而是"非常旧的历史记录在数据量很大时逐渐从公开列表退出"的预期行为，需要在 vNext 阶段明确这是否是期望的产品行为（类似"只展示近期活跃发布"）还是必须支持完整历史回溯。

理由：当前措辞容易让人以为"M5修复后这个问题就只是个数字上限"，但更准确的说法是——修复后的方案本质上变成了"近期发布优先展示"模型，这本身可能是合理的产品设计（类似大多数信息广场类产品的"只看近期"逻辑），但需要产品侧确认这是不是预期行为，而不仅仅当作技术债来填。

### 3.3【建议增】第9节"正式生产禁用测试登录确认"可以增加一条关于`AUTH_SESSION_SECRET`轮换场景的确认项

**观察**：第9节确认项里有"生产 `AUTH_SESSION_SECRET` 已配置，且不是测试环境密钥"，但没有提到——如果生产密钥未来需要轮换（例如怀疑泄露），轮换后所有已签发的会话Cookie会全部失效，需要用户重新登录。结合第10.4节新增的"Cookie服务端硬过期校验"，建议在第9节补充一条：

> 若后续轮换 `AUTH_SESSION_SECRET`，需提前告知是否会导致全部在线用户被强制登出，并评估轮换时机。

这条不是阻塞项，但属于"上线后才会被发现的运营细节",提前写进确认清单可以避免临时手忙脚乱。

### 3.4【建议改】第14节交付物清单可以补充"代码架构问题修复对照表"

**观察**：第14节列出的交付物都是面向运营/产品的文档，但第10节列出7项代码架构问题，目前没有一个单独的交付物来跟踪"哪一项P1/P2在哪个commit修复、是否已托管复验"。考虑到M5阶段几轮验收报告的经验——逐项可追溯的对照记录对后续复核非常重要，建议在第14节交付物清单中补充：

> - `规划文档/里程碑文档/发布前准备/架构收口问题修复对照表.md`（记录第10节每项P1/P2对应的修复提交号、单测覆盖情况、是否已通过`m5:hosted:verify`复验）

## 4. 未发现问题的部分（确认无需改动）

以下内容经核实，判断准确，不建议改动：

- 第2节"不重新定义M1-M5业务范围"的定位准确，与历次M5验收报告的范围边界一致。
- 第4.2节"本阶段不包含"的列表与历次报告中反复确认的vNext范围（支付、评价、审核后台等）完全对应,没有范围蔓延。
- 第10.3节反馈入口问题——核实`app/feedback/page.tsx`后确认页面确实只有纯文案、无任何可执行渠道（无`mailto:`、无表单），描述准确。
- 第10.6节登出入口问题——核实`app/profile/page.tsx`和`app/layout.tsx`后确认界面上确实找不到"退出登录"相关文案或按钮，描述准确。
- 第10.4节Cookie硬过期校验问题——核实`server/auth-session.ts`后确认服务端读取会话时只验证签名和字段完整性,完全没有基于`createdAt`的时间窗口判断,描述准确。
- 第15节风险说明的四条风险陈述与前序验收报告的判断口径一致，没有夸大或缩小。
