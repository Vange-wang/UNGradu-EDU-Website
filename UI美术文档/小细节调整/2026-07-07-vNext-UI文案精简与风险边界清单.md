## 2. 总体清理原则

### 2.1 必删文案类型

- 内部设计术语：`Step Form`、`Workspace`、`Dashboard`、`Contact Exchange`、`D+`、`MVP`、`任务分组`、`状态区` 等不应出现在用户可见页面。
- 技术解释：例如“自动轮询刷新”“证明文件只记录当前已有元信息”“保留原有字段”“不改变提交结构”“文件名、类型和大小”。
- 页面功能自述：例如“这个页面用于...”“当前仅保存...能力”这类对普通用户没有行动价值的说明。
- 重复说明：同一屏中反复出现“公开页不展示联系方式”“双方同意后交换”，应保留一次强提示，其他位置压缩或删除。

### 2.2 可压缩文案类型

- 流程说明：保留下一步动作即可，不展开解释后台流程。
- 表单帮助文字：改成短句，优先放在字段 placeholder 或单行提示里。
- 风险提示：保留关键边界，但从长段落压缩为短句或 2-3 个要点。
- 空状态：保留行动引导，不解释页面结构。

### 2.3 必保留文案类型

- 隐私边界：公开页不展示联系方式，联系方式仅在双方同意并二次确认后展示。
- 联系方式安全：不要在公开说明、聊天消息、反馈中直接提交手机号、微信号、详细地址、证件、支付凭证。
- 未成年人保护：涉及孩子 / 学生时，只写学习情况和大致上课安排，不写精确住址或敏感身份信息。
- 付款和交易边界：平台当前不做支付、担保、抽佣、退款、合同。
- 平台能力边界：平台不提供认证、资质保证、人工仲裁、即时客服承诺。
- 风险反馈边界：反馈仅用于记录和排查，不承诺即时处理或人工介入。

## 3. 页面级清单与替换建议

### 3.1 首页 `/`

必删：

- 删除或替换用户可见的 `MVP` 口径，如“当前版本”区块内若出现 `MVP`、内部阶段名，一律改为用户能理解的“试运行”或直接删除。
- 删除重复的流程解释。首页已在 hero、流程区、平台边界区多次说明“发布 / 筛选 / 站内沟通 / 交换联系方式”，应减少重复。

可压缩：

- `家长发布需求，大学生展示家教资料。公开页面不展示联系方式，双方先站内沟通，确认同意后再交换。`
  建议改为：`先发布需求或资料，再站内沟通；双方确认后才交换联系方式。`
- `填写学段、科目、预算和上课偏好，先把需求讲清楚。`
  建议改为：`填写科目、预算和上课偏好。`
- `展示可教科目、时间和课时费范围，公开页不放联系方式。`
  建议改为：`填写可教科目、时间和课时费。`
- 流程区标题 `需求 / 家教 / 沟通 / 同意后交换`
  建议改为：`发布、沟通、确认`

必保留：

- `公开页不展示联系方式`
- `交换前二次确认`
- `不做支付、担保、认证或人工仲裁`
- `风险反馈仅记录排查`

开发员执行建议：

- 首页 hero 保留 1 句主说明、2 个身份入口、2-3 个边界标签即可。
- 删除后检查首屏右侧状态面板是否出现大块空白；如空，应让边界标签更紧凑排列，而不是补长文案。

### 3.2 登录页 `/login`

必删：

- 不要出现“手机号登录”“第三方认证已接入”等未确认口径。

可压缩：

- `当前仅支持邮箱验证码登录或注册；设置密码后，也可以使用邮箱和密码登录。这里不提供实名认证或第三方认证入口。`
  建议改为：`使用邮箱验证码登录或注册；设置密码后可用邮箱密码登录。`
- `登录后再发布、筛选和站内沟通`
  建议改为：`登录后继续发布和沟通`
- `首次验证码登录会创建账号`
  建议保留，可改为：`首次验证码登录即创建账号`
- `登录后可补充联系方式`
  建议保留，但与下一条合并：`登录后可补充联系方式，交换仍需双方确认`
- `联系方式交换仍需双方确认`
  建议与上一条合并，避免三枚标签过挤。

必保留：

- 登录方式为邮箱验证码 / 邮箱密码。
- 未提供实名认证或第三方认证入口的边界可保留，但不必放在首屏大段说明中，可放为短提示：`暂不提供实名认证或第三方认证。`
- 联系方式交换仍需双方确认。

开发员执行建议：

- 登录页说明控制在 2 行内。
- 移动端登录卡片上方不要堆 3 个以上说明标签，避免表单被挤到首屏下方太深。

## 5. UI 验收标准

代码开发员按本清单实现后，UI 设计师建议按以下标准复核：

- 桌面端和移动端均不出现横向滚动、文字出框、按钮变形、输入框被挤压。
- 删除说明文字后，页面仍能理解下一步：用户知道该发布、登录、返回、提交、保存、发送或请求交换联系方式。
- 按钮、字段、卡片没有明显空洞；如删掉长文后出现空白，应调整间距或卡片布局，而不是补回解释性长文。
- 首页、登录页、规则页、反馈页首屏不被说明文字占满。
- 发布需求页、发布家教信息页移动端表单优先可填，侧栏 / 步骤说明不能压过字段。
- 联系方式页移动端先看到隐私边界和表单，不出现重复说明卡堆叠。
- 聊天页移动端消息区、输入区、交换联系方式区不互相挤压。
- 不出现 `Step Form`、`Workspace`、`Dashboard`、`Contact Exchange`、`MVP`、`D+` 等内部术语。
- 必须保留隐私、联系方式、未成年人、付款、平台不担保 / 不认证 / 不仲裁等安全边界。

## 6. 是否允许代码开发员按清单实现

从 UI 设计职责判断：允许代码开发员在收到产品经理允许实现后，按本清单执行 UI 文案删除、压缩和替换。

限制条件：

- 代码开发员不得把本清单理解为新增产品能力。
- 不得新增支付、担保、认证、人工客服、仲裁、退款、合同、自动推荐等未确认能力。
- 不得删除隐私、联系方式、未成年人、付款和平台边界类关键安全提示。
- 涉及 `/feedback` 是否改为站内表单、最小字段和记录方式，应以产品经理输出为准。
