### 2.2 POST /api/auth/sms/send-code 验证码安全

**审查文件**：
- `Code文档/app/api/auth/sms/send-code/route.ts`
- `Code文档/server/sms-auth.ts`（`sendSmsLoginCode` 函数）
- `Code文档/server/sms-delivery.ts`
- `Code文档/server/sms-auth-api.ts`（`POST_SEND_CODE` 函数）

**审查结论：✅ 通过。**

**证据**：

1. **服务端生成验证码**（`sms-auth.ts` 第 96-98 行）：
   - `generateSixDigitCode()` 使用 `randomInt(100000, 1000000)` 生成真随机 6 位数字。
   - 经过 `normalizeGeneratedCode` 归一化，拒绝 `000000`。

2. **验证码哈希存储**（`sms-auth.ts` 第 78-94 行）：
   - `hashCode` 函数使用 HMAC-SHA256，密钥为 `SMS_CODE_SECRET`，输入为 `${phone}:${code}`。
   - 只有哈希值 `codeHash` 被写入数据库（`sms-auth.ts` 第 198-206 行），验证码明文不持久化。
   - 生产环境无 `SMS_CODE_SECRET` 时返回 `null`（第 73 行），非生产环境使用开发占位密钥（第 75 行）。

3. **不泄露验证码**（`sms-auth-api.ts` 第 44-63 行）：
   - `POST_SEND_CODE` 返回的响应只包含 `expiresInSeconds`、`phoneMasked`、`resendAfterSeconds`。
   - 不返回验证码明文，不返回 `codeHash`。
   - 返回的手机号已脱敏（如 `138****8000`）。

4. **SMS 发送在服务端完成**（`sms-delivery.ts` 第 60-143 行）：
   - 腾讯云短信 API v3 签名（TC3-HMAC-SHA256）完全在服务端计算。
   - `TENCENTCLOUD_SECRETID` 和 `TENCENTCLOUD_SECRETKEY` 只从 `process.env` 读取，绝不出现在前端代码。
   - 发送失败时返回 `{ ok: false, error: "SmsSendFailed" }`，不向客户端暴露腾讯云内部错误详情。

5. **测试验证**（`tests/sms-auth.test.ts` 第 99-113 行）：
   - 测试明确断言：响应 JSON 不包含验证码明文（`"123456"`），不包含完整手机号（`"13800138000"`）。
   - 测试明确断言：即使代码生成器返回 `000000`，实际发送的也不是 `000000`（第 116-124 行）。

**业务方可读说明**：验证码是由系统在服务端随机生成的，生成后立即哈希加密保存。网页和接口响应里不会泄露验证码是什么。发送短信的腾讯云密钥只存在服务器环境变量里，不会出现在网页代码或 Git 仓库中。

### 2.3 POST /api/auth/sms/login 校验与会话安全

**审查文件**：
- `Code文档/app/api/auth/sms/login/route.ts`
- `Code文档/server/sms-auth.ts`（`verifySmsLoginCode` 函数）
- `Code文档/server/sms-auth-api.ts`（`POST_LOGIN` 函数）
- `Code文档/server/auth-session.ts`

**审查结论：✅ 通过。**

**证据**：

1. **新手机号自动创建账号**（`sms-auth.ts` 第 295-311 行）：
   - 验证码通过后查询 `userCollection`，若不存在则创建新 `SmsUserDocument`。
   - 新账号字段：`userId = user_<phoneHash 前 24 位>`、`status: "active"`、`createdAt`、`lastLoginAt`。

2. **老手机号复用账号**（`sms-auth.ts` 第 313-316 行）：
   - 已有用户直接更新 `lastLoginAt`，保留原来的 `userId`、`createdAt`。
   - 测试 `sms-auth.test.ts` 第 206-267 行验证了：同一手机号第二次登录后 `userId` 和 `createdAt` 与第一次相同。

3. **禁用账号拦截**（`sms-auth.ts` 第 300-302 行）：
   - 如果 `existingUser.status === "disabled"`，返回 403 "账号暂不可用，请联系平台处理"。

4. **服务端签名会话 Cookie**（`sms-auth-api.ts` 第 86-110 行）：
   - 登录成功后调用 `createAuthSessionCookie({ env, phone })` 生成 Cookie。
   - 响应包含 `set-cookie` 头，设置 `ungradu_auth_session` Cookie。

5. **Cookie 安全属性**（`auth-session.ts` 第 73-98 行）：
   - `HttpOnly`：前端 JavaScript 无法读取 Cookie，防止 XSS 窃取。
   - `SameSite=Lax`：防止 CSRF 跨站请求携带 Cookie。
   - `Path=/`：全站可用。
   - `Max-Age=604800`（7 天）。
   - 生产环境增加 `Secure` 标志（仅 HTTPS 传输）。
   - 签名算法：HMAC-SHA256，密钥为 `AUTH_SESSION_SECRET`，签名使用 timing-safe 比较防止时序攻击。

6. **响应不泄露完整手机号**（`sms-auth-api.ts` 第 95-109 行）：
   - 登录成功响应只返回 `phoneMasked`（脱敏手机号）、`userId`、`createdAt`、`lastLoginAt`。
   - 完整手机号仅存在于 HttpOnly Cookie 的加密 payload 中，前端 JS 不可读。

**业务方可读说明**：用户第一次用手机号验证码登录时，系统自动创建账号（等于注册）。以后再用同一个手机号登录，会回到原来的账号。登录后系统给浏览器发一个加密签名的 Cookie，这个 Cookie 前端脚本拿不到（防止黑客通过网页漏洞偷走），后续所有需要登录才能用的功能都靠这个 Cookie 识别用户身份。

**审查文件**：`Code文档/server/sms-auth.ts`

| 错误次数限制 | `sms-auth.ts:14, 265-285` | 5 次 | `MAX_VERIFY_ATTEMPTS = 5`，超过后返回 429 "验证码错误次数过多，请重新获取" |

**测试覆盖**（`tests/sms-auth.test.ts`）：

- 第 126-137 行：60 秒内重复发送被频控（429）。
- 第 140-156 行：错误验证码 5 次后锁定（429）。
- 第 158-203 行：过期验证码被拒绝（400）。
- 第 206-267 行：验证码使用后不可复用（400），新老账号正确创建/复用。
- 第 297-308 行：SMS 登录接口拒绝 `000000`。

**业务方可读说明**：验证码有 5 分钟有效期；60 秒内不能重复发送；输错 5 次验证码后这条验证码就作废了，需要重新获取；每条验证码只能用一次，用过了就不能再用。这些规则都是为了保护用户账号安全，防止有人暴力试码或滥用短信发送。

   - `GET /api/auth/session`（`auth-api.ts` 第 23-39 行）：调用 `readAuthSessionFromRequest` 从 Cookie 中解析并验签会话。
   - `readAuthSessionFromRequest`（`auth-session.ts` 第 105-159 行）：解析 Cookie、验证 HMAC 签名（timingSafeEqual）、检查 `createdAt` 未过期且非未来时间。
   - **每个页面刷新都会重新验证**，不需要 localStorage 或前端存储任何会话信息。

2. **退出登录清除会话**：
   - `logout-button.tsx`（第 10-25 行）：调用 `POST /api/auth/logout`。
   - `POST /api/auth/logout`（`auth-api.ts` 第 93-101 行）：返回 `clearAuthSessionCookie()` 设置的 Cookie。

   - 退出后执行 `router.push("/")` 和 `router.refresh()`，页面回到首页。

3. **退出后不能访问私有数据**：
   - 所有私有 API（联系方式、我的需求、我的家教信息、聊天等）通过 `readAuthenticatedUserId` 获取用户身份。
   - `readAuthenticatedUserId`（`api-utils.ts` 第 32-74 行）：
     - 先读 Cookie → 已清除 → 返回 `null`。
     - 再尝试 `x-ungradu-test-user-phone` 头 → 生产环境拒绝。
     - 最终返回 401 "Login is required for this API."。

4. **测试验证**（`tests/sms-auth.test.ts` 第 269-295 行）：
   - 登录后能从 Cookie 中读回 `phone: "13800138000"`。
   - 无 Cookie 时调用私有 API（`GET /api/contact-profile`）返回 401。

**业务方可读说明**：用户登录后，7 天内刷新页面或关闭浏览器再打开，只要 Cookie 还在就能自动识别身份，不需要重新登录。点"退出登录"后，浏览器 Cookie 被清除，再访问个人页面或聊天会被拦截并要求重新登录。这个 Cookie 是加密签名的，前端脚本拿不到也改不了。

### 2.8 产品经理三项风险复核

#### 2.8.1 `RequireTestSession` 命名遗留

**Zcode 判断：同意产品经理结论，风险归类 P2 合理。**

**复核证据**：
- `features/auth/require-test-session.tsx`：组件名 `RequireTestSession`，类型名 `RequireTestSessionProps`。
- `features/auth/use-test-session.ts`：hook 名 `useTestSession`，返回类型引用 `TestSession`。
- **但实际行为**：`useTestSession` 调用 `GET /api/auth/session`（第 28 行），读取的是服务端签名 Cookie 的正式会话，**不是** M1 测试登录的 localStorage 会话。
- `RequireTestSession` 也是基于 `useTestSession` 的结果做路由守卫——同样读的是正式会话。

**风险分析**：
- 名称中 `Test` 字样容易让后续协作者误以为这是测试/临时能力，可能被误删或误改。
- 不影响当前真实的登录流程——无论叫什么名字，读的都是同一个 `/api/auth/session`。
- **建议**：后续迭代时将 `RequireTestSession` → `RequireAuthSession`、`useTestSession` → `useAuthSession`、`TestSession` → `AuthSession`。不影响本阶段验收。

#### 2.8.2 手机号承接既有业务身份

**Zcode 判断：同意产品经理结论，风险归类合理。**

**复核证据**：
- `auth-session.ts`：Cookie payload 中保存的是 `phone`（手机号）。
- `api-utils.ts` 第 41 行：`authenticatedUserId: session.phone`——业务 API 的用户标识是手机号。
- 所有现有的 CloudBase 数据（`contact_profiles`、`parent_needs`、`tutor_profiles`、`conversations`、`messages`）都以手机号作为 `ownerUserId` 或参与者标识。
- 新增的 `userId`（`user_<phoneHash24>`）只在 `sms_login_users` 集合中使用，尚未推广到其他业务数据。

**风险分析**：
- 当前设计能兼容已有的家长、老师、需求、聊天等全部业务数据，不会造成数据断裂。
- 手机号作为用户标识在换绑手机号场景下有局限性（目前 MVP 不涉及换绑）。
- 后续若要支持换绑手机号、实名认证或多身份聚合，需要从手机号主标识迁移到稳定 `userId`。
- **建议**：后续账号体系迭代时规划迁移。不影响本阶段验收。

#### 2.8.3 真实短信未在生产 URL 冒烟

**Zcode 判断：同意产品经理结论，属于外部配置与生产验收风险。**

**复核证据**：
- 仓库内代码已包含完整的短信发送适配器（`sms-delivery.ts`）、验证码生成与校验（`sms-auth.ts`）、API 路由（`send-code/route.ts`、`login/route.ts`）。
- 测试环境使用 fake 短信发送器，所有逻辑测试均可通过。
- 但真实短信能否送达，取决于：
  - 腾讯云短信账号是否已开通且有余额。
  - 短信签名是否已审核通过。
  - 短信模板是否已审核通过。
  - CloudBase 生产环境变量是否正确注入（`TENCENTCLOUD_SECRETID`、`TENCENTCLOUD_SECRETKEY`、`TENCENT_SMS_APP_ID` 等）。
  - 生产 URL 是否可正常访问且 HTTPS 配置正确。
  - 端到端冒烟（输入手机号 → 收到短信 → 输入验证码 → 登录 → 刷新 → 退出）是否全部通过。

**风险分析**：
- 仓库内代码侧已具备短信登录闭环，代码本身无需返工。
- 但缺乏外部配置和生产冒烟验证，就不能宣布"正式环境用户可以正常登录"。
- **必须动作**：项目总控制人完成腾讯云短信和 CloudBase 生产环境变量配置，并在正式 URL 完成真实短信登录冒烟后，才能对外宣布生产登录完成。
