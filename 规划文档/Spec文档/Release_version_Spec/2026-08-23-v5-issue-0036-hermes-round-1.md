- **位置**：§1.2 第 26 行 vs §1.3 第 46 行

- **影响**：该文件正是文档用来“固定 ISSUE-0036 为 `open / USER_CONFIRMATION_PENDING` 且不改状态”的 canonical 状态来源。哈希矛盾意味着：(a) 若为笔误，下游执行者/复核者将无法以精确哈希复现权威内容，触发 UPSTREAM_GATE_BLOCKED 或绑定错误内容；(b) 若文件在两次读取间被改动，则文档未披露这一材料事件，§1.1 的 canonical 状态结论可能与 §1.3 绑定内容漂移。无论哪种，都动摇整篇文档赖以成立的“精确 SHA-256 绑定”方法论。
- **修正/关闭触发**：重新读取该文件并重算哈希，确定唯一权威值并在两处统一；若文件确实发生变化，须显式说明变更及其对 §1.1“canonical 状态不变”结论的影响。修复后由后续轮次复核。

## Non-Serious Findings

### N-001 — §5.2 冻结状态机未穷举快乐路径与已发布内容编辑/删除的转移

- **位置**：§5.2 第 134 行 vs §2.3 第 81 行
- **证据**：第 134 行显式列出的转移仅覆盖申诉（`rejected → appeal_pending → needs_manual_review → published/rejected`）、编辑后重审（`rejected → draft → pending_review`）和删除恢复（`deleted → pending_review`）。但 §2.3 第 3 项要求“已发布内容编辑、删除、恢复和申诉都会重新经过适用审核”，且 §5.2 表暗示存在 `draft → pending_review`（提交）、`pending_review → published/rejected`（授权决定）、`published → draft`（编辑）、`published → deleted`（删除）等路径，这些未在冻结转移枚举中显式写明。
- **影响**：状态机实现者可能对快乐路径和已发布内容编辑/删除的转移规格理解不足，产生实现缺口。
- **修正**：补全冻结转移表，显式列出所有允许转移（含进入 `deleted` 的前驱状态），或明确交叉引用其定义位置。

### N-002 — `pending_review` 与 `needs_manual_review` 语义边界重叠

- **位置**：§5.2 第 120 行 vs 第 126 行
- **证据**：第 120 行定义 `pending_review`=“等待确定性/自动审核”，`needs_manual_review`=“需要人工决定，均不得公开”。但第 126 行 `allow_candidate → pending_review` 的约束是“后续经授权审核决定才可 published”。`allow_candidate` 已是确定性规则的输出，却仍映射回“等待确定性/自动审核”的 `pending_review`，且两者最终都需授权决定才能公开。
- **影响**：实现者/测试者难以区分两个队列的实操差异（例行审核 vs 升级审核），可能影响队列路由与验收断言。
- **修正**：明确二者的操作性区别（如 `pending_review`=无联系方式信号、走例行授权；`needs_manual_review`=有信号/歧义/失败、走重点人工），或合并。

### N-003 — 自我冻结哈希与 AUTHOR_FROZEN 标签尚未对齐

- **位置**：第 3 行（元数据）vs 第 48 行
- **证据**：第 3 行声明 `AUTHOR_FROZEN`；第 48 行却写本稿自身冻结源 SHA-256 是“写前快照”（17488 bytes / 198 lines，而实际为 20843 bytes / 217 lines），且“本次冻结修改后以新的源 hash 作为 Hermes 绑定”——即最终绑定哈希尚待重算。
- **影响**：冻结标签与绑定哈希未同步，HERMES 门禁若直接采信现有哈希会绑定到错误快照。
- **修正**：定稿后重算并回填第 48 行的最终源 SHA-256 与字节/行数，再进入 HERMES 复核。
