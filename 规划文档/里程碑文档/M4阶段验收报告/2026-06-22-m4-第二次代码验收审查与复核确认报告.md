## 4. 第一轮 P0 复验：未授权前不再返回手机号

第一轮问题：

- `SavedConversation` 直接暴露 `participantPhones`。
- `SavedContactExchangeRequest` 直接暴露 `requesterPhone`、`receiverPhone`。
- 聊天页和我的聊天页把这些完整对象放入 React state，用户在授权前即可通过浏览器开发者工具看到对方手机号。

本轮修复确认：

- `Code文档/features/chat/chat-storage.ts` 将内部存储类型与对外返回类型拆分。
- 内部仍使用 `StoredConversation`、`StoredConversationMessage`、`StoredContactExchangeRequest` 保存参与者手机号，用于当前本地测试阶段的权限判断。
- 对页面和测试暴露的类型改为脱敏视图。

对外返回类型现在为：

```ts
export type SavedConversation = {
  id: string;
  sourceId: string;
  sourceType: ConversationSourceType;
  createdAt: string;
};

export type SavedConversationMessage = {
  id: string;
  conversationId: string;
  direction: "sent" | "received";
  text: string;
  createdAt: string;
};

export type SavedContactExchangeRequest = {
  id: string;
  conversationId: string;
  direction: "sent" | "received";
  status: ContactExchangeRequestStatus;
  secondConfirmedAt: string | null;
  createdAt: string;
  updatedAt: string;
};
```

关键实现：

- `toConversationView` 只返回 `id`、`sourceId`、`sourceType`、`createdAt`。
- `toMessageView` 将 `senderPhone` 与当前用户手机号比较后转为 `direction`，返回值不含手机号。
- `toContactExchangeRequestView` 将 `requesterPhone` / `receiverPhone` 转为 `direction`，返回值不含手机号。
- `createOrReadConversation`、`readConversationForUser`、`readConversationsForUser`、`sendConversationMessage`、`listConversationMessages`、`createContactExchangeRequest`、`approveContactExchangeRequest`、`rejectContactExchangeRequest`、`withdrawContactExchangeRequest`、`listContactExchangeRequestsForConversation` 均返回脱敏视图。
- `readAuthorizedContactProfiles` 只在存在已同意且完成二次确认的请求后返回双方存档联系方式。

前端消费层复核：

- `app/chats/[id]/page.tsx` 中消息方向判断已从 `message.senderPhone === currentUserPhone` 改为 `message.direction === "sent"`。
- 联系方式交换请求操作判断已从比较 `request.receiverPhone` / `request.requesterPhone` 改为 `request.direction === "received"` / `request.direction === "sent"`。
- `app/profile/chats/page.tsx` 虽未在本轮直接修改，但其调用的 `readConversationsForUser` 已在存储层统一返回脱敏视图，因此聊天列表 state 不再含 `participantPhones`。

测试确认：

- `tests/chat-storage.test.ts` 已补充断言：创建/读取会话返回对象不包含双方手机号。
- 消息列表返回对象不包含对方手机号。
- 联系方式交换请求列表返回对象不包含发起方手机号。

复验结论：第一轮 P0 已关闭。

## 5. 第一轮 P1 复验：聊天页已增加 3 秒轮询

第一轮问题：

- 聊天页只在页面加载和当前用户发送/处理请求后手动刷新。
- 对方在另一个页面发送新消息后，当前页面不会在 5 秒内自动看到新消息。

本轮修复确认：

- 新增 `Code文档/features/chat/chat-polling.ts`：

```ts
export const CHAT_POLLING_INTERVAL_MS = 3000;
```

- `Code文档/app/chats/[id]/page.tsx` 中新增轮询：

```ts
useEffect(() => {
  const intervalId = window.setInterval(refresh, CHAT_POLLING_INTERVAL_MS);

  return () => window.clearInterval(intervalId);
}, [refresh]);
```

这意味着聊天页在加载后每 3 秒重新读取当前会话、消息、交换请求和授权联系方式。对方写入新消息后，在当前本地测试模型下，当前聊天页最多约 3 秒会刷新展示，满足 Spec 中 5 秒内看到新消息的 M4 验收要求。

测试确认：

- `tests/chat-polling.test.ts` 已断言 `CHAT_POLLING_INTERVAL_MS` 大于 0 且不超过 5000。

复验结论：第一轮 P1 已关闭。

## 8. 非阻塞观察

### 8.1 本地存储内部仍使用手机号作为参与者标识

本轮修复已经确保页面可见返回对象不含对方手机号，但当前本地测试存储内部仍使用 `participantPhones`、`requesterPhone`、`receiverPhone` 来完成参与者判断和联系方式授权判断。

在当前 M4 本地测试阶段，这可以接受；但 M5 或接入 CloudBase 时，必须进一步将该策略升级为后端可信用户 ID、数据归属校验和接口过滤，不能把本地存储内部模型原样带入生产。

### 8.2 轮询测试覆盖的是时间常量，不是组件级自动刷新

`tests/chat-polling.test.ts` 目前验证了轮询间隔不超过 5 秒；实际自动刷新行为通过 `app/chats/[id]/page.tsx` 中的 `setInterval(refresh, CHAT_POLLING_INTERVAL_MS)` 代码审查确认。

这不阻塞 M4 第二轮验收，但建议 M5 或端到端测试阶段补充浏览器级验证：一方写入消息后，另一方停留在聊天页无需手动刷新即可看到新消息。
