## SERIOUS 发现

### S-001 — 申诉流程在状态机中未充分指定

- **严重程度**：严重
- **位置**：§6.1 状态图（第 227–232 行）；§6.2.1 允许/禁止转换（第 258–272 行）；第 265 行提及申诉
- **证据**：
  - 状态图（第 227–232 行）将转换建模为：`rejected → draft`（用户修改后重新提交）。**未出现** `rejected → needs_manual_review` 这一转换。
  - 第 265 行指出“申诉进入 `draft` 或 `needs_manual_review`”——暗示两条路径，但未说明各自触发条件。
  - 第 216 行将“申诉”列入人工审核队列项。
  - 第 262–263 行允许 `needs_manual_review → rejected`（人工裁决），但未指定用户对被拒人工裁决的申诉是否重新进入 `needs_manual_review`，也未说明申诉是否需要修改内容。
- **影响**：
  - 核心用户流程存在歧义：用户不同意自动拒绝时，是必须修改并重新提交（`draft`），还是可以无需修改进行申诉（`needs_manual_review`）？
  - 实现人员无法在没有臆测的情况下对申诉进行编码——可能会导致申诉绕过审核（即 `rejected → published`）或造成无限循环。
  - 申诉 SLA（队列延迟、响应时间、二审要求）完全缺失——而正常的审核队列 SLA 已在 §9 中定义。
- **修正**：将以下内容加入 §6：
  1. 显式状态转换：`rejected → appeal_pending` → 人工审核 → `needs_manual_review`（然后 `published` 或再次 `rejected`）。
  2. 触发条件：若用户**未**修改内容即发起申诉 → `needs_manual_review`；若用户修改内容 → `draft → pending_review`（与当前路径一致）。
  3. §9 中应新增申诉 SLA（建议：入队 p95 ≤ 30 分钟，裁决 p95 ≤ 4 小时，或明确标注“待业务方确认”）。
  4. 将 `rejected → needs_manual_review` 加入 §6.2.1 的“允许转换”列表，并添加“申诉”的触发条件。
- **后续关闭条件**：状态图、允许转换列表与 §9 SLO 表中均出现显式申诉转换；触发条件以文字形式记录。

### S-002 — 申诉缺乏滥用/速率限制

- **严重程度**：严重
- **位置**：§6.1（第 239 行起）；§8（第 299 行起）
- **证据**：
  - 第 294 行对**队列重试**定义了有限次数与退避（“队列重试采用有限次数和退避；超限转人工”）。但未对**用户发起的申诉**指定等效保护。
  - 申诉将内容直接路由至人工队列（§6，第 216 行）。恶意或脚本化用户可通过反复申诉同一内容占用人工审核资源，形成拒绝服务攻击。
  - 无论人工审核 SLA（§9，第 354 行）如何，系统都必须在申诉源头进行防护——否则 SLA 将不可强制执行。
- **影响**：
  - 操作风险：无限制申诉可耗尽人工队列容量，使合法审核无限期延迟。
  - 安全风险：攻击者可通过反复对同一内容进行申诉探测来观察审核模式（枚举抗性）。
- **修正**：在 §6 或 §8 中新增申诉速率限制规则。建议：同一实体在 24 小时内最多申诉 1 次；申诉不改变内容时需附带原因码；同一 `contentHash` 被维持原决定的比例超过阈值（如 3 次）后自动维持原决定并仅追加审计，不再重新排队。将该限制加入 §9 SLO 表或 §10 验收清单。
- **后续关闭条件**：文档中以文字形式明确记录申诉速率限制与滥用边界；§9 或 §10 中将其作为可测试条件体现。
