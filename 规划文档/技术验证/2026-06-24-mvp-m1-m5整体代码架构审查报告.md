## 1. 总体结论

M1-M5 当前代码框架整体合理，可以维持 MVP/M5 验收通过结论。

当前代码已经从早期纯浏览器 `localStorage` MVP，演进为：

- Next.js App Router 页面层。
- `features/*` 业务领域模块。
- `server/*` 服务端业务逻辑和 CloudBase 数据访问。
- `app/api/*` Next API route 作为可信接口边界。
- HttpOnly 签名 Cookie 登录态。
- CloudBase 服务端 SDK 数据读写。
- Vitest 单元测试、服务端流程测试、HTTP flow/load 脚本、托管环境复验脚本。

这套结构已经能支撑 MVP 的核心闭环：

1. 家长发布找老师需求。
2. 大学生发布家教资料。
3. 双边广场公开展示和筛选。
4. 详情页发起站内会话。
5. 双方文字聊天。
6. 双方同意并二次确认后交换联系方式。
7. 服务端校验归属、权限和联系方式保护。
8. CloudBase 测试托管环境完成真实 HTTP flow 和 50 虚拟用户 load 复验。

但该结论只代表测试托管环境下的 MVP/M5 代码验收通过，不等同于正式生产发布已经准备完成。正式上线前仍建议先处理本报告列出的 P1 项，尤其是会话查询索引化、登录跳转参数校验、反馈入口可执行化。

## 2. 当前代码架构判断

### 2.1 分层结构

当前代码分层基本清晰：

| 层级 | 主要目录 | 评价 |
| --- | --- | --- |
| 页面与路由 | `app` | 覆盖首页、登录、个人页、发布页、广场、详情、聊天、规则、反馈和 API route，路由结构符合 MVP 业务流程。 |
| 领域模块 | `features/auth`、`features/profile`、`features/parent-needs`、`features/tutor-profiles`、`features/chat` | 业务对象边界基本清晰，命名围绕登录、联系方式、需求、老师资料、聊天和联系方式交换展开。 |
| 服务端业务 | `server` | M5 后新增可信服务端逻辑，承担权限、归属、脱敏、CloudBase 读写和业务状态流转。 |
| 通用工具 | `lib` | 仍保留浏览器存储和测试存储工具，用于兼容早期 M1-M4 本地阶段和测试。 |
| 测试与脚本 | `tests`、`scripts` | 覆盖领域校验、服务端权限、M5 flow/load、托管复验等关键路径。 |
| 部署配置 | `Dockerfile`、`.env.example` | 已支持 CloudBase Run 测试托管，构建期占位变量和运行期密钥边界有文档说明。 |

总体看，M5 的服务端化改造是正确方向：权限和敏感数据保护已经从“前端约定”转为“服务端可信边界”。

### 2.2 范围控制

当前代码没有明显越界塞入支付、评价、复杂排课、合同、自动推荐、举报封禁后台、第三方 IM SDK 等后续功能。MVP 保持在自助撮合闭环，符合 Spec 和里程碑边界。

### 2.3 主要技术债性质

当前遗留问题更多是上线前收口和增长前扩展性问题，不是推翻架构的问题：

- 部分 API 查询仍偏 MVP 简化实现。
- 部分页面仍有占位性质。
- 浏览器端错误处理和真实生产登录体系尚未完整。
- 旧 localStorage 代码仍存在，但已经不是 M5 主路径。

## 4. 新发现或需要重新定级的问题

### P1：聊天会话查询仍是全集合扫描

位置：

- `Code文档/server/conversations.ts`
- `readAllConversations()` 中使用 `conversationsCollection.where({}).get()`
- `createOrReadServerConversationFromSource()` 和 `listServerConversationsForUser()` 依赖该全量读取结果做筛选和去重

风险：

- 数据量增长后，CloudBase 单次查询上限可能导致会话漏读。
- 同一来源对象和同一双方用户可能因为漏读旧会话而重复创建会话。
- 用户个人聊天列表可能缺少历史会话。
- 性能会随集合增长线性变差。

建议：

- 新增可索引字段，例如 `participantKey`、`sourceKey`、`conversationUniqKey`。
- 创建会话时写入稳定唯一键，例如 `sourceType:sourceId:sortedUserIds`。
- 查询列表时按当前用户参与键查询，而不是全量读集合。
- 去重应依赖唯一键或数据库约束策略，而不是内存扫描。

### P1：登录后 `next` 跳转参数未做白名单校验

位置：

- `Code文档/features/auth/login-form.tsx`
- 登录成功后执行 `router.push(searchParams.get("next") ?? "/")`

风险：

- `next` 参数可被构造为非预期跳转目标。
- 即使 Next.js 对外部 URL 有一定处理，该处仍应显式限制为站内路径，避免协议相对路径或奇怪输入绕过。

建议：

- 只允许以 `/` 开头且不以 `//` 开头的路径。
- 不符合规则时跳转到 `/`。
- 可抽取 `sanitizeNextPath()` 并补单测。

### P1：反馈入口未形成最小可执行通道

位置：

- `Code文档/app/feedback/page.tsx`

风险：

- 页面提示“通过运营邮箱提交反馈”，但没有展示邮箱、`mailto:` 链接、表单或其他提交方式。
- 对骚扰、虚假信息、联系方式滥用等高风险场景，用户无法按页面指引完成反馈。
- MVP 虽不需要完整工单后台，但至少应提供真实可用入口。

建议：

- 上线前至少提供一个运营邮箱和 `mailto:` 链接。
- 如果暂不公开邮箱，改为最小反馈表单并写入 CloudBase。
- 页面文案应写清处理时限和需要提供的信息。

### P2：Cookie 服务端读取缺少硬过期校验

位置：

- `Code文档/server/auth-session.ts`

现状：

- Cookie 设置了 `Max-Age=7天`。
- 服务端验签后只校验 `phone` 和 `createdAt` 字段存在，没有判断 `createdAt` 是否超过有效期。

风险：

- 浏览器正常会按 `Max-Age` 删除 Cookie。
- 但如果旧 Cookie 被复制或重放，只要签名密钥未轮换，服务端仍可能接受。

建议：

- `readAuthSessionFromRequest()` 中解析 `createdAt`。
- 若 `createdAt` 无效或超过 `MAX_AGE_SECONDS`，返回 `null`。
- 补充过期 Cookie 被拒绝的单测。

### P2：前端 API client 默认响应一定是 JSON

位置：

- `Code文档/features/chat/chat-api-client.ts`
- `Code文档/features/parent-needs/parent-need-api-client.ts`
- `Code文档/features/tutor-profiles/tutor-profile-api-client.ts`
- `Code文档/features/profile/contact-profile-api-client.ts`
- `Code文档/features/auth/login-form.tsx`
- `Code文档/features/auth/use-test-session.ts`

风险：

- CloudBase Run 首次托管复验时曾出现 HTML 错误页返回。
- 前端直接 `response.json()` 会抛解析异常，用户看到的是页面异常或无清晰错误。

建议：

- 抽取统一 `safeParseApiResponse()`。
- 非 JSON 响应转换成 `{ ok: false, errors: { request: "服务暂时不可用，请稍后重试" } }`。
- 对 `response.ok` 和 content-type 做统一处理。

### P2：老师资料价格区间模型与 UI 不一致

位置：

- `Code文档/app/tutor-profiles/new/page.tsx`
- `Code文档/features/tutor-profiles/tutor-profile.ts`

现状：

- 领域模型 `feeRanges` 是数组。
- 页面只编辑 `feeRanges[0]`。

风险：

- 开发员容易误以为产品支持多组价格区间。
- 用户实际只能填写一组。
- 后续筛选、展示和编辑逻辑可能围绕错误假设继续扩展。

建议：

- 如果 MVP 只支持一组，则将模型收敛为单对象，后续 vNext 再扩展数组。
- 如果产品确实需要多组，则补“添加/删除课时费区间”的 UI 和测试。

### P2：证明图片入口与真实能力不一致

位置：

- `Code文档/app/tutor-profiles/new/page.tsx`
- `Code文档/app/tutor-profiles/[id]/page.tsx`
- `Code文档/app/profile/tutor-profiles/page.tsx`

现状：

- 发布页只保存图片文件元信息。
- 没有真实上传 CloudBase 存储。
- 详情页和个人页显示“证明图片：N 张”。

风险：

- 用户可能误以为平台已保存并可审核/查看证明图片。
- 后续审核、真实性和风控流程容易基于错误前提设计。

建议：

- MVP 若不做真实上传，应在 UI 中明确“当前仅记录文件名，不支持查看/审核”。
- 或者直接隐藏图片数量展示，避免制造审核能力错觉。
- vNext 若做真实性能力，再接入真实文件上传、访问权限、审核状态和删除策略。

### P2：缺少可见登出入口

位置：

- `Code文档/app/profile/page.tsx`
- `Code文档/app/layout.tsx`
- `Code文档/app/api/auth/logout/route.ts`

现状：

- 后端已有 `/api/auth/logout`。
- 页面没有明显登出按钮。

风险：

- 测试账号切换不方便。
- 共用设备场景下，用户无法主动结束会话。

建议：

- 在个人页或顶部导航增加“退出登录”按钮。
- 调用 `/api/auth/logout` 后跳转首页或登录页。

### P3：公开列表分页策略仍是阶段性方案

位置：

- `Code文档/server/parent-needs.ts`
- `Code文档/server/tutor-profiles.ts`

现状：

- M5 已从单次 `.get()` 改为按 `status=published`、`createdAt desc`、`skip/limit` 拉取近期公开记录。
- 当前最多读取约 1000 条近期公开记录。

判断：

- 该问题已经不阻塞 MVP/M5。
- 但正式增长前需要升级为数据库索引、游标分页或服务端分页 API。

### P3：浏览器真实流程测试仍不足

现状：

- 当前单测和 HTTP 脚本覆盖较强。
- 但没有 Playwright 或等价浏览器 E2E，无法自动覆盖真实页面交互、路由跳转、按钮状态、表单错误展示和移动端布局。

建议：

- 发布前至少补 1 条冒烟 E2E：登录、发布需求、发布老师资料、广场筛选、进入详情、创建聊天、发消息、请求交换联系方式、同意后查看联系方式。
- 若时间有限，可先用手工验收清单替代，但应记录结果。

## 6. 建议给代码开发员的处理顺序

### 第一优先级：上线前应修

1. 修复登录 `next` 参数校验。
2. 让反馈页具备真实可用入口。
3. 将聊天会话查询从全集合扫描改为索引化查询。

### 第二优先级：上线前强烈建议修

1. Cookie 服务端读取增加过期校验。
2. 前端 API client 增加非 JSON 响应容错。
3. 增加登出入口。
4. 明确证明图片当前能力边界。

### 第三优先级：vNext 或技术债治理

1. 老师资料多组价格区间模型和 UI 对齐。
2. 公开列表升级游标分页或服务端分页。
3. 旧 localStorage 代码整理、标记 legacy 或删除不用路径。
4. 抽取重复校验、ID、分页和错误处理工具。
5. 增加浏览器 E2E 冒烟测试。

## 7. 上线前架构结论

当前 M1-M5 代码不是“不能上线”的状态，而是“测试托管环境验收通过、正式生产上线前需要收口”的状态。

可以继续推进发布前准备，但不建议直接进入生产发布。建议先完成：

1. 生产环境变量清单。
2. 正式生产关闭测试登录确认。
3. 独立生产 `AUTH_SESSION_SECRET`。
4. 反馈入口落地。
5. 登录跳转安全修复。
6. 会话查询索引化。
7. 最小浏览器冒烟验收。

完成这些后，MVP 进入小范围试运行会更稳。
