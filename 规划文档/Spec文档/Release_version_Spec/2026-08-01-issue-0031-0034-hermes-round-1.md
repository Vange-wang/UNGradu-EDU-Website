## Serious Findings

### S-001 — Process ambiguity: Document QA "一次性整改" vs three-round review model

- **Severity**: SERIOUS
- **Location**: §8.1, lines 302–303
- **Evidence**:
  > `本 Spec 完整草案形成并自检。` (line 299)
  > `总负责人冻结 canonical hash 后组织 Hermes 关键文档审查；最多三轮` (line 300)
  > `出现 SERIOUS 问题时交 Document QA 一次性整改；仅 NON_SERIOUS 问题可以登记为非阻塞台账。第三轮仍有严重问题，进入 DOCUMENT_REVIEW_LIMIT_REACHED，由业务方决定。` (lines 302–303)

- **Impact**: The word `一次性` (one-time / single-batch) is ambiguous against the three-round model. Two conflicting readings exist:
  - **Reading A** (likely intended): Each Hermes review round that discovers SERIOUS findings triggers a single *batch* Document QA pass (all findings processed at once), then proceeds to the next Hermes round.
  - **Reading B** (literal): Only one Document QA session is permitted *total* across all rounds. If Round 1 finds SERIOUS issues, QA fixes them. If Round 2 finds *different* or *residual* SERIOUS issues, there is no defined path — escalate immediately to `DOCUMENT_REVIEW_LIMIT_REACHED`, or fall into a procedural deadlock.

  Reading B would mean the process collapses on the second round of SERIOUS findings, which is plausible for a complex multi-Issue spec. The document does not explicitly state whether Document QA can be invoked more than once.

- **Correction**: Replace `一次性整改` with explicit language. Recommended text:
  > `出现 SERIOUS 问题时，本轮所有 SERIOUS 发现集中交 Document QA 一次性批量整改后进入下一轮 Hermes 审查；仅 NON_SERIOUS 问题可登记为非阻塞台账。第三轮审查后仍有 SERIOUS 问题未关闭，进入 DOCUMENT_REVIEW_LIMIT_REACHED，由业务方决定。`

- **Recheck trigger**: After correction, verify that the flow map (draft → freeze → Hermes R1 → [QA if SERIOUS] → Hermes R2 → [QA if SERIOUS] → Hermes R3 → [LIMIT_REACHED or PASS]) is unambiguous.

### S-002 — Undefined "安全隔离" for unversioned legacy records creates data-loss risk

- **Severity**: SERIOUS
- **Location**: §3.3, line 131
- **Evidence**:
  > `旧记录必须迁移/回填成功或明确被安全隔离，不能被"无版本"绕过并发控制。`

- **Impact**: The document correctly identifies that existing records in `parent_needs` and `tutor_profiles` lack `version` and `updatedAt` fields (§1.1 lines 23–24). It mandates that these old records must be "migrated/backfilled successfully OR explicitly safely isolated." However, `安全隔离` (safely isolated) is never defined. An implementer could interpret this as any of:
  - Make old records **read-only** (users can see but not edit them) — acceptable but degrades UX.
  - **Hide** old records from all views until backfilled — breaks user access to their own content.
  - **Archive** them to a separate collection — potentially loses relational links to chats and exchange requests.
  - **Physically delete** old records — violates the no-hard-delete policy.

  Without a definition, the escape hatch ("if backfill fails, isolate them") could itself become a data-loss or user-visible breakage vector. This is a material risk because the backfill of `version` onto existing records is non-trivial (requires an initial value decision, a consistency mechanism, and validation for records currently being edited).

- **Correction**: Add a definition in §3.3 or §9 (Decision Gates). Recommendation:
  > Add a decision gate D8:
  > `旧记录无 version/updatedAt 的隔离策略 | 默认：标记只读 + 提示用户"重新发布以启用管理功能"；在 UI 明确告知并保留原有聊天/交换关联 | 隐藏或物理删除将丧失可审计性和用户信任 | 0033 实现前`

  And in §3.3, replace `明确被安全隔离` with:
  > `明确被安全隔离（定义见决策门 D8，至少保留可读、可审计、可关联聊天/交换，且向用户可见并解释限制）`

- **Recheck trigger**: Verify that the isolation strategy is decision-gated and that no implementer can choose an interpretation that silently hides or deletes user data.
