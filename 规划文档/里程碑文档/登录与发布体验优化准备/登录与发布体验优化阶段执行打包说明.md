# 登录与发布体验优化阶段执行打包说明

日期：2026-06-28

任务 ID：`UX-PUBLISH-2026-06-28-001`

发起方：项目总控制人

执行 Agent：产品经理 Agent（`019efc62-584b-79a2-90df-808f28ecefce`）

## 1. 背景

正式环境试用反馈显示：邮箱登录、发布需求、发布家教信息、联系方式保存已经可用，说明“能登录、能发布、能保存基础信息”的主链路已经跑通。

但当前体验仍有几个明显问题，会影响真实用户继续使用：

- 发布家教信息时，课时费 / 学段只能写一种，不能表达“不同学段不同收费”。
- 登录成功后仍能看到并点击登录入口，容易误触到空白登录表单，以为要注册另一个账号。
- 详情页、表单页缺少返回入口，用户不知道怎么回到上一页或列表页。
- 页面上暴露了太多杂乱的字母数字字段，看起来像系统内部信息，影响信任感。
- 聊天窗暂时无法完整验证，原因是业务方目前只有一个账号，缺少第二个账号模拟对话另一方。

本阶段目标不是扩展新业务，而是把已经跑通的登录与发布体验打磨到“普通用户能顺手使用、不会被技术字段干扰”的程度。

## 2. 阶段目标

本小阶段目标：

- 老师发布家教信息时，可以添加多组“学段 + 课时费”。
- 已登录用户不再误触登录 / 注册表单。
- 详情页和表单页具备清晰的返回入口。
- 普通用户页面不裸露系统 ID、内部字段、技术字段。
- 聊天窗验收条件明确：至少两个账号 / 两个邮箱分别模拟家长和老师后再验证。

## 3. 问题一：课时费 / 学段只能写一种

### 产品目标

老师发布家教信息时，应能表达多组收费规则。例如：

- 小学：100 元 / 小时
- 初中：150 元 / 小时
- 高中：200 元 / 小时

### 交互要求

- 在家教信息发布 / 编辑表单中，将现有单一“学段 + 课时费”升级为可重复条目。
- 每一条包含两个核心字段：`学段`、`课时费`。
- 提供一个清晰的“加号”小按钮，用于新增一组“学段 + 课时费”。
- 每组条目建议提供删除按钮，避免用户加错后无法移除。
- 至少保留一组条目，不能全部删除为空。
- 页面展示老师信息时，应以用户能看懂的形式显示多组收费规则，而不是拼接成难读字符串。

### 验收标准

- 老师可以新增至少 2 组“学段 + 课时费”。
- 每组学段和课时费能分别填写、保存、再次打开后仍能看到。
- 删除某一组后，其它组不受影响。
- 不允许保存空学段、空课时费或明显非法课时费。
- 公开详情页和个人页能清晰展示多组收费规则。

### 优先级

必须修复：P1。

原因：这是发布家教信息的核心业务表达能力。只能写一种收费，会导致老师资料不完整，也影响家长判断。

## 4. 问题二：已登录后仍可点击登录按钮

### 产品目标

用户登录成功后，不应再被引导到空白登录 / 注册表单。系统应明确告诉用户“你已经登录”，并提供去个人页或退出登录的路径。

推荐方案：

- 已登录状态下隐藏登录入口。
- 导航区域或页面入口显示“个人页 / 我的资料 / 退出登录”等更合理的入口。
- 只有用户从个人页或导航中点击退出登录后，才重新显示登录 / 注册入口。

可接受替代方案：

- 如果用户直接访问 `/login`，页面不展示登录表单，而展示“你已登录”，并提供“进入个人页”“退出当前账号”两个按钮。
- 退出后才展示邮箱验证码登录表单。

### 验收标准

- 已登录用户在首页或导航中看不到会误导其重新登录的入口。
- 已登录用户直接访问登录页时，不出现空白邮箱登录表单。
- 已登录用户能清楚看到当前登录状态或进入个人页入口。
- 用户退出登录后，登录 / 注册入口恢复可用。
- 不允许通过已登录状态误触创建第二个账号。

### 优先级

必须修复：P1。

原因：这是登录体验的基本闭环。已登录却继续显示登录表单，会让普通用户困惑，也可能制造重复账号。

## 5. 问题三：缺少返回按钮

### 产品目标

详情页、表单页、个人子页面应提供明确返回路径，让用户知道如何回到上一页、列表页或个人页。

### 交互要求

- 需求详情页：提供“返回需求列表”或“返回上一页”。
- 老师详情页：提供“返回老师列表”或“返回上一页”。
- 发布需求表单：提供“返回上一页 / 返回我的需求 / 返回首页”中最合适的入口。
- 发布家教信息表单：提供“返回上一页 / 返回我的家教信息 / 返回首页”中最合适的入口。
- 聊天详情页：提供“返回聊天列表”。
- 联系方式管理页和个人子页面：提供“返回个人页”。

### 验收标准

- 用户进入主要详情页和表单页后，首屏或页面顶部能看到明确返回入口。
- 返回按钮文案是中文业务语义，不使用只有开发者能懂的符号或路径。
- 返回行为稳定，不把用户带到无关页面。
- 移动端和桌面端均可点击，且不遮挡表单或主要内容。

### 优先级

P2 优化。

原因：不影响核心数据提交，但明显影响可用性和方向感。建议本阶段一起修复。

## 6. 问题四：页面暴露杂乱字母数字字段

### 产品目标

普通用户不应看到系统 ID、内部字段、技术字段或未翻译的数据库字段。页面应展示中文标签、业务状态和必要的脱敏信息。

### 需要识别并处理的字段类型

默认不应裸露给普通用户：

- 系统 ID：如 `id`、`_id`、`userId`、`ownerUserId`、`conversationId`、`messageId`、`requestId`、`profileId`。
- 数据库字段：如 `createdAt`、`updatedAt`、`status`、`emailHash`、`phoneHash`。
- 技术配置或内部状态：如 collection 名称、路由片段、哈希、token、secret、debug 字段。
- 未翻译枚举：如 `active`、`pending`、`closed`、`draft`。
- 长串字母数字：除非它是用户必须核对的订单号或追踪号，本项目当前阶段一般不应展示。

处理方式：

- 能隐藏的直接隐藏。
- 必须展示的，改成中文标签和业务文案。
- 时间字段展示为“发布时间”“更新时间”，使用可读格式。
- 状态字段展示为“已发布”“待补充”“已关闭”等中文状态。
- 邮箱、联系方式等敏感信息按权限展示，必要时脱敏。
- 调试信息只允许在开发环境或管理员工具中出现，不应出现在普通用户正式页面。

### 验收标准

- 普通用户浏览首页、列表页、详情页、个人页、发布表单后，不应看到无解释的长串 ID。
- 状态、时间、身份、费用、学段等信息均使用中文标签。
- 内部字段不出现在普通用户可见页面。
- 如果确需展示识别信息，必须说明用途并进行短码化或中文化。
- 不泄露邮箱验证码、密钥、哈希、CloudBase 内部信息。

### 优先级

必须修复：P1。

原因：正式环境页面暴露大量技术字段，会直接损害用户信任，也可能带来隐私和风控风险。

## 7. 聊天窗验证缺口

当前结论：暂不判定聊天窗已坏。

原因：业务方目前只有一个账号，无法完整模拟“家长和老师两个不同身份之间发起会话、收发消息、权限隔离”的真实场景。

### 需要的验证条件

至少需要：

- 两个独立账号 / 两个邮箱。
- 账号 A 模拟家长。
- 账号 B 模拟老师。
- 账号 A 发布找老师需求，或对老师资料发起咨询。
- 账号 B 发布老师资料，或对家长咨询进行回复。
- 两个账号分别登录，确认聊天列表、聊天详情、消息收发和非参与者访问限制。

### 验收标准

- 家长账号能从老师详情或匹配入口发起聊天。
- 老师账号能看到对应聊天并回复。
- 双方都能看到消息时间、内容和对方身份。
- 刷新页面后聊天记录仍存在。
- 非会话参与者不能读取聊天内容。
- 退出登录后不能访问聊天内容。

### 优先级

验收缺口：待双账号 / 第二账号验证。

不作为本轮代码已坏结论。

## 11. 不做范围

本小阶段不做：

- 支付。
- 复杂排课。
- 实名认证。
- 合同。
- 审核后台。
- 举报封禁后台。
- 自动推荐。
- 聊天高级功能，例如图片聊天、已读回执、消息撤回、客服介入。
- 复杂账号体系、换绑邮箱、账号合并。
- 新增营销增长玩法。

以上能力如需要，应进入后续 vNext 或单独 Spec。
