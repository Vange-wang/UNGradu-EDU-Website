`Code文档/features/parent-needs/parent-need-storage.ts` 第 41-42 行：

```ts
function createParentNeedId(ownerPhone: string, count: number) {

}
```

`Code文档/features/tutor-profiles/tutor-profile-storage.ts` 中 `createTutorProfileId` 函数与上述实现结构完全相同，仅函数名不同，同样将原始手机号拼入 ID。

确认：两个 ID 生成函数都把登录手机号作为 ID 的第一段，未做任何哈希、加密或脱敏处理。

URL 使用位置核对：

`Code文档/app/parent-needs/page.tsx` 第 198 行：

```tsx
<Link className="button secondary" href={`/parent-needs/${need.id}`}>
```

确认：广场列表页确实把含手机号的 `id` 直接写入了 `<Link href>`，该链接会被浏览器渲染为可见、可复制、可分享的 URL，原报告描述准确。

## 3. 对 P2 风险的逐项复核

### P2：M2 已存在的本地测试数据可能无法进入 M3 广场 — 确认属实

代码位置核对：

`Code文档/features/parent-needs/parent-need-storage.ts` 中，`saveOwnerPhone(ownerPhone, storage)` 仅在 `saveParentNeed` 函数内部被调用（第 119 行），用于维护 `ungradu.parentNeedOwners` 跨账号索引；`readAllParentNeeds` 完全依赖该索引来枚举所有发布者再逐一读取其需求列表。

确认：如果某个测试账号是在 M2 代码（即 `932da42` 之前的版本）下发布过需求，对应数据只会写入 `ungradu.parentNeeds.{ownerPhone}`，不会触发 M3 新增的 `saveOwnerPhone` 调用，因此该账号不会出现在 `ungradu.parentNeedOwners` 列表中，进而 `readAllParentNeeds` 不会读取到这部分历史数据。

确认大学生家教信息一侧存在完全相同的索引模式和相同风险。

**复核结论：P2 属实，根因描述准确。** 这是一个数据迁移/兼容性问题，而非功能逻辑错误，原报告将其定为 P2（不阻塞，但需要在测试说明或工作记录中写明）的严重程度判断合理。
