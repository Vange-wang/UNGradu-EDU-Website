## 3. 审查明细

### 3.1 多组“学段 + 科目 + 课时费”

审查结论：通过，允许进入复核。

确认点：

- `Code文档/app/tutor-profiles/new/page.tsx` 中家教发布表单已将收费规则改为 `feeRanges` 可重复条目，每条包含 `grade`、`subject`、`min`、`max`。
- 页面提供“+ 新增一组学段与课时费”按钮，并提供删除按钮。
- 删除按钮在仅剩一组时禁用，满足“至少保留一组”的口径。
- `Code文档/features/tutor-profiles/tutor-profile.ts` 中校验要求每组学段、科目、最低课时费、最高课时费均完整有效，且最低值不能高于最高值。
- `formatTutorFeeRange()` 用中文业务文案展示多组收费规则，并兼容旧数据中学段或科目为空的情况。
- `Code文档/server/tutor-profiles.ts` 与本地存储兼容逻辑均已按 `feeRanges[].grade/subject/min/max` 参与保存、公开展示和筛选。
- `Code文档/tests/tutor-profile.test.ts` 已增加多组收费规则保留和旧数据格式化测试。

产品判断：执行包要求的是“多组学段 + 课时费”，本次实现进一步把“科目”也纳入同一组收费规则，符合任务输入材料中的审查重点“多组学段 + 科目 + 课时费”。

### 3.2 已登录状态登录入口 / 登录页

审查结论：通过，允许进入复核。

确认点：

- `Code文档/features/auth/session-nav.tsx` 已按登录态切换导航：未登录显示“登录”，已登录显示“个人页 / 退出登录 / 规则”。
- `Code文档/features/auth/login-page-content.tsx` 中已登录用户访问 `/login` 时展示“当前已登录”、进入个人页和退出登录入口，不再展示邮箱验证码登录表单。
- 退出登录后导航回到首页并刷新状态，登录入口恢复可用。

产品判断：该实现满足“已登录用户不再被误导重复注册 / 登录”的 P1 口径。

### 3.3 主要页面返回入口

审查结论：通过，允许进入复核。

确认点：

- 发布需求页提供“返回我的需求”。

- 聊天详情页提供“返回我的聊天”。

产品判断：返回入口覆盖执行包列出的主要详情页、表单页、聊天页和个人子页面，文案均为中文业务语义。

### 3.4 普通用户页面技术字段清理

审查结论：通过，允许进入复核。

确认点：

- 本轮重点页面未再直接展示“当前测试账号”“服务端集合名”“来源 ID”等内部字段文案。
- 聊天列表将会话来源展示为“来自一条家教需求 / 来自一条家教信息”，不再暴露来源 ID。
- 聊天详情中交换请求状态通过 `statusLabels` 展示为“待处理 / 已同意 / 已拒绝 / 已撤回 / 已过期”。
- 消息时间和交换请求日期使用中文可读日期 / 时间格式展示。
- 公开列表、详情页和个人页仍在代码中使用 `id` 作为路由和 React key，但没有在普通用户页面正文中裸露无解释的长串 ID。

产品判断：本轮已满足“普通用户页面不裸露系统 ID、内部字段、技术字段”的 P1 体验口径。路由和接口内部仍需使用 ID，不应误判为页面展示问题。

### 3.5 聊天窗双账号验证

审查结论：维持验收缺口，不作为代码阻塞。

确认点：

- 执行包已明确聊天窗需要至少两个独立账号 / 两个邮箱分别模拟家长和老师后再验证。
- 当前材料未提供第二个可用邮箱账号，也未提供双账号正式环境冒烟记录。
- 本轮代码并未扩大聊天高级能力范围，也未发现足以将聊天窗判定为代码已坏的新增证据。

产品判断：`ISSUE-0010` 应继续保持“待双账号 / 第二账号验证”状态。它不阻止本轮进入 ZCode 复核，但后续正式验收仍需项目总控制人提供第二个可用邮箱账号。

## 4. 非阻塞观察

- 当前公开详情页和聊天页 URL 仍使用资源 ID 作为路由参数，这是当前应用既有路由机制；本轮产品审查只确认普通用户页面正文不裸露无解释的内部 ID。若后续业务方希望 URL 也短码化或业务化，应单独进入技术债或 vNext，而不作为本轮 P1 阻塞。
- 生产真实邮箱验证码登录是否已经在正式 URL 冒烟，不属于本轮登录与发布体验优化代码提交的验收对象，仍按登录系统顺利落地阶段遗留外部配置事项处理。
- 本轮不关闭 `ISSUE-0006` 至 `ISSUE-0010`，只给出产品经理第一轮审查结论。
