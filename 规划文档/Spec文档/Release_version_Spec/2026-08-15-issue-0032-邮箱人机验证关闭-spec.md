## 2. 目标、非目标与 provider-neutral 约束

### 2.1 目标

为邮箱验证码发送建立不可由客户端单独绕过的服务端人机验证信任链：

1. 用户先完成挑战并取得短时 token；
2. 服务端验证 token 的签名/状态、一次性消费、时效、hostname、action、会话和请求上下文；
3. 只有验证成功且组合限流允许时，服务端才调用既有邮箱发送动作；
4. 任何不确定、超时、不可达或配置缺失都 fail-closed，不发送验证码；
5. 用户得到不泄露风控细节的可理解反馈；经业务方批准并冻结后方可使用的无障碍替代路径当前未定义，保持 USER_CONFIRMATION_PENDING。

### 2.2 非目标

- 不在本稿选择或绑定真实 provider，不预填 provider 域名、地域、采购、价格、计费、DPA 或法律结论。
- 不写入真实 site key、secret、API key、邮箱供应商 key 或生产环境配置。
- 不以客户端勾选、隐藏字段、前端状态或自报验证结果替代服务端校验。
- 不改变账号、会话、邮箱内容、验证码有效期或既有发送业务语义，除非后续用户确认和独立 Spec 另行冻结。
- 不在本稿执行 provider 网络请求、真实邮件发送、部署、生产观察、Issue 状态修改或 Git mutation。
- 不携带数据库、付费、其他 Issue 或跨分支实现。

### 2.3 provider-neutral 接口约束

实现前只允许冻结抽象字段与行为，例如：

- challenge_token；
- expected_hostnames、expected_actions；
- token_ttl、verify_timeout；
- provider response 的成功/失败/不可达分类；
- one-time consume、账号/IP/设备/会话/动作的组合限流；
- secret 仅以引用名存在，真实值由授权平台 owner 管理。

字段名、默认值、真实 endpoint 和厂商响应映射必须在用户确认、供应商授权和技术复核后另行登记。候选服务名只可作为评估对象，不是本稿的选型结论。

## 3. 用户可见结果

### 3.1 正常流程

用户打开登录或邮箱验证码入口，完成可用的人机挑战并提交邮箱。服务端验证成功后，才发送一次验证码；页面显示“验证码已发送”或等价的确认，不显示 provider 响应、风险分数、Secret、内部 request ID 或用户隐私数据。

### 3.2 失败流程

缺少 token、伪造、过期、重复、hostname/action 不符、会话不符、服务端超时、provider 不可达、Secret 引用缺失、限流命中、邮箱发送失败或结果不确定时：

- 邮箱发送次数必须为 0；
- 页面显示统一、安全、可操作的提示，如“验证未完成，请稍后重试”；
- 不告诉攻击者是哪个字段失败，不回显 token，不暴露账号是否存在；
- 记录最小化审计并遵循重试/冷却策略；
- 若后续批准无障碍替代路径，该路径也必须进入同一服务端验证、一次性消费与限流，不得成为绕过入口；在批准 receipt 出现前，不得把替代路径描述为可用。

### 3.3 用户可感知的边界

验证服务暂时不可用时，产品可以提示稍后重试或人工支持入口，但不得降级为“仅前端勾选即可发送”。反复失败不得造成验证码洪泛，也不得通过更宽松错误处理隐藏未确认的 provider 风险。

## 7. 安全、隐私、未成年人与失败控制

- 测试使用合成邮箱、脱敏账号和批准的测试域名；不把真实邮箱、儿童资料、token、Cookie、Secret 或 provider 原始响应写进仓库、截图、日志或 Issue。
- challenge token 视为短期敏感凭据，服务端只保存必要的消费标记和审计摘要，不保存可重放原文；日志必须脱敏。
- 错误消息不得透露账号存在、provider 名称、hostname、action、风控字段或内部失败原因。
- 邮箱发送属于有副作用动作，验证成功与发送授权必须在同一服务端信任链中；验证结果不明确时保持发送 0。
- 经批准的无障碍方案必须满足相同的服务端验证、一次性和限流要求；不得为某类用户设置隐含绕过。当前未批准替代路径时，只验证常规挑战的适用基础无障碍要求，不得虚构替代方案。
- 任何可能携带未成年人信息的注册/登录上下文只用最小化字段；本 Issue 不扩展未成年人数据处理范围。

## 8. 停止、回滚与重开

### 8.1 停止条件

出现 `V4_PARAMETER_RECEIPT` 缺失/冲突、客户端可绕过、重放后重复发送、错误 host/action 可通过、服务不可达仍发送、Secret 出现在日志、限流无法阻断、已批准无障碍路径绕过、未批准路径被当作可用、provider/network/DPA 未授权、生产 key 不可追溯或独立复核为 REWORK_REQUIRED 时，立即停止，不进入下一阶段。

### 8.2 回滚

回滚只能回到最近一个有精确 base receipt 和配置 receipt 的已验收版本。回滚时停止新的发送、撤销/轮换暴露凭据、验证登录/验证码旧路径和审计告警。禁止以“保留旧前端入口”表述为真实回滚已演练；真实回滚必须由授权平台 owner 执行并单独取证。

### 8.3 重开

生产出现验证码洪泛、绕过、误拒异常、重复发送、provider 配置漂移、Secret 泄露、无障碍投诉或业务撤销 provider/DPA/成本确认时，ISSUE-0032 保持 Open 或由 Issue 管理员按新证据重开。本 Spec 不自动把“provider-neutral 准备完成”转为关闭。

## 9. 验收骨架（参数待冻结）

1. 存在完整且经批准的 `V4_PARAMETER_RECEIPT`；全部测试记录引用其精确路径/hash，并覆盖 token_ttl、verify_timeout、host/action、消费标记保留/清理和组合限流的等于/低于/高于边界。缺失或冲突时本节不可执行，也不得给阶段 PASS。
2. 缺 token、伪造 token、过期 token、重复 token、错误 hostname、错误 action、错会话、超时、不可达、Secret 引用缺失和风险不确定的请求，邮箱发送次数均为 0。
3. 有效 token 最多消费一次；并发重放、重复提交和重试不会产生多次发送。
4. 客户端删除挑战、修改隐藏字段、直接调用发送接口、伪造 Header 或使用旧响应，均不能绕过服务端验证。
5. 账号、IP、设备、会话和动作限流规则按 receipt 可复现；限流失败时不发送，不泄露内部规则。
6. 验证成功、发送成功、发送失败、验证失败和 provider 不可达的用户文案不泄露敏感原因；若无障碍替代路径已由业务批准，则有独立证据证明其可用且不绕过同一服务端链，未批准时明确 N/A/PENDING 而非通过。
7. 测试/预生产/生产 Secret 引用和 provider endpoint 环境隔离，日志与截图无明文凭据。
8. 供应商、hostname/action、TTL、IP 最小化、成本、DPA、轮换、目标网络和生产窗口均有单独确认和证据；未确认项保持 pending。
9. 独立安全/技术复核、适用生产观察、产品验收、业务接受和 Issue 管理员复读全部完成后，才可提出关闭。
