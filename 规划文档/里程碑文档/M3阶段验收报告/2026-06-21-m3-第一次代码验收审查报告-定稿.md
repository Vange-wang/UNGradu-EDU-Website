## 4. 问题清单

### P0：公开详情 URL 暴露发布者手机号 — 已核实属实

涉及位置：

- `Code文档/features/parent-needs/parent-need-storage.ts:41-42`（`createParentNeedId`）
- `Code文档/features/tutor-profiles/tutor-profile-storage.ts`（`createTutorProfileId`，结构与上者完全相同）
- `Code文档/app/parent-needs/page.tsx:198`
- `Code文档/app/tutor-profiles/page.tsx:192`

问题说明：

`createParentNeedId` 和 `createTutorProfileId` 均使用 `${ownerPhone.trim()}-${Date.now()}-${count + 1}` 生成记录 ID，把登录手机号原样拼入 ID 第一段，未做任何哈希、加密或脱敏处理。M3 广场页又把该 ID 直接放进详情页链接：

```tsx
<Link className="button secondary" href={`/parent-needs/${need.id}`}>
```

`app/tutor-profiles/page.tsx` 存在结构相同的链接。这会让发布者登录手机号出现在浏览器地址栏、历史记录、截图、日志和分享链接中。

详情页正文复核：`app/parent-needs/[id]/page.tsx` 通读全文，确认正文只展示学段、科目、区域、预算、性别偏好、时间段、孩子简介，并明确写明“不展示家长联系方式”，确实没有渲染 `ownerPhone` 字段本身——问题严格出在 URL 层，不在正文渲染层。

对称性确认：家长需求与大学生家教信息两侧的 ID 生成函数、URL 拼接方式完全对称，不是单一文件的孤立疏漏，修复时必须两侧同步处理。

测试覆盖确认：`tests/parent-need-marketplace.test.ts` 与 `tests/tutor-profile-marketplace.test.ts` 当前均无任何用例断言 `id` 不包含 `ownerPhone`，确认这是一个尚未被测试覆盖的真实回归风险。

违反标准：

- `AGENTS.md` 要求涉及联系方式、未成年人信息和隐私保护的逻辑必须谨慎设计。
- MVP Spec 权限与安全要求：未授权前不得返回或展示对方联系方式，联系方式保护是 MVP 核心安全主线。

影响：M3 验收要求“详情页不展示联系方式”，当前详情页 URL 中的动态 ID 包含发布者登录手机号，属于公开可见信息，因此该项验收**不通过**。

建议：

- 记录 ID 不得包含手机号、微信号或任何可识别联系方式；改用 `crypto.randomUUID()`、自增序号配合不可逆映射，或后端生成的不可反推 ID。家长需求与大学生家教信息两侧需同步修复。
- 增加测试：保存需求/家教信息后，断言 `id` 和详情链接不包含 `ownerPhone`，两侧均需覆盖。

### P2：M2 已存在的本地测试数据可能无法进入 M3 广场 — 已核实属实

涉及位置：

- `Code文档/features/parent-needs/parent-need-storage.ts`（`saveOwnerPhone` 调用点、`readAllParentNeeds`）
- `Code文档/features/tutor-profiles/tutor-profile-storage.ts`（对应同构实现）

问题说明：

M3 新增 `ungradu.parentNeedOwners` 和 `ungradu.tutorProfileOwners` 作为跨账号聚合索引，但该索引只在 M3 版本的 `saveParentNeed` / `saveTutorProfile` 内部调用 `saveOwnerPhone` 时写入。若测试账号是在 M2 代码（`932da42` 之前）下发布过需求或家教信息，旧数据只存在于 `ungradu.parentNeeds.{ownerPhone}` / `ungradu.tutorProfiles.{ownerPhone}`，没有进入 owners 索引；`readAllParentNeeds` / `readAllTutorProfiles` 完全依赖该索引枚举发布者，因此不会读取到这部分历史数据。

影响：不一定影响全新测试数据，但会影响从 M2 接续到 M3 的验收体验：已发布内容可能在“我的发布”中存在，却不出现在广场中。这是一个数据迁移/兼容性问题，而非功能逻辑错误。

建议：

- 若继续使用本地测试存储，补一个轻量迁移或重建索引机制（例如在读取时检测到某账号有发布数据但未在 owners 索引中时自动补录）。
- 至少在开发员工作记录和测试说明中写清楚 M3 验收前需要用 M3 代码重新发布测试数据。

补充说明：

- 初审时本机因残留 `next dev` 进程导致 `.next/trace` 报 `EPERM`，停止占用进程并清理 `.next` 后复跑通过；复核时使用从未运行过 `next dev` 的独立干净环境，构建一次性通过，未重现该问题。两次结果相互印证，确认该问题是本机环境噪音（dev server 文件锁），不是代码缺陷，但仍建议开发员在本机修复 P0 后保持“构建前关闭 dev server”的习惯。

## 7. 阶段结论与下一步建议

**M3 当前暂不通过。**

修复要求：

1. **必须修复**：将 `createParentNeedId` 与 `createTutorProfileId` 改为不包含手机号、微信号或任何可识别联系方式的标识符，两侧需同步修复，不能只修复一侧。

4. 修复完成后，重新执行 `npm test`、`npm run lint`、`npm run typecheck`、`npm run build`，并在开发员工作记录中更新验证结果。

P0 修复并复验通过后，才建议进入 M4：站内聊天与联系方式交换的开发。M4 涉及更高密度的隐私敏感操作（聊天记录、联系方式交换二次确认），如果 M3 阶段遗留的标识符隐私问题不先解决，后续风险会被进一步放大。
