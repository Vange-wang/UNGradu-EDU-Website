## 1. 设计总原则与状态不变量

1. **公开先决条件**：只有服务端在当前 `owner`、`contentVersion`、`contentHash`、`policyVersion`、审核决定和幂等校验均通过后，才可以展示“已公开”。前端状态、AI 单独输出、超时或重试不得授权公开。
2. **失败闭环**：检测器、标准化、AI、队列、审计、权限、版本或预算任一失败，都停留在 `pending_review` 或 `needs_manual_review`，页面明确“当前不会公开”。
3. **版本隔离**：已发布内容编辑时生成新版本；新版本待审期间，旧的最后已发布快照按 Spec 推荐默认继续可见。不得把旧审核结果套给新内容。
4. **删除优先**：软删除后 48 小时内的恢复只能走 `deleted → pending_review`，不能直达 `published`。删除期间聊天只读、不能发消息、不能创建/确认/继续交换联系方式，也不能查看联系方式。
5. **申诉不绕过审核**：不改内容的申诉只能走 `rejected → appeal_pending → needs_manual_review → published/rejected`；改稿必须走 `rejected → draft → pending_review`。`appeal_pending` 不得直达公开。
6. **隐私最小化**：状态解释只给用户下一步，不解释内部规则命中值、模型判断或审核人员细节；未成年人友好，不使用羞辱、定罪或“你违规了”的语气。

### 1.1 允许与禁止转换（UI 必须与服务端结果一致）

| 允许转换 | UI 可见结果 | 明确禁止的 UI 假象 |
| --- | --- | --- |
| `draft → pending_review` | 显示“已提交审核 / 审核中”，不显示“已发布” | 草稿卡片出现在公开列表或公开详情 |
| `pending_review → published` | 显示“审核通过，内容已公开” | 仅凭提交成功、前端标志、AI allow 或超时显示公开 |
| `pending_review → rejected` | 显示“需修改后重新提交”，不显示命中原文 | 在卡片上写出手机号、微信号、邮箱等具体命中值 |
| `pending_review → needs_manual_review`；`needs_manual_review → needs_manual_review/published/rejected` | 显示等待/人工复核；两者均不公开，只有当前版本可追溯决定才能离开人工状态 | 以“系统处理中”掩盖永久失败或自动放行 |
| `rejected → appeal_pending` | 显示申诉已提交、等待人工复核 | 申诉提交后立即恢复公开、聊天或联系方式 |
| `rejected → draft → pending_review` | 改稿后重新提交新版本 | 复用旧 contentHash 或旧通过结果 |
| `published → deleted → pending_review` | 删除后恢复进入重新审核 | “恢复”按钮直接标记已公开 |

## 2. 七状态生命周期展示矩阵

下表是建议的 UI 基线。`用户标签`、`主文案`、`动作`均是候选设计，业务确认前不得视为最终生产文案。

| 内部状态 | 用户标签（候选） | 状态卡主文案（候选） | 默认可见性 | UI 动作与限制 | 聊天/联系方式 |
| --- | --- | --- | --- | --- | --- |
| `draft` | 草稿，尚未提交 | `这份内容还没有提交审核，当前不会公开。` | 仅 owner 在本人列表/编辑入口可见 | `继续编辑`；若已有草稿提交能力，主按钮为 `提交审核`；不得出现 `立即发布` | 不创建新的公开关系；无联系方式 |
| `pending_review` | 审核中 | `已收到提交，正在快速审核。审核通过后才会公开；审核期间其他人不可见。` | 仅 owner；不出现在公开列表/详情 | 显示只读状态和 `刷新状态`（如产品确认允许）；提交锁定；不提供绕过审核的发布按钮 | 不恢复新聊天/联系方式交换 |
| `needs_manual_review` | 需要人工复核 | `需要进一步人工复核，复核完成前不会公开。请稍后查看状态。` | 仅 owner/受控人工角色；不公开 | 普通用户只可查看状态；不允许重复创建队列；可显示 `刷新状态`，不显示“加急”或“找客服”能力 | 不公开、不恢复聊天或联系方式 |
| `published` | 已公开 | `审核通过，内容已公开。` | 按既有公开权限展示 | `编辑内容` 会生成新版本并重新审核；编辑辅助文案：`保存后会先审核新版本，当前已公开内容会继续保留。` | 沿用既有 ISSUE-0033 权限；不因本状态自动交换联系方式 |

| `appeal_pending` | 申诉处理中 | `申诉已提交，等待人工复核。复核完成前不会公开，也不会恢复聊天或联系方式。` | 仅 owner/受控人工角色 | 默认只显示 `查看状态`；`撤回申诉` 先隐藏/禁用，是否允许及其目标状态必须业务确认 | 不公开、不恢复聊天或联系方式 |
| `deleted` | 已删除 | `内容已删除。恢复后会重新审核，审核通过前不会公开。` | 仅 owner 在恢复窗口内可见；公众看不到状态细节 | 48 小时恢复窗口内可显示 `恢复并重新审核`；过期或版本/权限失配不显示恢复按钮 | 聊天只读；禁止新消息、关系动作和联系方式查看 |

### 2.1 对外未授权访问

当非 owner 访问 pending、manual、rejected、appeal 或 deleted 记录时，页面不返回状态细节、拒绝原因或时间信息。统一候选文案为：

> `当前内容不可见或已下线。`

该文案不暗示记录是否存在，也不泄露用户是否被拒绝。公开详情只允许服务端返回 `published` 快照。

## 3. 操作、文案与失败路径矩阵

### 3.1 提交、等待与成功

| 场景 | 候选用户文案 | UI 语义与验收要求 |
| --- | --- | --- |
| 草稿提交前 | `提交审核` | 使用真正的提交控件；按钮附近保留简短说明“审核通过后才会公开”。 |

| 人工队列不可用 | `审核服务暂时不可用，内容仍未公开。请稍后查看状态。` | 错误靠近当前操作；不展示队列名称、内部错误码或人工联系方式；重试受同步锁和退避控制。 |
| AI/外部审核服务不可用 | `审核服务暂时不可用，内容仍未公开。系统会在可安全处理时继续审核。` | 不向普通用户暴露“AI、供应商、模型、地域或预算熔断”；服务端只能保持 pending/manual。 |
| 审计写入失败 | `审核暂时无法完成，内容仍未公开。请稍后查看状态。` | 不允许前端重试绕过审计；告警和重试属于内部流程。 |

## 4. 可访问性与交互验收设计

### 4.1 焦点与键盘

- 页面进入状态：焦点顺序为统一 Header 返回键 → 页面标题/状态摘要 → 内容摘要 → 当前允许的动作。不要新增第二个内容区返回入口；返回键按真实访问历史返回，不把视觉稿写死为首页。
- 提交成功：将焦点移到唯一状态摘要（若用户仍在输入且无错误，不抢走输入焦点）；状态摘要有稳定 `id`，避免重复 live-region。
- 拒绝/失败：错误提示放在对应提交或申诉按钮下方；使用 `aria-describedby` 关联按钮/表单，必要时把焦点移到第一个无效字段或错误摘要。
- 申诉对话框（只有业务确认允许该模式时）：打开后焦点进入标题或第一个必填项；Tab 不得逃出对话框；Escape 关闭；关闭后焦点回到触发按钮。
- 所有动作可用键盘完成；Enter 在表单内只产生一次提交；Space/Enter 不触发重复队列；二级动作使用明确的 button 语义，不用可点击的纯文本。
- 触控目标不低于 `44×44px`；移动端按钮可换行但不被状态卡、阴影或底部安全区裁切。

### 4.2 live-region、错误关联与视觉表达

| 信息级别 | 语义 | 推荐用法 |
| --- | --- | --- |
| 普通状态 | `role=status`、`aria-live=polite`、必要时 `aria-atomic=true` | pending、manual、published、appeal_pending 的状态变化 |
| 需要立即处理 | `role=alert`、`aria-live=assertive` | 提交失败、队列不可用、版本冲突、恢复失败 |
| 字段错误 | 字段 `aria-invalid=true` + `aria-describedby` | 申诉原因缺失、补充说明超长等局部错误 |
| 正在处理 | 区域 `aria-busy=true` + 原生 disabled | 提交/申诉/恢复进行中；文案显示“处理中…” |

- 同一状态只保留一个可读摘要，避免状态徽章、横幅和 Toast 重复朗读。
- 状态不能只靠颜色或图标区分；必须同时显示中文标签、可读文案和可访问名称。
- 不在 live-region 中放完整用户正文、联系方式、命中片段、模型输出、供应商名或内部 reasonCode。
- 被动轮询更新状态时不抢焦点；状态变化应保持阅读顺序稳定，避免页面跳回顶部。

### 4.3 重复提交锁与安全失败

1. 用户点击、Enter 或辅助技术触发提交时，先同步设置本地锁，再发异步请求。
2. 锁定期间按钮 disabled，文案从 `提交审核/提交申诉/恢复并重新审核` 变为 `提交中…/申诉提交中…/恢复中…`。
3. 同一 `owner + entity + contentVersion + contentHash + idempotencyKey` 的重试只返回既有结果，不生成第二个审核任务、通知或公开版本。
4. 网络、队列、AI、审计或版本异常只解除到可安全的 pending/manual/error 状态；不能在客户端切到 published。
5. 错误消息持续可见，直到用户重新发起合法动作或服务端返回新的状态；不能因刷新或路由跳转悄悄消失。

- 状态面板位于本人记录标题与内容摘要之间，作为独立浅色框体；状态标签、标题、主文案和操作按“标签/标题 → 说明 → 操作”垂直层级排列，外框边界不被标签或阴影压住。
- 宽屏状态卡可采用“左侧内容摘要 + 右侧状态/动作”两列；状态/动作列保持足够宽度，错误提示紧贴对应按钮下方。`published` 编辑提示与状态不能挤压主内容。
- 操作组同一视觉基线：主动作在前，次动作间距至少 `12px`；若文案较长可换行，不允许按钮互相覆盖或贴外框边缘。
- 任何设计标注、测试数值、`PREVIEW ONLY` 说明只存在于设计证据包装层，不进入正式页面高度或可访问树。

### 5.3 移动布局（重点 390px）

- 状态卡单列：状态标签/标题 → 主文案 → 辅助说明 → 操作；操作按钮按全宽或等宽纵向排列，触控目标至少 `44px` 高。
- 允许长文案自然换行；不通过缩小生产字号、负 margin 或横向滚动解决拥挤。状态卡、按钮、live-region 和底部安全区均必须 contained。
- 状态更新不改变页面滚动位置；错误焦点进入可见区域，状态更新后不把用户带回页面顶部。
- 390px 必须满足 `document.clientWidth === document.scrollWidth`；状态徽章、按钮文本和说明均不能出现裁切、溢出或与 Header/底部区域重叠。
- 桌面双列折叠为移动单列后，动作顺序保持“当前状态说明 → 主要安全动作 → 次要动作”；不把“申诉”置于“修改内容”之前，除非业务确认另有优先级。

## 6. 可安全先冻结与必须业务确认

### 6.1 可安全先冻结的 UI 骨架（不等于业务接受）

| 可冻结项 | 冻结口径 | 失败时的保守结果 |
| --- | --- | --- |
| 状态标签集合 | 内部键值固定为 `draft/pending_review/needs_manual_review/published/rejected/appeal_pending/deleted`；用户标签候选为 `草稿/审核中/需要人工复核/已公开/需修改后重提/申诉处理中/已删除` | 未知状态显示“状态暂不可用，当前不会公开”，不猜测为已公开；#12 owner 未确认时可先使用“需要进一步复核”而不承诺人工 SLA |

| AI 对用户的表达 | 用户只看到“审核服务暂时不可用/继续处理”，不看到 AI/供应商细节 | 服务异常保持 pending/manual |

### 7.2 每张截图/每个 DOM 证据必须记录

- 路由、登录角色（需求方/老师/非 owner）、状态、`contentVersion`/公开快照关系（只记录非敏感标识）。

## 8. UI 失败判据（任一项即 `UI_REWORK_REQUIRED`）

1. pending、manual、rejected、appeal 或 deleted 出现在公开列表/公开详情，或显示“已发布/已公开”。
2. `rejected → published`、`appeal_pending → published`、`deleted → published`，或无当前版本人工决定的 manual → published 由 UI 按钮暗示或可触发。
3. 删除态仍能发消息、创建/确认/继续交换联系方式或查看联系方式；申诉/人工状态恢复聊天或联系方式。
4. 文案泄露具体命中规则、敏感正文、联系方式片段、模型分数、提示词、供应商/队列内部信息，或用“你违规了”等羞辱未成年人/家长/老师的表达。
5. 提交/申诉/恢复的按钮在未 hydration、session 未就绪、版本未加载、重复点击或请求进行中仍可造成重复任务；Enter 与鼠标路径不一致。
6. 失败/超时/队列不可用/审核服务不可用后无持续提示，提示离操作太远，或没有可读 `role=alert/status` 与错误关联。
7. 焦点丢失、键盘无法完成操作、对话框形成焦点陷阱、Escape 不可关闭、错误焦点不可见，或状态只靠颜色/图标表达。
8. 390px 出现横向滚动、文本/按钮裁切、状态卡与 Header/底部/阴影重叠；桌面状态列过窄导致文案或动作不可读。
9. 预览标签、测量值、路由注释或“PREVIEW ONLY”污染正式页面，或本稿候选色彩/框体替换既有 D+ 视觉却未获批准。
10. 只给本地测试/截图而没有逐状态的实际 DOM、可访问性和失败路径证据，或把 UI 通过冒充生产/业务验收。

## 9. 交接与当前门禁

- 先使用状态服务端返回值渲染标签和文案；UI 不自行推断审核结果，不新增“直接发布”旁路。
