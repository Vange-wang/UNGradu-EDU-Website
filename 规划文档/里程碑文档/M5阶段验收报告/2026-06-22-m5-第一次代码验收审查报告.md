## 1. 验收结论

M5 第一次代码验收结论：**暂不通过**。

本轮 M5 代码已经完成大量关键安全迁移：

- 新增 CloudBase 服务端 SDK 连接和本地环境变量说明。
- 新增 CloudBase 集合检查脚本，并成功读取测试环境集合。
- 将联系方式存档、家长需求、家教信息、会话、消息、联系方式交换迁移到服务端 API。
- 业务 API 优先读取 HttpOnly 签名 Cookie，不再由前端 API client 主动传入测试用户手机号。
- 服务端按 `ownerUserId`、`participantUserIds` 和请求方向校验数据归属。
- 公开列表和公开详情使用白名单 View Model，不返回 `ownerUserId` 或联系方式。
- 未授权前，联系方式交换接口返回 `null`，非会话参与者无法读取消息、交换请求或授权联系方式。
- 生产环境模拟构建中，即使设置 `NEXT_PUBLIC_ALLOW_TEST_LOGIN=true`，临时测试登录仍不会重新启用。
- 本地服务端核心流程和 50 并发模拟测试通过。

但 M5 是“安全和发布前验证”，不仅是代码迁移。本轮仍缺少两类发布前验收所需证据：

1. **尚未完成 CloudBase 云托管或 Web 应用托管部署后的真实 API 闭环验证。**
2. **50 并发基础压测目前只覆盖本地 fake collection 的服务端模块，不是部署环境或真实 CloudBase API 的并发验证。**

因此，本轮可以判定为：**代码级安全迁移基本达标，但发布前 M5 验收证据不足，暂不通过。**

### 3.3 数据归属和越权校验

服务端接口已按以下规则实现：

- `contact_profiles`：只读写当前登录用户自己的联系方式档案。
- `parent_needs`：保存时强制使用当前用户作为 `ownerUserId`；我的列表只按当前用户查询；公开视图不返回 `ownerUserId`。
- `tutor_profiles`：保存时强制使用当前用户作为 `ownerUserId`；我的列表只按当前用户查询；公开视图不返回 `ownerUserId`。
- `conversations`：按来源对象 owner 建立参与者；非参与者不能读取会话、读取消息或发送消息。
- `contact_exchange_requests`：只有会话参与者可发起和查看；只有接收方可同意/拒绝；只有发起方可撤回。
- `authorized-profiles`：未同意、未二次确认、请求过期/拒绝/撤回或非参与者场景下均返回 `null`。

### 3.4 联系方式保护

已确认：

- 公开需求和家教信息 View Model 不返回 `ownerUserId` 或联系方式。
- 会话和消息 View Model 不返回参与者用户 ID 或联系方式。
- 交换请求 View Model 只返回 `direction`，不返回 requester/receiver 用户 ID 或联系方式。
- 授权联系方式接口只有在存在已同意且完成二次确认的请求后才返回双方联系方式。

判断：未授权联系方式不可通过当前服务端 API 获取，代码级验收通过。

## 4. 阻塞问题

### P1：尚未完成部署环境下的真实 API 闭环验证

Spec M5 要求：

- 核心流程全部走通。
- CloudBase 免费额度和部署方式经过验证。
- 已完成发布、筛选、聊天、交换联系方式流程的发布前验证。

当前已完成的是本地 Next.js 构建、服务端模块测试和 CloudBase 集合读取；但本轮未看到以下证据：

- CloudBase 云托管或 Web 应用托管部署成功记录。
- 部署后 `/api/*` 路由可在真实托管环境访问。
- 真实托管环境中完成登录、发布、筛选、聊天、交换联系方式闭环。
- 真实托管环境中的 `AUTH_SESSION_SECRET`、CloudBase 密钥和生产/测试环境变量配置校验。

风险：

- 本地 `next build` 通过不能等同于 CloudBase 托管部署通过。
- 本地 API 可以读取 CloudBase 集合，不能等同于部署环境中的 API 路由、Cookie、安全头、环境变量和网络权限都可用。

验收影响：

- 该项阻塞 M5 发布前验收通过。

建议修复：

1. 将当前分支部署到 CloudBase 测试环境或云托管测试服务。
2. 记录部署方式、服务名、访问地址和环境变量配置方式。
3. 在部署地址上完成一次核心闭环验证：登录、发布、筛选、详情、聊天、交换联系方式、二次确认、授权展示。
4. 将结果追加到 M5 第二轮复验报告。

### P1：50 并发基础压测尚未覆盖真实 API 或部署环境

Spec M5 要求：

- 已完成 50 并发核心流程基础压测，且发布、筛选、聊天、交换联系方式流程正常响应。

当前 `npm run m5:load` 复用 `m5-server-flow-and-load.test.ts`，使用 fake collection 直接调用服务端模块。它可以证明业务函数在本地内存模型下的并发安全和权限返回不乱，但尚不能证明：

- Next.js API route 层在并发请求下正常。
- CloudBase SDK 真实读写在并发下正常。
- CloudBase 测试环境在 50 并发下响应稳定。
- Cookie 认证、HTTP 请求、部署网关、数据库查询在端到端链路下正常。

验收影响：

- 当前只能认定为“50 并发服务端模块模拟通过”，不能认定为“发布前 50 并发基础压测通过”。

建议修复：

1. 使用 k6、Artillery 或等价脚本对部署后的 API 地址发起 50 并发基础压测。
2. 至少覆盖：登录、发布需求、发布家教信息、筛选、创建会话、发送消息、发起和同意联系方式交换。
3. 记录压测命令、目标地址、并发数、成功率、错误率和关键接口响应情况。
4. 将结果追加到 M5 第二轮复验报告。

## 5. 非阻塞观察

### 5.1 `m5:cloudbase:collections` 未检查 `users` 集合

当前 `npm run cloudbase:check` 默认读取 `users` 集合，并已通过；`npm run m5:cloudbase:collections` 检查了 6 个业务集合，但不包含 `users`。

由于当前 M5 尚未把真实用户账号写入 `users`，该问题不阻塞本轮。但从 Spec 数据对象看，`users` 属于核心集合，建议后续将 `users` 也纳入 M5 集合检查脚本，避免发布前遗漏。

### 5.2 页面仍显示“测试账号”文案

部分页面仍显示“当前测试账号”相关文案。考虑到当前仍是 M5 测试环境和临时登录态阶段，该项不阻塞本轮代码验收。但正式 MVP 发布前，如果采用真实手机号登录，应同步替换为更正式的账号文案。

### 5.3 正式短信验证码仍未接入

本轮通过 HttpOnly 签名 Cookie 解决了“前端 localStorage 登录态不可信”的问题，但登录入口仍是测试验证码 `000000`。生产环境禁用测试登录已经通过；正式上线前仍需补充合规手机号短信登录或明确上线阶段仍处于受限测试环境。
