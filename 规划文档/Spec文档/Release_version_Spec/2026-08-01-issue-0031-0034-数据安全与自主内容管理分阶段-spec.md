## 1. 背景、目标与边界

### 1.1 背景与当前事实

生产 044 已承载发布、公开列表、站内聊天、联系方式交换和邮箱登录等既有闭环。当前仓库可确认的事实为：

- 家长需求与家教信息均存放于 CloudBase 文档集合 `parent_needs`、`tutor_profiles`，记录包含不可由客户端指定的 `ownerUserId`、`id`、`status: published` 与 `createdAt`；公开输出不含所有者标识。
- 已有“我的”列表与本人修改端点，服务端以会话导出的用户 ID 比对 `ownerUserId`；现有模型没有删除状态、版本号、`updatedAt`、恢复期限或审计事件的正式契约。
- 站内聊天使用会话、消息、联系方式档案和联系方式交换请求集合；发布记录与聊天创建有关联。现有隐私原则仍为：公开列表与详情不展示直接联系方式，交换必须在站内沟通并二次确认后发生。
- 邮箱验证码使用 CloudBase 的 `email_login_codes`、`email_login_users`；当前验证码有效期和使用状态由服务端处理，但发送接口前尚未有“浏览器挑战成功后由服务端验证”的人机验证信任链。
- 会话 Cookie 使用服务端密钥、`HttpOnly`、`SameSite=Lax`，生产启用 `Secure`；CloudBase 服务端访问依赖环境变量，不得把任何真实值写入仓库或本文。
- Worker 已承担公开入口、源站校验和部分安全响应头职责。其正确生产配置属于证据核验范围，不可仅据源代码推定已生效。

以上仅描述本次读取时的实现起点；集合完整清单、生产数据量、实际索引、备份可用性、外部服务套餐、地区与成本尚未由仓库充分证明，列入实施前决策门。

## 3. 阶段 1：ISSUE-0033 本人已发布内容管理

### 3.1 产品契约

适用对象是当前认证主体自己创建的 `parent_needs` 与 `tutor_profiles` 记录。本人列表默认显示有效记录，详情/编辑入口只能从本人列表进入；公开列表和公开详情只显示 `published` 状态且不含内部所有者字段。未登录访问本人列表、编辑、删除或恢复返回 `401`；面向非所有者，记录不存在、已删除或无权访问统一返回 `404` 和统一产品文案，避免对象枚举。

| 能力 | 必须行为 | 不得行为 |
| --- | --- | --- |
| 查看本人列表/详情 | 服务端以会话主体过滤；显示状态、创建/最近更新时间和可操作项 | 用客户端 owner 参数或公开详情代替本人详情 |
| 修改 | 仅本人可提交经过既有字段校验的完整/明确部分更新；成功返回新版本和更新时间 | 覆盖 `ownerUserId`、创建时间、删除审计或服务端状态 |
| 删除 | **已确认采用软删除**：记录立即从公共与本人“有效”视图消失；`deletedAt` 后 **48 小时内可恢复**，保留最小 tombstone、审计和关系追溯 | 在 48 小时窗口、备份、审批和审计条件不满足时物理删除 |
| 恢复 | **已确认**仅原所有者在 `deletedAt` 后 48 小时内发起；再次校验所有权、版本和当前状态 | 超期、非所有者或已受控清理时静默成功 |

**D1 已确认的实施口径**：业务方所称“保留 2 天”按可测试且不受时区影响的 **`deletedAt` 后 48 小时内可恢复**解释，不按自然日零点计算。字段至少包含 `status: deleted`、`deletedAt`、`deletedByUserId`、`updatedAt`、`version`；常规用户不填写自由文本删除理由。48 小时到期后才允许进入受控物理清理，仍需备份可恢复、审批、审计和批次范围证据；更长的法律/投诉保留要求若适用，须在 0033 实施前另行确认。

### 3.2 聊天与联系方式交换的关系

删除发布记录不是删除删除前的聊天记录；以下 D2 操作语义已由业务方确认：

1. 删除后该记录不得继续出现在公开列表、公开详情或作为新建聊天/交换请求的来源。
2. 删除期间，原会话参与者仍可读取删除前已存在消息，页面提示“关联发布已删除”；该会话转为只读，禁止发送新消息。
3. 删除期间禁止新建、确认或继续任何联系方式交换；即使过去已完成交换，也不得通过该删除来源继续查看联系方式。
4. 合法恢复发布记录后，必须重新校验所有权、会话参与者、记录状态和版本，才可恢复聊天/联系方式相关能力；恢复不得自动创造新的披露，也不得改变历史审计。

聊天、交换请求与发布记录之间的多集合更新须在同一事务中完成；若当前存储不支持足够原子性，实施前必须提出补偿事务、重试和人工修复方案并经技术/业务方确认。删除、恢复、只读门控、联系方式限制和审计必须幂等，任何部分失败均不得留下“页面可继续发送/查看联系方式”的放行状态。

### 3.3 API、数据与并发约束

| 主题 | 最小契约 |
| --- | --- |
| 主体 | `authenticatedUserId` 仅来自已验证会话；服务端读取后与记录 `ownerUserId` 比较 |
| 标识 | 路由中的记录 ID 是定位线索，不是授权；保持不透明 ID |
| 状态 | `published`、`deleted` 为第一阶段最低状态；任何新增状态须有迁移、显示与权限定义 |
| 乐观并发 | 读取返回 `version`；修改/删除/恢复必须携带期望版本或等价条件。版本不符返回可识别冲突，不丢失后写入 |
| 幂等 | 删除、恢复和关联状态转换带 `Idempotency-Key` 或服务端等价去重键；重复请求返回原始最终结果，不重复写审计或触发通知 |
| 时间 | 服务端写 UTC ISO-8601；客户端只格式化显示，不能作为排序/授权依据 |
| 错误 | 未登录 `401`；面向非所有者，记录不存在、已删除或无权访问统一 `404` 与统一产品文案；冲突 `409`；校验 `400/422`。错误不泄露 owner 或联系方式 |
| 防伪造 | 写操作校验 Origin/CSRF 策略、内容类型、大小、字段白名单与速率限制 |
| 审计 | 追加式事件至少含事件 ID、目标类型/ID、操作者 ID、前后状态摘要、版本、时间、结果、关联请求 ID；敏感内容仅摘要/哈希 |

实施前须先盘点现有记录缺失 `updatedAt/version` 的情况，并给出向后兼容读法。旧记录按已确认 D8 只读隔离，不能被“无版本”绕过并发控制。

**安全隔离的最低不变量（D8 已确认）**：缺失 `version/updatedAt` 的旧记录只读隔离，向本人提示重新发布以启用管理；隔离不是静默隐藏、物理删除或切断关系的替代做法。记录仍按既有读取权限可读、可审计，并保留与既有聊天和联系方式交换的关联；本人必须可见“暂不可管理”的限制说明。隔离记录不得接受修改、删除或恢复等依赖 `version` 的写操作，也不得以缺失字段绕过并发检查；重新发布必须生成/确认受版本控制的新记录并留下审计。

## 4. 阶段 2A：ISSUE-0031 SQL 数据库迁移选型与实施

### 4.1 当前起点与决策原则

当前可确认的持久化起点是 CloudBase 文档集合（包括内容、会话/消息、交换请求、联系方式档案、邮箱用户/验证码及反馈等），不是已确认的 SQL 数据库。实际集合数量、字段、索引、数据量、TTL、地域、导出能力和恢复点目标尚未证实，不能据旧文档或命名假设。

迁移的目标是数据一致性、可审计关系、查询与运维可控性；不是为“使用 SQL”而迁移。推荐先做可重复只读盘点与样本脱敏导出，再以如下矩阵和成本/合规证据作业务选择。

| 候选 | 优势 | 主要代价/风险 | 适用前提 | 当前推荐 |
| --- | --- | --- | --- | --- |
| 托管 MySQL 8.x | 常见运维技能与生态、事务/约束成熟，适合关系型内容和审计 | 模式迁移、连接数、跨平台网络、备份与成本需实测 | 与 CloudBase/Worker/Next 的私网或受控网络、备份恢复和地域合规均满足 | 业务方已表达倾向；供应商/地域/预算/RPO/RTO 仍未定案 |
| 托管 PostgreSQL | 约束、JSON/全文与扩展能力强，工具完善 | 团队运维能力、托管可用性、连接池和成本需确认 | 同上，且有明确接入与灾备方案 | 等权备选 |
| 保留 CloudBase 文档存储并强化模型 | 改动较小、贴近当前实现 | 复杂关系/事务/对账能力可能受限，不能自动满足迁移诉求 | 盘点后证明可满足 0033 和安全/运维目标 | 作为“不迁移”对照方案 |
| 其他托管兼容 SQL | 可能贴合成本或区域要求 | 锁定、兼容性与迁移工具差异 | 完整 PoC、合规、恢复和预算证据 | 仅在上述方案不满足时评估 |

业务方已确认 D4 的方向为“倾向 MySQL”，但最终数据库供应商、地域、主从/高可用等级、RPO/RTO、预算上限、停机容忍、数据保留和供应商合同，仍须先完成证据矩阵并在 ISSUE-0031 实施前由业务方确认；这些未决项不阻塞先行 ISSUE-0033。

### 4.2 目标数据模型与约束

实现前以源集合盘点为准完成字段映射；最低关系模型应包括 `users`、`parent_needs`、`tutor_profiles`、`conversations`、`conversation_messages`、`contact_profiles`、`contact_exchange_requests`、`email_login_codes`、`risk_feedback`、`audit_events` 与 `migration_runs`。不将当前未盘点字段擅自丢弃。

- 每表使用不可枚举的稳定主键（UUID/ULID 二选一，推荐 UUIDv7 或可排序 ULID）；外键明确所有者、会话参与者、来源内容和审计关联，关键外键默认限制或受控软删，禁止级联物理删除聊天证据。
- 对 `owner_user_id`、`status`、`created_at`、`updated_at`、`deleted_at`、`version` 建立与查询模式对应的复合索引；公开排序、本人列表、会话参与者、未完成交换、验证码限流/过期清理和审计追溯均须由 EXPLAIN/负载测试证明。
- 金额使用定点整数最小单位或 `DECIMAL`，不得使用二进制浮点；所有服务器时间以 UTC 存储，客户端按时区显示；文本采用 `utf8mb4` 与明确排序规则。
- 发布删除、聊天来源标记、交换状态、审计和幂等记录在同一事务；验证码验证/占用与账户写入也须原子或有可证明的补偿机制。
- 数据库权限最小化：应用读写账户、迁移账户、只读报表账户、备份/恢复账户分离；生产禁止使用超级用户作为应用连接。

### 4.3 迁移、对账、恢复与回滚

1. **只读发现**：登记集合/字段/数据量/时间范围/脏数据/引用关系/现有索引/敏感等级，生成脱敏基线快照与源-目标映射。
2. **设计冻结**：业务方确认选型、停机或双写策略、RPO/RTO、保留期和预算；技术复核确认容量、网络、连接池、密钥与恢复演练可行。
3. **演练**：在隔离测试/预生产以生产形态脱敏样本全量迁移，执行 schema、校验、对账、故障注入和恢复；每次迁移有不可复用运行 ID。
4. **切换策略**：业务方已确认采用经演练的“短暂写冻结 + 单源切换”，避免未证明正确的长时间双写。若未来改为近零停机双写，必须重新形成业务方确认，并先定义单一权威源、顺序/重放/幂等、延迟阈值、冲突裁决、影子读与停写回退，完成两次成功演练后才可采用。
5. **生产迁移**：先验证加密备份可恢复，再停止或受控排队写入；导入、约束校验、记录数/主键集合/业务聚合/抽样内容哈希对账均通过后切流。旧源只读保留到观察期结束。
6. **回滚**：在预先定义的不可逆 schema/数据步骤前设 GO/NO-GO 点；发生对账差异、权限错误、性能阈值越界或审计缺失时回到旧源，记录影响窗口并重放经核准的写入，绝不以“看起来可用”跳过对账。

备份至少包括加密静态副本、异地/跨故障域策略（由业务方和平台能力决定）、定期恢复演练和恢复审计。只有实际恢复到隔离环境并完成完整性验证的记录才算“可恢复”。

### 4.4 0031 验收与完成定义

本地需有 schema/映射/迁移单元测试；集成需在隔离环境完成一次可重复迁移、对账、失败注入和恢复；预生产需完成容量与连接池压测、权限测试、备份恢复演练；生产需有批准单、切换记录、源目标对账、监控观察期和独立复核；业务方需确认成本、停机/风险与结果。任一数据丢失、重复、越权、无法恢复、RPO/RTO 未达标或对账解释不清即为阻塞，不得关闭 0031。

## 5. 阶段 2B：ISSUE-0032 邮箱验证码发送前的人机验证

### 5.1 信任边界与成功链路

浏览器挑战只负责获取短时 token；它不是授权证明。服务端才是唯一裁决点：

```text
浏览器请求挑战（指定 action）
  → 浏览器携带 token 与邮箱发送请求
  → 服务端校验会话/请求格式/限流
  → 服务端向验证提供商核验 token
  → 服务端核对 success、hostname、action、签发时间、一次性使用与风险结果
  → 全部通过后，才创建并发送邮箱验证码
```

D6 方向已确认优先评估 Cloudflare Turnstile/等价服务，服务端强制校验、fail-closed、最小化 IP；最终供应商、允许域名、精确 token 时效、IP 精确保留期、无障碍替代、地区可用性、成本和生产监控仍须在 0032 接入前完成证据评估与业务确认。验证结果必须绑定 `email_send_code` 之类的明确 action、允许域名和短时效（推荐从签发到服务端验证不超过 5 分钟，以提供商限制为准），并以 token 哈希/挑战 ID 在服务端记录一次性消费。不得记录原始 token。

### 5.2 Fail-closed、防绕过与隐私

- token 缺失、格式错误、网络/服务端校验失败、`success=false`、hostname/action 不匹配、过期、已使用、风险等级不达标或验证服务不可用时，均不创建也不发送验证码；返回不泄露绕过线索的错误。
- 浏览器不得持有验证私钥。服务端验证私钥只在相应环境的 Secret 管理中存在，必须轮换、最小授权、审计读取；公网日志、前端 bundle、错误响应与测试夹具均不得出现它。
- 发送端还必须组合按账户/邮箱（哈希或规范化标识）、IP/网络与设备信号的分层限流、冷却时间、单日预算、验证码尝试上限和异常告警。IP 仅在合法必要范围内使用/短期保留并脱敏；精确保留策略仍是 0032 接入前决策门。
- 可访问性不得等于公开绕过：使用提供商可访问挑战能力；若需要人工替代，推荐仅允许受训运营人员通过受审计的后台、短时一次性服务器授权完成，且无用户自助白名单。替代流程、适用地区和响应承诺为实施前决策门。
- 测试环境使用供应商测试 key 与隔离域名；生产切换前复核 hostname/action、环境变量和失败告警。回滚仅能回到已验证的旧**服务端**防滥用策略，不能降级成前端勾选或无验证发送。

### 5.3 0032 验收

| 层级 | 必须可复现的证据 |
| --- | --- |
| 本地 | 缺 token、伪 token、错误 hostname/action、过期、重复 token、供应商超时、限流命中均不调用邮件发送；有效 token 才恰好创建一次验证码 |
| 集成 | 使用官方测试 key，服务端实际验证；重放、跨环境 token、跨 action token 和并发请求均失败或被幂等处理 |
| 预生产 | 与预生产域名/Secret/监控连通，验证失败率、发送量、延迟和限流有脱敏指标；无障碍路径被独立操作验证 |
| 生产 | 生产域名/action 强制生效，失败时无邮件发出，密钥未泄露，告警可达；采用受控邮箱端到端验证 |
| 业务方 | 确认可接受的摩擦、可访问替代、隐私/保留与成本 |

## 6. 阶段 2C：ISSUE-0034 全站安全基线与加固

### 6.1 威胁模型与控制分层

安全是持续过程。以下矩阵定义最低验证面，而不是绝对安全承诺。

| 威胁面 | 最低控制 | 主要层 | 可验证证据 |
| --- | --- | --- |
| 认证/会话 | 强密钥、签名验证、Cookie `HttpOnly/Secure/SameSite`、失效/登出、生产禁用测试登录 | 仓库+平台 | 代码审查、会话负例、生产 Cookie/路由验证 |
| 授权与对象级权限 | 每个读写目标服务端按会话主体授权，拒绝 IDOR、批量枚举与客户端 owner 声明 | 仓库+生产 | 本人/非本人/匿名矩阵、审计与渗透式负例 |
| 输入输出 | schema 白名单、长度/类型限制、编码输出、富文本策略、上传文件校验 | 仓库 | 单元/集成攻击样本与 UI 输出检查 |
| CSRF/XSS/CSP | 写请求 Origin/CSRF 策略，安全编码，CSP 逐步收紧并报告违反 | 仓库+Worker+生产 | Header/Dom 测量、报告端点、攻击样本 |
| SQL/注入 | 参数化查询、最小 DB 权限、迁移审查、禁止拼接 SQL/命令 | 仓库+数据库 | 静态扫描、负例、DB 权限清单 |
| SSRF/出站访问 | URL allowlist、禁止内网/metadata、超时/重定向限制、出站审计 | 仓库+平台 | 负例和网络策略证据 |
| Secret | Secret manager、环境隔离、轮换、最小读取、扫描与事故处置 | 平台+仓库 | 不含值的变量清单、轮换/扫描记录 |
| 滥用/DoS | 分层限流、配额、队列/超时、WAF/Worker 规则、容量阈值 | 仓库+平台 | 压测、429 行为、告警演练 |
| 依赖供应链 | 锁文件、依赖审计、更新策略、构建来源与 SBOM/版本记录 | 仓库+CI | 审计报告、变更审批 |
| 日志/监控 | 结构化脱敏日志、请求关联 ID、异常/权限/备份告警和保留策略 | 仓库+平台 | 脱敏抽检、告警演练 |
| 备份/恢复 | 加密备份、RPO/RTO、定期恢复演练、不可变审计 | 平台+运维 | 恢复演练与对账 |
| 隐私/未成年人 | 数据最小化、公开字段审查、联系方式隔离、访问/删除/保留流程 | 产品+仓库+平台 | 数据清单、权限矩阵、业务方确认 |

### 6.2 Cloudflare、Worker、CloudBase 与源站隔离

Worker 的 Header、规范域名、源站验证与 WAF/边缘策略必须通过实际生产请求验证；CloudBase/数据库服务凭证必须仅由服务端受控使用；源站不得因直连、伪造 Host、绕过边缘或泄露上游而暴露。平台配置变更、DNS、证书、WAF、Secret、数据库网络规则与备份策略均为平台操作，不能用仓库代码或截图替代。

### 6.3 与 ISSUE-0020 的边界

| 项目 | 本 Spec/0034 负责 | ISSUE-0020 仍独立负责 |
| --- | --- | --- |
| 安全设计与验证框架 | 定义威胁模型、控制、证据、生产验收标准 | 不因定义框架而解除已有外部阻塞 |
| 生产凭据与外部整改 | 要求最小权限、轮换、验证与记录 | 已登记的外部凭据轮换、已登录反馈成功、回滚入口与业务方残余风险接受 |
| 状态 | 0034 的实现/验收另行授权和关闭 | 仍为 `open / EXTERNAL_BLOCKED`，由 ISSUE 管理员维护 |

0034 不能宣称解决 0020，也不能用 0020 未关替代 0034 的实现证据；二者在生产发布门禁中按各自责任并列检查。

### 6.4 0034 验收、观察与完成定义

先建立资产/数据流/信任边界清单和按风险排序的控制台账，再逐项实施和验证。D7 方向已确认，但具体 owner、演练频率、数据保留期、告警阈值和证据格式须在 0034 实施前形成可验收值。每项控制记录 owner、配置位置、变更审批、负例、监控、回滚与复测日期。高风险认证、越权、公开联系方式、Secret 泄露、注入、源站绕过、恢复失败或未成年人数据不当暴露为阻塞。生产至少经过已确认的观察期并无未处理高危告警，独立复核和业务方风险确认完成后，才能进入 0034 关闭复核。

## 8. 统一交付、门禁与证据规则

### 8.1 从 Spec 到实施的门禁

1. 本 Spec 完整草案形成并自检。
2. 总负责人冻结 canonical hash 后组织 Hermes 关键文档审查；最多三轮，不能用本草案替代审查。
3. 每一轮 Hermes 审查若发现 `SERIOUS`，必须将**本轮全部** `SERIOUS` 集中成该轮唯一批次，交 Document QA 一次性批量整改后再进入下一轮 Hermes 审查；Round 2 的 residual/new `SERIOUS` 仍按同一规则形成该轮唯一批次。仅 `NON_SERIOUS` 问题可以登记为非阻塞台账，不触发 QA 修订。第三轮审查后仍有未关闭 `SERIOUS`，进入 `DOCUMENT_REVIEW_LIMIT_REACHED`，禁止自动第四轮，由业务方决定。
4. 业务方确认本 Spec 的决策门、0033 删除/恢复/聊天处理与阶段顺序。
5. 仅 0033 获得实现授权，完成本地、集成、独立产品/UI、生产和业务方验收，由 ISSUE 管理员关闭，达到 `ISSUE-0033 closed / WORKFLOW_COMPLETE`。
6. 此后才能逐项向业务方申请 0031、0032、0034 的实施授权；每项按本节独立验证，不能共享“已通过”结论。
