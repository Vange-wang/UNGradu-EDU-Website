# 登录系统顺利落地方案变更说明：邮箱验证码

日期：2026-06-27

任务 ID：`LOGIN-RUN-2026-06-27-001-CHANGE-EMAIL`

发起方：项目总控制人

执行 Agent：产品经理 Agent（`019efc62-584b-79a2-90df-808f28ecefce`）

## 1. 变更结论

登录系统顺利落地阶段的正式方案，从“手机号短信验证码登录”变更为“邮箱验证码登录”。

需要代码返工：需要。

返工原因：当前代码侧第一轮实现是手机号短信验证码登录，依赖腾讯云短信签名、模板和短信发送能力；但项目总控制人已确认，个人认证用户无法完成腾讯云国内短信签名 / 模板资质，因此手机号短信正式方案暂时不可落地，不符合新的正式登录目标。

新的产品目标：真实用户可以通过邮箱验证码完成注册、登录、退出，不再依赖 M1 测试登录，也不依赖国内短信签名资质。

## 2. 为什么要改

原方案希望用手机号短信验证码登录。这个方案对用户很直观，但在正式生产中必须依赖短信服务商的签名和模板审核。

现在的问题是：

- 项目当前主体是个人认证用户。
- 个人认证用户无法完成腾讯云国内短信签名 / 模板资质。
- 没有通过审核的短信签名和模板，就不能稳定、合规地给真实用户发送正式登录短信。
- 因此，即使代码里已经做了短信验证码登录，正式环境也无法真正落地。

所以本阶段不再继续把“腾讯云国内短信验证码登录”作为正式上线方案，改为邮箱验证码登录。

## 3. 新目标

本阶段新的目标是：

- 用户可以在正式环境输入邮箱地址。
- 系统向该邮箱发送一次性验证码。
- 用户输入验证码后完成登录。
- 新邮箱第一次验证通过后，系统自动创建账号，等同完成注册。
- 老邮箱再次验证通过后，系统直接登录原账号。
- 登录后用户可以进入家长 / 老师身份入口或后续资料流程。
- 刷新页面后登录状态不丢。
- 用户退出登录后，不能继续访问个人私有数据。
- 生产环境继续禁用测试登录、固定验证码和临时身份头。

## 4. 新验收标准

以下标准必须可操作、可复验。

### 4.1 主流程

- 用户能在正式环境打开登录页。
- 登录页展示邮箱验证码登录，不再展示手机号短信登录作为主方案。
- 用户能输入格式正确的邮箱地址。
- 用户点击获取验证码后，邮箱能收到验证码。
- 新邮箱首次通过验证码后，系统自动创建账号或完成注册。
- 老邮箱再次通过验证码后，系统直接登录原账号。
- 登录成功后能进入家长 / 老师身份入口或后续资料流程。
- 从受保护页面跳转到登录页时，登录成功后能回到原页面或合理目标页。

### 4.2 登录态与退出

- 登录成功后，刷新页面登录状态不丢。
- 登录成功后，可以访问个人页、我的发布、我的聊天、联系方式管理等个人数据。
- 退出登录后，服务端会话被清除。
- 退出登录后刷新页面仍保持未登录。
- 退出登录后不能访问个人数据或私有 API。

### 4.3 验证码安全

- 错误验证码会被拒绝。
- 过期验证码会被拒绝。
- 已使用验证码不能重复使用。
- 频繁发送验证码会被拦截。
- 同一邮箱连续输错验证码次数过多会被限制。
- 验证码不得出现在前端源码、浏览器可见数据、接口响应、日志或报告正文中。
- 邮件服务密钥、验证码密钥、会话密钥不得出现在 Git 仓库或报告正文中。

### 4.4 生产安全边界

- 正式环境必须配置 `APP_ENV=production`。
- `/api/auth/test-login` 在正式环境不可用。
- `M5_ENABLE_HOSTED_TEST_LOGIN=true` 即使误配，也不能打开生产测试登录。
- `NEXT_PUBLIC_ALLOW_TEST_LOGIN=true` 即使误配，也不能展示生产测试登录入口。
- `x-ungradu-test-user-phone` 在生产环境不能作为登录身份。
- 固定验证码 `000000` 不能作为生产验证码。

### 4.5 隐私与泄露

- 登录成功响应不得向不该看到的人泄露完整邮箱。
- 页面、接口响应和报告中应优先展示脱敏邮箱，例如 `a***@example.com`。
- 验证码不得被写入普通日志。
- 邮件服务账号、授权码、API 密钥不得提交到 Git。

## 5. 代码开发员要做什么

代码开发员需要把当前短信登录实现替换为邮箱验证码登录实现。

### 5.1 页面与交互

- 登录页主文案改为邮箱验证码登录 / 注册。
- 输入框从手机号改为邮箱。
- “获取验证码”“登录 / 注册”“重新发送”等交互保留，但文案和校验改成邮箱口径。
- 移除或下线短信验证码登录作为本阶段主流程。
- 保留 `next` 参数跳转能力，登录成功后回到用户原本要去的页面或合理入口。
- 错误提示要让普通用户看得懂，例如邮箱格式错误、验证码错误、验证码过期、发送太频繁。

### 5.2 API 与服务端认证

建议至少提供：

- `POST /api/auth/email/send-code`：发送邮箱验证码。
- `POST /api/auth/email/login`：校验邮箱验证码并登录。
- `GET /api/auth/session`：读取当前登录态，继续复用或兼容现有接口。
- `POST /api/auth/logout`：退出登录，清除登录态。

服务端要求：

- 邮箱格式必须服务端校验。
- 验证码必须有有效期，建议 5 分钟。
- 验证码只能使用一次。
- 同一邮箱不能无限发送验证码，建议至少 60 秒内不能重复发送。
- 同一邮箱或同一 IP 的错误尝试次数要有限制。
- 验证码存储避免明文长期保存，建议只保存哈希、过期时间和尝试次数。
- 登录成功后写入服务端签名 HttpOnly Cookie 或等价安全会话。
- 不允许客户端传入任意 userId 冒充他人。

### 5.3 账号记录

建议形成或复用用户集合，至少能表达：

- 用户唯一 ID。
- 邮箱哈希或邮箱脱敏展示字段。
- 创建时间。
- 最近登录时间。
- 账号状态：正常、禁用、试运行移除等。
- 是否为试运行白名单用户，如采用白名单方案。

注意：

- 当前历史业务身份如果仍以手机号承接，需要给出兼容策略。
- 新邮箱账号与已有业务数据的归属关系必须清楚，不能导致用户看不到原有数据或看到别人的数据。
- 若暂不迁移历史手机号身份，应在代码侧落地说明中写明兼容边界和后续迁移项。

### 5.4 邮件服务接入

代码开发员需要接入发件邮箱服务或邮件服务商。

可接受的接入方式：

- SMTP 发信。
- 邮件服务商 API 发信。
- 由项目总控制人指定的其他正式邮件发送服务。

要求：

- 邮件服务账号、授权码、API Key 只能从服务端环境变量读取。
- 不在前端暴露邮件服务密钥。
- 不在日志中打印完整验证码、授权码或 API Key。
- 邮件发送失败时，给用户返回可理解提示。
- 对邮件服务商异常、配额不足、账号授权失败等情况提供可定位日志，但不泄露密钥。

### 5.5 测试与文档

代码开发员至少补充或更新：

- 邮箱格式校验测试。
- 发送邮箱验证码成功测试。
- 发送验证码频控测试。
- 验证码错误测试。
- 验证码过期测试。
- 验证码重复使用测试。
- 新邮箱首次登录自动创建账号测试。
- 老邮箱再次登录复用账号测试。
- 登录态刷新后仍可读取测试。
- 退出登录后不能访问个人数据测试。
- 生产环境测试登录仍不可用测试。
- 不泄露验证码、邮箱、密钥的测试或审查说明。

同步更新：

- `Code文档/README.md`
- `Code文档/.env.example`
- 代码侧登录系统落地说明
- 开发员工作记录

## 6. 项目总控制人要提供什么

以下事项必须由项目总控制人或其指定负责人提供，代码开发员不得自行编造真实账号或密钥：

- 发件邮箱服务或邮件服务商选择。
- SMTP / API 地址。
- SMTP 端口和加密方式，如适用。
- 发件账号。
- 授权码或 API 密钥。
- 发件人名称。
- 邮件标题和正文模板确认。
- 试运行收件邮箱名单。
- 是否限制只有白名单邮箱可以注册 / 登录。
- 邮件发送额度、失败告警和异常处理联系人。
- 生产环境邮件相关变量配置方式。

真实授权码、API Key、邮箱密码不得写入 Git、规划文档正文或聊天记录。

## 7. 本阶段不做什么

本阶段只解决“可以正常登录”。

明确不做：

- 手机号短信验证码正式登录。
- 腾讯云国内短信签名 / 模板资质推进。
- 企业短信资质办理。
- 密码登录。
- 社交登录，例如微信、QQ、Apple、Google。
- 实名认证。
- 复杂账号体系。
- 手机号换绑。
- 邮箱换绑。
- 多账号合并。
- 支付。
- 评价。
- 审核后台。
- 举报封禁。
- 自动推荐。
- 复杂排课。

以上能力如后续需要，应进入 vNext 或单独 Spec。

## 8. 暂停确认项

遇到以下情况，代码开发员必须暂停并问项目总控制人：

- 邮件服务商未确认。
- SMTP / API 地址未确认。
- 发件账号、授权码或 API Key 缺失。
- 是否只允许白名单邮箱登录未确认。
- 邮件标题或正文模板未确认。
- 邮件发送失败是否需要人工兜底未确认。
- 账号身份从手机号切换到邮箱会影响历史业务数据归属。
- 任何真实密钥被要求写入 Git、报告或聊天记录。
