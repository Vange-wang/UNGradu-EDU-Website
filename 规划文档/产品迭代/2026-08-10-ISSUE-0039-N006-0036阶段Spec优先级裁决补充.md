## 2. 裁决正文（已确认产品口径）

### 2.1 阶段变更 Spec 的专属管辖范围

阶段变更 Spec 只优先管辖以下“项目阶段和外部副作用”事项：

1. **数据库延期**：ISSUE-0031 本轮不迁移；当前 CloudBase 文档数据库保持单一事实源，
   20 CNY/月不批准、不采购、不计费、不迁移、不双写。恢复时另建独立周期并重新取证。
2. **非数据库执行顺序**：按 `ISSUE-0034 非数据库安全切片 → ISSUE-0032 → ISSUE-0036`
   推进；ISSUE-0020 可独立并行取证但不替代阶段门。
3. **付费/平台/生产边界**：非金钱授权不等于 provider、widget、Secret、DPA、预算或
   生产 key 已存在；生产写入、内容公开、验证码发送、AI 出域和人工生产队列均须单独授权。
4. **恢复触发与阶段门禁**：阶段失败、配置缺失、零容忍风险、外部证据缺失时保持
   `no-go/fail-closed`，按阶段 receipt、回滚、观察与业务接受条件恢复；不能以 0036 的
   功能语义绕过阶段门。

阶段变更 Spec 不决定 0036 的字段、检测模式、状态机、申诉、人工裁决、AI 输入边界或
0036 自身验收细则。

### 2.2 ISSUE-0036 专属 Spec 的专属管辖范围

  数据出域、保留和成本门；

### 2.3 两者的关系

两份 Spec 不互相覆盖：

```text
阶段变更 Spec：是否到了可以进入 S3、能否产生外部/生产副作用、数据库/付费边界
        ↓ 只有阶段顺序与非金钱门通过后
0036 专属 Spec：进入 S3 后具体如何审核、如何人工/申诉、哪些数据可出域、如何验收
```

进入 0036 时，必须先满足阶段变更 Spec 的顺序、非金钱和恢复门，再在该阶段内完整服从

的通用 fail-closed 文字删减 0036 的字段、规则、申诉或隐私要求。

## 3. 确定性优先级算法

遇到后续文档、实现或证据解释时，按下列顺序裁决：

1. **更新的业务方明确指令优先**：只有直接、明确且较新的业务指令才能改变本补充或任一
   Spec 的适用边界；须记录原意、日期/任务上下文和影响范围。广泛授权不得被解释为
   数据库、付费、出域、人工 owner 或自动公开的具体批准。
2. **先判定问题类型**：阶段顺序、数据库、预算/付费、平台/Secret、生产写入、恢复/回滚
   属阶段变更 Spec；审核字段、规则、状态、申诉、人工、AI/DPA/出域和审核验收属 0036。
3. **正交适用**：若一个动作同时涉及两类问题，必须同时满足两份 Spec；较严格边界生效。
   例如，0036 的 provider 评估不能绕过阶段的付费/生产门；阶段允许 provider-neutral
   本地 fixture 也不能绕过 0036 的最小输入、规则版本和人工兜底。
4. **同一事项发生直接冲突且没有新的业务指令时**：立即 `fail-closed`，不公开候选内容，
   不发送验证码，不调用未确认外部服务，不采购/开通，不写生产，不改变数据库；状态保留
   `pending/manual/no-go`，由产品经理提交最窄的产品/业务裁决，待确认后再恢复。
5. **不得自行推断“较新”**：提交时间、代码实现、供应商建议、测试通过或代理角色意见
   不能替代业务方明确指令；Issue 管理员只维护状态，不替业务选择冲突方案。
