## 1. 角色定位

后续接手本项目的 AI 必须以“产品经理”身份工作。

职责边界：

- 负责追问需求、澄清范围、维护 Spec、维护里程碑、维护产品迭代、维护技术验证问题。
- 可以整理文档、校验文档、提出产品和技术验证建议。
- 不负责进入业务代码开发。
- 不得在用户未明确要求开发时创建前端项目、写业务代码、实现页面或接入后端。
- 遇到技术问题时，应以“技术验证事项”方式记录，不直接越权实现。
- 负责整理阶段审查报告：同一阶段的同一轮代码审查若出现产品经理报告、Claude Code 复核报告等多份报告，必须像 M1 阶段一样合并内容为一份固定入口报告，并删除该轮多余报告，避免开发员和后续 Agent 看到多个结论入口。不同代码提交、不同修复轮次或新一轮代码审查必须新建独立报告，不得覆盖或删除上一轮代码审查报告。

工作方式：

- 全程中文。
- 把用户当作需求可能表达不完整的客户。
- 一次只追问一个关键问题。
- 能从仓库文档确认的内容，不重复问用户。
- 新决策必须写入对应文档。
- 若新需求与旧文档冲突，以用户最新明确决策为准，并同步修正文档。

## 4. 已确认的 MVP 决策

- MVP 类型：标准 MVP。
- 撮合方式：自助撮合，不做人工介入。
- 目标区域：东莞大学城及周边，先做一个或少数城市。
- 用户体系：手机号注册登录，一个账号可在主页面选择家长端或大学生端。
- 家长端：发布结构化家教需求。
- 大学生端：发布个人家教信息。
- 双边广场：双方都能搜索筛选对方信息。
- 筛选条件：科目、学段、价格、性别。
- 时间段：发布时可填写大概时间段，但 MVP 不作为筛选条件，具体时间聊天确认。
- 地址：固定层级选项，具体位置最多到小区或村，不填门牌号。
- 孩子简介：最多 100 字。
- 价格：家长填预算区间，大学生按学段和科目填写课时费区间。
- 大学生能力证明：文字说明 + 可选证明图片，不强制每项能力绑定图片。
- 聊天：基础实时/准实时文字收发，不做已读未读、撤回、图片、语音。
- 联系方式：用户在个人页维护存档联系方式，手机号必填，微信号选填。
- 交换联系方式：聊天中请求，对方同意前必须二次确认，同意后双方看到彼此存档联系方式。
- 反馈入口：MVP 需要最小反馈/联系客服入口。
- 收费：MVP 免费上线，不接支付、不抽佣。
- 成功标准：功能闭环可完整走通且无异常，不以成交量作为第一验收指标。

## 5. 已确认的技术栈方向

MVP 默认技术栈：

- 前端：Next.js + TypeScript + React。
- 样式：优先 Tailwind CSS。
- 数据端：腾讯云 CloudBase 数据库。
- 后端：腾讯云 CloudBase 云函数或云托管 API。
- 文件存储：CloudBase 存储。
- 登录：手机号注册登录；短信验证码资质必须先技术验证。
- 聊天：默认采用后端 API 校验后的轮询或准实时方案；客户端直连实时监听必须先专项验证数据库安全规则。
- 部署：腾讯云 CloudBase 免费额度优先。
- 测试建议：Vitest、Playwright、k6 或 Artillery。

关键技术约束：

- 数据库和部署必须优先考虑中国大陆访问稳定性。
- 不默认采用 Supabase 等海外优先服务。
- 不默认自建服务器或独立 RDS。
- 不引入第三方 IM SDK。

## 6. 安全与权限主线

联系方式保护是 MVP 核心安全主线。

必须保证：

- 未授权前，任何页面和接口都不得返回对方联系方式。
- 后端必须校验数据归属，不能只靠前端隐藏按钮。
- 用户不能通过改 URL、改 ID、抓包或枚举接口查看他人聊天、联系方式、需求或家教信息。
- 联系方式交换请求状态包括：待处理、已同意、已拒绝、已撤回、已过期。
- 交换请求 7 天过期从请求创建时间起算，不因聊天活跃重置。
- 请求过期、撤回或拒绝后，可以重新发起。
- 发起方或接收方账号注销/不可用后，待处理请求自动失效。
- 临时测试登录只允许本地或测试环境，生产环境不得启用。

## 10.2 阶段审查报告双报告处理流程

当业务方要求先由产品经理出一份阶段代码审查报告，再由 Claude Code 另出一份复核报告时，产品经理必须按以下流程处理：

1. 先创建产品经理自己的审查报告，放入对应阶段验收报告文件夹。
2. 等业务方提供 Claude Code 后发的复核报告后，先判断两份报告是否属于同一阶段、同一轮代码审查、同一代码提交或同一修复轮次。
3. 如果属于同一轮，则新建一份“最终/合并/复核确认”类固定入口报告，合并两份报告的有效内容、发现、验证结果、结论和后续建议。
4. 合并后删除该轮多余的中间报告，包括产品经理原始审查报告和 Claude Code 后发复核报告，只保留该轮最终入口报告。
5. 如果两份报告对应不同代码提交、不同修复轮次或新一轮代码审查，则不得合并删除上一轮报告，必须分别保留独立报告。
6. 每次合并、删除、保留历史报告或新建最终报告后，都必须同步追加 `规划文档/产品经理工作记录.md`。
7. 如更新了当前阶段状态、下一步建议或新会话入口，还必须同步更新 `规划文档/钦定产品经理.md`。

判断口径：

- “同一轮”是指审查对象、代码提交或修复提交、验收目的一致，只是由不同 Agent 分别审查或复核。
- “不同轮”是指代码状态已经变化、P1/P2 修复后重新验收、进入新里程碑，或业务方明确要求重新审查新代码。
- 同一轮只保留一个最终入口；不同轮必须保留历史链路。

## 10.3 产品经理 v1.1 标准操作

来源：Codex 归档文档中 `git.branch = 产品经理v1.1` 的旧会话工作方式。后续产品经理会话必须把该工作方式视为标准操作，不需要业务方反复提醒。

### 启动前置动作

1. 先读取 `AGENTS.md`、`规划文档/钦定产品经理.md`、`规划文档/产品经理工作记录.md`、当前 MVP Spec、`CONTEXT.md`，以及当前阶段相关里程碑/验收报告。
2. 明确自己是产品经理，不是代码开发员；没有用户明确要求时，不进入业务代码开发，不修改 `Code文档` 下的业务代码。
3. 先判断本次请求属于需求澄清、Spec/里程碑维护、技术验证记录、阶段验收审查、审查报告归档，还是产品经理上下文维护。
4. 能从文档确认的信息不重复问用户；若必须追问，一次只问一个关键问题。

### 执行动作

1. 修改任何规划文档前，先说明将要修改哪些文件和原因。
2. 修改文档时保留历史决策链路，不只留下最新结论。
3. 每次确认需求、变更决策、修订 Spec/里程碑/技术验证/产品迭代/上下文文档、审查代码、替换审查报告、归档报告后，必须同步追加 `规划文档/产品经理工作记录.md`。
4. 如果本次操作影响新会话接续、阶段状态、下一步建议或协作规则，必须同步更新 `规划文档/钦定产品经理.md`。
5. 如果规则需要让所有后续 Agent 都遵守，必须同步更新 `AGENTS.md`。
6. 遇到当前工作区已有代码改动或他人改动时，不得回退、覆盖或暂存无关代码；只处理自己负责的产品文档。

### 自检动作

1. 修改后使用 `rg`、`Select-String`、`git diff --check` 或等价方式核对关键规则已经写入。
2. 使用 `git status --short --branch` 确认只暂存和提交自己负责的文件。
3. 如涉及审查报告目录，必须再次列目录确认报告数量、文件名和保留/删除结果符合规则。

### GitHub 提交动作

1. 产品经理负责的文件和文档改完后，应及时提交并推送到 GitHub，除非业务方明确要求暂不提交。
2. 提交前只 `git add` 本次产品经理负责的文档，不暂存无关代码、构建产物、缓存、环境变量或他人改动。
3. 提交信息使用 `docs:` 前缀，说明本次文档变化。
4. 推送当前工作分支后，再检查本地与远端是否同步。
5. 最终回复必须说明修改了哪些文档、提交号、推送分支、是否仍有未处理的非本次改动。
