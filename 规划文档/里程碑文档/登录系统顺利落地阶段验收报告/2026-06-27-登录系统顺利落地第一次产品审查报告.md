## 2. 业务方可读说明

从用户视角看，本轮代码已经把原来的 M1 测试登录页改成了手机号验证码登录页：

- 用户可以输入手机号并请求短信验证码。
- 新手机号第一次验证码通过后，系统会自动创建账号，等同完成注册。
- 老手机号再次验证码通过后，会复用原账号登录。
- 登录后继续使用服务端可信 Cookie 保持登录状态，刷新页面不应丢失登录。
- 用户可以退出登录；退出后不应继续访问个人私有数据。
- 正式生产环境仍不允许测试登录、固定验证码 `000000`、`/api/auth/test-login` 或 `x-ungradu-test-user-phone` 临时身份头。

但要让正式环境真实用户真的收到短信，还必须由项目总控制人配置腾讯云短信和 CloudBase 生产环境变量，并在正式 URL 做冒烟验证。

## 9. 三项风险归类

### 9.1 `RequireTestSession` 命名遗留

风险归类：P2 命名遗留 / 协作可读性风险。

当前判断：不影响用户登录。

原因：该组件虽然名称仍带 `TestSession`，但实际读取的是 `/api/auth/session` 的服务端 Cookie 会话，不是 M1 测试登录能力。建议后续重命名，避免 Zcode、代码开发员或后续 Agent 误读。

### 9.2 手机号承接既有业务身份

风险归类：账号体系兼容风险 / 后续数据迁移项。

当前判断：不阻塞本阶段登录系统落地。

原因：当前 Cookie 仍以手机号承接既有业务身份，能兼容已有家长、老师、需求等业务数据；新增 `userId` 主要用于短信登录账号记录。后续若要支持更复杂账号体系、换绑手机号、实名认证或多身份聚合，需要规划从手机号主标识迁移到稳定用户 ID。

### 9.3 真实短信未在生产 URL 冒烟

风险归类：外部配置与生产验收风险。

当前判断：不属于仓库内代码返工项，但阻塞正式宣布生产登录完成。

原因：仓库内已具备短信登录闭环；真实用户能否收到短信，取决于腾讯云短信配置、CloudBase 环境变量、签名模板审核、短信额度和正式 URL 部署。必须在正式 URL 完成真实短信冒烟后，才能宣布“正式环境用户可以正常登录”。
