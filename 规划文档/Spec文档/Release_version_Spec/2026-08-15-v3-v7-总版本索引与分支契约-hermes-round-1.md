## 严重发现

### S1 — 串行链的前置门禁强度逐级漂移（关闭 vs 已验收证据 vs 退出门）

- 严重级别：SERIOUS
- 位置：L43–46（映射表"前置版本"列）、L50、L101、L124、L146、L20、L197
- 证据：
  - L50 统一要求 "V3 通过并关闭 → V4 通过并关闭 → V5 通过并关闭 → V6 通过并关闭"
  - L43（V4 前置）="V3 完成全部适用退出门"；L44（V5 前置）="V4 完成全部适用退出门"
  - L45（V6 前置）="V5 已验收证据与退出门"；L46（V7 前置）="V6 关闭 receipt 与退出门"
  - L101（V4 入口）="V3 已完成其退出门**并有可引用的关闭 receipt**"（最强）
  - L124（V5 入口）="V4 完成退出门"（无关闭 receipt 要求）
  - L146（V6 入口）="V5 已验收证据包 V5_ACCEPTED_EVIDENCE_REF 完整且可复读"（最弱，既不要求关闭也不要求退出门）
  - 而 L20、L197 明确 "分支完成/技术通过/文档通过/任何单层 PASS 均不等于 Issue 关闭"
- 影响：同一份门禁契约内，下游启动所需的上游强度有三种口径。按 L146 的字面，V6 可在 "V5 证据包被验收" 后即启动，早于 ISSUE-0036 被 Issue 管理员 canonical 关闭——直接违背 L50 的严格串行链与 §9（L233）的统一关闭顺序。文档的核心用途就是串行门禁，门禁措辞漂移构成下游执行风险。
- 修正：将所有下游前置统一为 "上一 Issue 管理员已决定 canonical 关闭 + 可引用 closure receipt"（对齐 L101 措辞），同步改写 L43–46、L124、L146。若确有意允许"证据验收即可启动"（弱化），则必须同步改弱 L50 并说明理由，两种口径不得并存。
- 未来闭合触发：冻结前逐条核对 L43–46、L101、L124、L146、L50 五处措辞强度一致。

### S2 — V3 base commit 未知，且无建立规程 / owner / 兜底，并被误归类为用户确认项

- 严重级别：SERIOUS
- 位置：L19、L42、L67、L252、§4.1（L56–63）、§11（L262）
- 证据：
  - L42（V3 前置）="上一已验收版本的精确 base，**当前未知**"
  - L19/L67 强调 known HEAD（33314857…）"不是上一已验收版本确定提交，不得直接当作任何 V3 base"
  - L252 将 "V3 的精确 base commit" 列入 "用户确认前未决"
  - §4.1 只定义 base receipt **应包含什么**，未定义如何**确立**该 base
  - §11 仅要求总负责人 "核对输入 provenance"
- 影响：
  1. 整条 V3→V7 链的根基（V3 base，逐级级联到 V4–V7）当前未知，且文档已否定唯一已知候选（known HEAD），却未给出任何找回"上一已验收版本确定提交"的规程、责任人或兜底（如 tag/发布记录/CI 记录/reflog 审计，或重新基线+风险接受）。根基无解则整链无限期阻塞。
  2. "确定 base commit" 是技术 provenance 事实，不是用户偏好；把它放进"用户确认前未决"是类别错误——用户无法确认 git provenance。按此执行可能由用户在未验证 SHA 下背书，直接违反 §4.2 自身约束。
- 修正：明确 (a) 谁有权认定"上一已验收版本"及其确定提交；(b) 何种证据（tag/发布记录/CI/独立复核 hash）足以证明某 commit 已验收；(c) provenance 不可恢复时的兜底决策路径。将 L252 从"用户确认"项改为"总负责人/code owner 待建立"项，用户仅确认范围与残余风险。
- 未来闭合触发：冻结前必须产出符合 §4.1 的 exact base receipt，或记录明确兜底决策（重新基线+风险接受），二者缺一不得冻结。
